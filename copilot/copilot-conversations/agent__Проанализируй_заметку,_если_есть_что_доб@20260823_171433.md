## Что уже есть

Заметка описывает два механизма из классической схемы ByteByteGo:

1. **Token-based authentication** — логин/пароль → сервер выдаёт токен с ограниченным сроком жизни → клиент ходит с ним в заголовке HTTP.
2. **HMAC authentication** — сервер выдаёт пару Public App ID + API Key, клиент считает подпись `hmac A` от данных запроса, сервер воспроизводит ту же подпись `hmac B` своим экземпляром ключа и сравнивает.

Оба сценария расписаны по шагам корректно, картинки на месте (обе лежат в `attachments/`, ссылки не битые).

## Неточности, которые стоит поправить

- **«SHA256 или MD5»** — MD5 криптографически скомпрометирован (коллизии), для подписей его использовать нельзя. В вашей же заметке [[Хеширование]] это прямо сказано. Лучше: SHA-256/SHA-384, упомянуть MD5 только как антипаттерн.
- **«публичный (Public App ID)»** — это не ключ, а просто идентификатор клиента, он не секретный. Секрет — только API Key. Стоит уточнить формулировку.
- В шаге 6–7 не хватает запятой («совпадают, ответ посылается…») — мелочь.

## Чего не хватает (главное)

- **JWT** — самый частый формат «токена» из первого пункта вообще не назван: структура header.payload.signature, чем подписан, какие claims, где живёт срок действия. Это ядро темы.
- **OAuth 2.0 / OpenID Connect** — делегированная авторизация и флоу (authorization code + PKCE, client credentials). Для web API это индустриальный стандарт, без него тема неполная.
- **API Key и Basic Auth** — хотя бы абзацем: когда допустимы, почему Basic только поверх TLS.
- **Куда класть токен на клиенте**: localStorage (уязвим к XSS, есть в [[Межсайтовый скриптинг (Cross-site scripting, XSS)]]) vs httpOnly cookie (риск CSRF, есть в [[Совместное использование ресурсов между источниками (Cross-Origin Resource Sharing, CORS)]]-тематике). Это практический вопрос №1.
- **Refresh token и revocation**: что делать при компрометации access-токена, ротация refresh-токенов, blacklist/logout.
- **Защита HMAC от replay-атак**: timestamp + nonce в подписываемых данных — без этого перехваченный запрос можно переиграть.
- **Сравнение подписей за константное время** (timing attack) — классическая деталь реализации HMAC.
- **Session vs Token** — короткая таблица сравнения (stateful/stateless, масштабирование, logout).
