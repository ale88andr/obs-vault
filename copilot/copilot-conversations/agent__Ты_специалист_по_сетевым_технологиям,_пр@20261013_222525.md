## Критические ошибки (надо исправить)

**1. Ключ `-i` перепутан с `-I` — дважды (строки 37 и 65).**

Это самая грубая ошибка. В списке ключей и в разделе про IPv6 написано, что `-i` задаёт интерфейс. На самом деле:

- `-i` (строчная) — **интервал между пакетами** в секундах (по умолчанию 1 с; значения меньше 0.2 с разрешены только root).
- `-I` (прописная) — **интерфейс или源-адрес**, с которого идут запросы: `ping -I eth0 8.8.8.8`.

Правильно: `-i` — интервал, `-I` — интерфейс.

**2. Описание `-w` неполное и путается с `-W` (строка 36).**

Текст говорит только «`-w` — время завершения команды». Точнее:

- `-w deadline` — общий дедлайн команды в секундах (ping выйдет по его истечении, сколько бы ответов ни пришло);
- `-W timeout` — сколько ждать ответа **на один пакет** (тоже в секундах).

Без различения `-w` и `-W` список ключей вводит в заблуждение.

**3. Bash-скрипт нерабочий (строки 300–309).**

Там четыре ошибки сразу:

- `If [` и `Fi` — в bash ключевые слова строчные: `if` и `fi`;
- `[ $? -eq 0]` — нет пробела перед `]`, нужен `[ $? -eq 0 ]`;
- shebang `#! /bin/bash` — по канону `#!/bin/bash` (без пробела);
- смешаны отступы, а `then` стоит после `]` — для однострочной записи ок, но лучше разнести.

Рабочий вариант:

```bash
#!/bin/bash

if ping -c 1 -W 2 "$HOST" > /dev/null 2>&1; then
    # команда, если хост ответил
    echo "OK"
else
    # узел недоступен
    echo "DOWN"
fi
```

Кстати, проверять `$?` после `ping` можно, но `if ping ...` короче и надёжнее.

**4. `traceroute` описан неверно (строка 285).**

Написано: «traceroute посылает тот же ICMP-пакет, что и ping». Это не так:

- `tracert` (Windows) — да, по умолчанию шлёт ICMP Echo;
- `traceroute` (Linux) по умолчанию шлёт **UDP-датаграммы** на высокие порты (часто 33434+);
- ICMP-режим в Linux включается флагом `-I` (`traceroute -I`).

Механика с инкрементом TTL и ответами «Time Exceeded» — правильная, тут всё ок.

**5. `telnet` «по умолчанию установлен на Linux» — уже неверно (строка 71).**

В современных дистрибутивах (RHEL/CentOS 8+, Debian/Ubuntu свежих, Fedora) telnet-клиент **не ставится** по умолчанию. Лучше показать актуальную альтернативу:

```bash
nc -zv host 443        # netcat
curl -v telnet://host:443   # или /dev/tcp в bash
```

## Неточности и устаревшие приёмы

**6. Приём с `ccze` и `xargs` (строки 93–95) устарел и ненадёжен.**

Формула `ping [host] | xargs -n1 -i bash -c '...'` сомнительна: `-i` в xargs объявлен устаревшим и конфликтует с `-n1`. В GNU iputils уже давно есть штатный флаг **`-D`** — «печатать timestamp перед каждой строкой»:

```bash
ping -D -c 4 8.8.8.8
```

Никаких сторонних пакетов и костылей не нужно. Стоит либо переписать раздел на `-D`, либо упомянуть его как основной способ.

**7. Десятичный разделитель (строки 203, 231).**

«задержки... равен 6,798» и «уменьшаем до 1472» — тут всё по делу, но `6,798` — это локаль русского окружения. В выводе `ping` обычно точка: `rtt min/avg/max/mdev = 0.5/6.798/...`. Стоит писать так же, как реально в терминале, иначе читатель ищет запятую.

**8. Раздел про MTU (строки 213–237) — неполный.**

Стоит добавить, что:

- MTU 1500 — это L3 (IP-пакет); кадр Ethernet с заголовками — 1518 байт;
- значение `1472` = `1500 − 28` (20 байт IP-заголовка + 8 байт ICMP), это классический ориентир, но обоснование не дано;
- типовой реальный вывод ошибки выглядит как `ping: local error: message too long, mtu=1500` (не просто «Message too long»);
- для проверки PMTU по всему маршруту лучше использовать `ping -M do -s <N>` и что это работает только если по пути нет фильтрации ICMP.

**9. Раздел про прокси (строки 41–47) можно усилить.**

Утверждение «ping не может работать с прокси» в целом верное (ICMP проксируется редко), но:

- существует ping через SOCKS5 у некоторых инструментов;
- HTTP-прокси «пингуется» через `curl` (что уже упомянуто);
- стоит добавить специализированные утилиты: `tcping`, `nping`, `hping3`.

**10. Broadcas t-ping `-b` (строки 105–109).** Нужно уточнить: `ping -b <адрес .255>` требует прав root и часто **не работает** — многие ОС и Wi-Fi-инфраструктура игнорируют broadcast ICMP Echo. И в этом же абзаце вывод «если хост недоступен — блокируется ICMP либо проблема с сетью» логически не связан с командой выше (речь ведь о broadcast, где обычно никто не отвечает).

## Что стоит добавить

**A. Exit-коды — важно для скриптов и как раз рядом с вашим bash-разделом:**

- `0` — есть хотя бы один ответ;
- `1` — ответов нет;
- `2` — ошибка (неверный ключ, нет сети и т.п.).

**B. Таблица различий Linux / Windows — в заметке поминается `tracert` из Windows, но все команды даны под Linux.** Разница ключей значительная и путает новичков:

| Действие | Linux (`ping`) | Windows (`ping`) |
| --- | --- | --- |
| Число пакетов | `-c 4` | `-n 4` |
| Размер данных | `-s 100` | `-l 100` |
| Тайм-аут | `-w 5` (сек) | `-w 5000` (мс) |
| Пинг до остановки | по умолчанию | `-t` |
| Не фрагментировать | `-M do` | `-f` |
| TTL | `-t 64` | `-i 64` |
| Только IPv6 | `-6` | `-6` |

Особенно важно: `-i` и `-w` в Windows означают совсем другое, чем в Linux.

**C. Полезные ключи, которых нет в списке (строки 33–37):** `-n` (не резолвить имена — заметно ускоряет вывод), `-q` (только итоговая статистика), `-D` (таймстемп), `-a` (звук при ответе/потере), `-f` (flood, только root), `-t <ttl>`, `-W <сек>`.

**D. Почему ping может «врать».** Это ключевой практический момент, которого в статье нет: ICMP часто фильтруется и депротизируется (QoS, ICMP rate limiting). Поэтому «хост не пингуется» ≠ «хост недоступен», а высокий RTT по ICMP не всегда отражает реальную задержку прикладного трафика.

**E. Разбор вывода.** Стоит расшифровать строки `time=`, `ttl=` (сколько хопов прошёл пакет: `TTL_по_умолчанию − остаток`), `mdev` (джиттер), `packet loss`. У вас эти значения используются, но не объясняются.

**F. Инструменты вокруг ping:** `mtr` (ping + traceroute, live), `fping` (ping многих хостов списком — прямо под сценарий «ping всей подсети», где `-b` ненадёжен), `hping3`, `nping`. Для опроса подсети `fping -a -g 192.168.1.0/24` куда лучше broadcast-пинга.

**G. Ссылки на первоисточник.** Текст явно заимствован с merionet — стоит добавить атрибуцию и дату актуализации, чтобы при обновлении было понятно, что сверять.
