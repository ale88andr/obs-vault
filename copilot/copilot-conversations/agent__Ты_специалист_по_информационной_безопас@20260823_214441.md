## Что в заметке устарело или неверно

- **Рукопожатие описано по схеме RSA key exchange** (клиент шифрует premaster-секрет открытым ключом сервера). Это уязвимый к ретроспективной расшифровке режим, который давно не используют. Современный стандарт — **TLS 1.3** (RFC 8446): эфемерный (EC)DHE, forward secrecy, рукопожатие за 1 RTT. Стоит либо переписать разбор под TLS 1.3, либо явно пометить текущий текст как «TLS 1.2 и ранее» и добавить сравнение.
- **«Зелёный замок = сайт безопасен»** — опасное упрощение. Замок означает только валидность сертификата и шифрование канала. Фишинговые сайты массово используют бесплатные валидные сертификаты (Let's Encrypt). Браузеры уже отказались от «зелёного» замка и надписи Secure. Это стоит переформулировать, иначе заметка учит плохой ментальной модели.
- **Пункт 3 рукопожатия сформулирован некорректно**: сервер не «шифрует nonce закрытым ключом». Сервер отправляет сертификат (открытый ключ), а подпись закрытым ключом накладывается на параметры обмена ключами (ServerKeyExchange при DHE) или на Finished-сообщения. Сейчас текст учит неправильной криптографии.
- **Сжатие в протоколе записи** упомянуто как штатная функция — оно отключено и удалено из стандарта после атак CRIME/BREACH.
- **MAC-then-encrypt** — описание верно для старых CBC-режимов, но современные наборы (AES-GCM, ChaCha20-Poly1305, см. [[Режим GCM]]) используют AEAD, где целостность встроена в шифрование. Кстати, у вас уже есть заметка про GCM — напрашивается связка.
- **Про порты**: формулировка «изменение номера порта позволяет TCP направлять трафик…» технически бессмысленна. Порт лишь указывает процессу, какой сервис слушать; безопасность он не добавляет. Плюс сейчас почти всё живёт на 443 и различается по ALPN/SNI.

## Что я бы добавил обязательно

- **История версий и статус протоколов**: SSLv2/v3 (мёртвы, POODLE), TLS 1.0/1.1 (запрещены RFC 8996 в 2021), TLS 1.2, TLS 1.3 — таблицей со статусом.
- **Perfect Forward Secrecy** — ключевое понятие, полностью отсутствует. Именно ради него умерли статические RSA-обмены.
- **Инфраструктура сертификатов**: цепочка доверия, корневые/промежуточные CA, отзыв (CRL → OCSP → OCSP stapling), Certificate Transparency. Без этого непонятно, что именно проверяет клиент.
- **TLS 1.3 отличия**: 0-RTT early data и его главный практический риск — replay-атаки; session tickets/PSK вместо session ID; обязательный DHE.
- **Атаки на TLS** хотя бы списком с одним предложением каждый: BEAST, CRIME, POODLE, downgrade/FREAK/Logjam, Heartbleed (баг реализации, не протокола), Lucky13, ALPACA, SSL stripping (и ответ на неё — **HSTS**). У вас есть [[Атака Man-In-The-Middle]] — логично сослаться и раскрыть MitM-тему именно там.
- **SNI и приватность**: имя хоста передаётся в открытом виде в ClientHello; ECH (Encrypted Client Hello) как решение. Для ИБшника важно: DPI видит SNI (у вас есть заметка про [[Технология DPI]]).
- **mTLS** — клиентские сертификаты, критично для API и сервисных сетей (перекликается с [[Аутентификация в web API]]).
- **Практический чеклист харднинга**: отключить TLS < 1.2, только AEAD-наборы, HSTS, OCSP stapling, ограничение срока жизни сертов; инструменты проверки — testssl.sh, sslyze, SSL Labs.
- **Учитывая контекст вашего хранилища** (разделы СКЗИ, ViPNet, ФСТЭК): отдельным блоком — ГОСТовские профили TLS (реализации КриптоПро/ViPNet, требования ТК26) и место TLS среди VPN-технологий рядом с [[IPSec и VPN]]. Для аудиторий по 152-ФЗ/ГИС это то, что реально спрашивают.
- **Перспектива**: пост-квантовые гибридные обмены ключами (X25519 + ML-KEM) — уже развёрнуты в основных браузерах, через пару лет станет обязательной темой.
