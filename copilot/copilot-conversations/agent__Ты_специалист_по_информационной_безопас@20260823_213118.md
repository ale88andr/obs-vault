## Сначала — что стоит исправить

1. **Несостыковка TLS 1.2 vs 1.3.** Заголовок говорит «процесс подтверждения связи в TLS 1.3», но дальше перечисляются `Certificate`, `Server Key Exchange`, `Server Hello Done` — это сообщения **TLS 1.2**. В TLS 1.3 нет ни ServerKeyExchange, ни ServerHelloDone: ключ передаётся в расширении `key_share` прямо внутри ClientHello/ServerHello, а всё после ServerHello (`EncryptedExtensions`, `Certificate`, `CertificateVerify`, `Finished`) уже **зашифровано**. Судя по всему, скриншоты из дампа TLS 1.2 — стоит явно пометить это или переснять на 1.3.

2. **Логика проверки сертификата перепутана.** Проверка подписи сертификата подтверждает *подлинность самого сертификата* (его выпустил указанный CA и содержимое не изменено), а не «факт обладания сервером секретным ключом». Владение приватным ключом доказывается отдельно — сервер подписывает транскрипт рукопожатия (`CertificateVerify` в 1.3 / параметры в ServerKeyExchange в 1.2).

3. **Про резолв доменного имени — неверно.** Браузер не сравнивает IP-адреса после DNS-резолва. Идёт проверка **hostname**: домен из URL сверяется с полем **SAN** (Subject Alternative Name) / CN сертификата. DNS тут вообще не участвует — иначе любой MITM с подменой DNS проходил бы проверку.

4. **Мелочи:** обозначения `DH(c,S)`/`DH(s,C)` используют разный регистр для одного и того же; стоит унифицировать. И добавить, что результат DH — это ещё не «keys», а только shared secret: дальше идёт **HKDF key schedule** (handshake/application traffic secrets).

## Что я бы добавил по содержанию

**Завершить историю рукопожатия** (сейчас она без финала):
- `Finished` и проверка транскрипта — почему это защита от MITM;
- key schedule TLS 1.3: HKDF-Extract/Expand, откуда берутся ключи шифрования;
- в TLS 1.2 — ChangeCipherSpec и почему в 1.3 он остался только как костыль совместимости.

**Record protocol** — второй протокол внутри TLS, о нём ни слова: типы записей (Handshake, Alert, ApplicationData), AEAD-шифрование, номера последовательностей, `close_notify`.

**Анатомия cipher suite.** Например `TLS_ECDHE_RSA_WITH_AES_256_GCM_SHA384` → key exchange / auth / bulk cipher / mode / hash. Полезно и то, что в 1.3 осталось всего 5 наборов.

**Таблица «что убрали в TLS 1.3»** — это лучшая иллюстрация эволюции: RSA key exchange (нет forward secrecy), CBC, RC4, SHA-1/MDC, компрессия, renegotiation.

**Атаки** — для security-заметки это must-have:

| Атака | Против чего | Вывод |
| --- | --- | --- |
| POODLE | SSL 3.0 | отключить SSL |
| BEAST | CBC в TLS 1.0 | 1.1+/AES-GCM |
| Lucky13 | тайминги CBC-MAC | AEAD-only |
| FREAK / Logjam | экспортные/DH-наборы | сильные параметры |
| Heartbleed | реализация OpenSSL | патчи, а не протокол |
| DROWN | SSLv2 | полный запрет legacy |

Важная мысль, которой не хватает: **уязвимости чаще в реализациях и конфигах, чем в самом протоколе**.

**Практика и харденинг** (то, с чем реально работаешь):
- конфигурационные baseline'ы: OWASP TLS Cheat Sheet, RFC 7525/9325, NIST SP 800-52, Mozilla SSL Config Generator;
- инструменты аудита: `testssl.sh`, `sslyze`, `sslscan`, SSL Labs;
- пара команд `openssl s_client -connect host:443 -tls1_3` и трюк с `SSLKEYLOGFILE` для расшифровки своего трафика в Wireshark — идеально ложится на ваш стиль заметки со скриншотами;
- смежное: **HSTS**, OCSP stapling + revocation вообще, Certificate Transparency, **session resumption** и риски **0-RTT replay**, SNI → ECH, mTLS, DTLS для UDP.

**Актуальное:** гибридный постквантовый key exchange (X25519+ML-KEM) уже развёрнут в Chrome/Cloudflare — в 2026 году заметке про TLS он нужен хотя бы абзацем.
