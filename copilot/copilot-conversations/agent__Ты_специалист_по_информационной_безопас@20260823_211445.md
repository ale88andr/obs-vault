## Общая оценка

Заметка — хороший вводный конспект уровня «что такое PKI» (похоже, перевод англоязычного курса): покрывает жизненный цикл ключа, ЦС, X.509, цифровую подпись и иерархию корневой/промежуточный ЦС. Но это именно **теория для новичка** — в ней нет ни практики проверки статуса сертификатов, ни корпоративного контекста, ни атак. И есть две фактические ошибки.

## Ошибки, которые я бы исправил первым делом

1. **Строка про CRL неверна.** Сейчас написано: *«по истечении срока действия сертификат… помещается в список отзыва сертификатов (CRL)»*. Это неверно: **истечение срока ≠ отзыв**. В CRL попадают сертификаты, отозванные *до* истечения срока (скомпрометирован ключ, сменились данные владельца, компрометация ЦС). Истёкший сертификат просто становится недействительным сам по себе.

2. **«Регистрирующий орган (RA)» стоит внутри списка полей X.509** (строка 53). RA — это не поле сертификата, а отдельный компонент инфраструктуры: регистрирующий орган проверяет личность заявителя *от имени* ЦС и передаёт ему запрос на выпуск. Его нужно вынести в собственный подраздел «Компоненты PKI: ЦС / RA / репозиторий / конечные субъекты».

3. Мелочь, но определение в начале говорит, что PKI обеспечивает конфиденциальность асимметричным шифрованием. На практике асимметрика используется для аутентификации и обмена ключами, а данные шифруются симметрично (это хорошо раскрыто у вас в [[TLS]]) — стоит уточнить, иначе закрепляется частое заблуждение.

4. «Сергей Алексеевич» как имя получателя выдаёт машинный перевод (Alice/Bob) и отвлекает. Я бы заменил на Алису и Боба.

## Что бы я добавил

### Приоритет 1 — критичные пробелы

- **Enrollment: процесс выпуска сертификата.** Заметка прыгает от генерации ключа сразу к распространению. Не хватает звена: заявитель генерирует пару ключей локально → формирует **CSR (запрос на подпись, PKCS#10)** с открытым ключом и атрибутами Subject/SAN → RA/CA проверяет личность → CA подписывает и выпускает сертификат. Без CSR непонятно, как открытый ключ вообще попадает в сертификат.
- **Проверка статуса сертификата на практике:** сравнение CRL vs OCSP vs OCSP Stapling, почему браузеры фактически игнорируют жёсткую проверку отзывов, тренд на **короткоживущие сертификаты** (Let's Encrypt — 90 дней) и автоматизацию через **протокол ACME**. Это то, с чем специалист сталкивается каждый день.
- **Валидация цепочки доверия:** как именно клиент строит цепочку leaf → intermediate → root из своего trust store, роль расширений AIA/CDP, кросс-подпись. Рисунок иерархии есть, а алгоритма проверки — нет.
- **Хранение приватных ключей:** HSM, TPM, программные key vaults, неизвлекаемые ключи, key escrow/backup. Пункт «Хранение» есть в жизненном цикле, но не раскрыт вовсе — а это главный операционный риск.

### Приоритет 2 — сильно усиливает заметку

- **Типы сертификатов:** DV / OV / EV, wildcard, SAN (multi-domain), code signing, client certificates, S/MIME. Таблицей на 5 строк:

| Тип | Для чего | Уровень проверки |
| --- | --- | --- |
| DV | сайты, API | только владение доменом |
| OV | организации | проверка юрлица |
| EV | банки, финтех | расширенная проверка юрлица |

- **Корпоративная PKI:** AD CS (Active Directory Certificate Services), автоэнроллмент через GPO, лучшая практика **офлайн-корневого ЦС**, публикация CDP/AIA. В заметке уже затронута иерархия — логичное продолжение.
- **Атаки на PKI и инциденты:** взломанный ЦС (классика — DigiNotar, 2011: скомпрометированные сертификаты → MITM в Gmail), недобросовестные ЦС (Symantec — исключение из trust store), MITM через корпоративные прокси с подменным корневым сертификатом, коллизии SHA-1, простои из-за просроченных сертфикатов. Хорошо ложится на вашу заметку [[Атака Man-In-The-Middle]] и тему [[Безопасность транспортного уровня (TLS)]]. Здесь же — **Certificate Transparency** как механизм обнаружения несанкционированных выпусков.
- **Где применяется, помимо HTTPS:** mTLS для сервис-сервис аутентификации, VPN, Wi-Fi 802.1X, подписание кода и документов, JWT/JWS поверх PKI.
