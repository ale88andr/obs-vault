## Главная мысль заметки

[[Windows Internals]] — это не набор фактов про Windows, а описание **двух границ и того, как система их пересекает**.

Первая граница — между процессами: чтобы одно приложение не могло испортить память другого. Вторая — между пользовательским кодом и ядром: чтобы приложение не могло сделать с машиной что угодно. Всё остальное в заметке — механика обслуживания этих двух границ.

## Память: почему адреса «ненастоящие»

Процесс — это прежде всего **изолированное адресное пространство**. Если бы программы работали с физическими адресами напрямую, любая из них могла бы прочитать пароль из памяти другой или затереть код ядра. Поэтому каждый процесс живёт в своей виртуальной реальности: он видит непрерывное пространство, а железо (MMU) на лету переводит его адреса в физические страницы по 4 КБ.

Перевод — это дерево из четырёх уровней. Адрес режется на куски по 9 бит (по 512 записей на уровень) плюс 12 бит смещения внутри страницы. 9×4 + 12 = 48 бит — отсюда и размер адресного пространства. Каждая запись — 64 бита, из которых часть отведена под атрибуты: «только чтение», «исполняемый», «доступно только ядру».

Дальше — три приёма, которые стоит держать в голове:

- **Разделение DLL.** Разные процессы могут указывать на одну и ту же физическую память — так `kernel32.dll` существует в одном экземпляре на всех.
- **Copy-on-write.** Пока страница только читается, она общая. Как только кто-то в неё пишет, система делает ему личную копию и подменяет запись только у него. Остальные продолжают видеть оригинал.
- **Kernel-бит.** Код ядра присутствует в адресном пространстве процесса, но помечен как доступный только из привилегированного режима. Попытка тронуть его из обычного кода — исключение и падение.

## Режимы: одна дверь в ядро

Процессор умеет работать в кольцах: ring 3 — приложение, ring 0 — ядро. Разница не в «правах доступа к файлам», а в том, какие инструкции доступны. Приложению запрещены привилегированные операции — и создание процесса как раз из них.

Значит, нужен легальный способ попросить ядро что-то сделать. Это **системный вызов**: кладём номер сервиса, выполняем инструкцию `syscall`, процессор переключается в ring 0, и диспетчер (`KiSystemCall64Shadow`) по номеру находит обработчик в таблице SSDT.

Тут важны детали, которые легко пропустить: `syscall` **не** переключает стек автоматически. Ядро сначала через `swapgs` получает доступ к своим структурам (KPCR), а потом отдельно подменяет `RSP` на стек ядра — иначе оно работало бы на стеке, который контролирует приложение.

## Железо и регистры: где «мы находимся»

Блок про кэши, CU/ALU и MMU нужен для одной мысли: у памяти есть иерархия скорости, и регистры — её вершина. Поэтому состояние выполнения процесса — это буквально значения регистров.

Из них запомнить стоит четыре:

- `RIP` — какая инструкция выполняется;
- `RSP`/`RBP` — вершина и база текущего фрейма стека;
- `RFLAGS` — флаги условий (результат последнего сравнения);
- `CR3` — физический адрес корневой таблицы страниц, то есть **«чей это адресный мир»**. Переключение процесса — во многом именно смена `CR3`.

`GS` — отдельная история: в user mode он указывает на TEB (данные потока), а в ядре — на KPCR (данные ядра). Именно поэтому `swapgs` — обязательный первый шаг syscall.

## Поток и стек

Процесс — это контейнер ресурсов, но сам по себе он не выполняется. Выполняется **поток**: у него свой набор регистров, свой стек и своя локальная память. Один процесс может иметь много потоков, и они реально работают параллельно на разных ядрах.

Стек — область, которая растёт вниз, от старших адресов к младшим. Каждый вызов функции резервирует кусок — stack frame: аргументы, локальные переменные, сохранённый `RBP` и адрес возврата. `ret` просто забирает этот адрес в `RIP`. Отсюда и все классические атаки: переполнил буфер на стеке — перезаписал адрес возврата — получил управление.

## PE-файл: как выглядит программа на диске

`.exe` — это контейнер **Portable Executable**. Начинается он с DOS-заголовка и DOS-заглушки (той самой «This program cannot be run in DOS mode») — наследство совместимости. Дальше — NT headers: там сказано, под какую архитектуру собран файл, где начинается код, какой у образа предпочтительный базовый адрес. Потом — таблица секций: `.text` (код), `.data` (изменяемые данные), `.rdata` (только чтение).

Ключевая для безопасности деталь: у каждой секции есть **атрибуты R/W/X**. Именно они не дают писать в код. Запись в read-only секцию — это access violation, а не «просто сработало».

## Windows API: три этажа

Приложение почти никогда не общается с ядром напрямую. Цепочка такая: `kernel32`/`kernelbase` (удобный документированный API) → `ntdll` (тонкие обёртки над системными вызовами) → `syscall` → ядро.

В `ntdll` три вида функций: `Nt*` — сами вызовы, `Zw*` — те же вызовы, но для кода ядра, `Rtl*` — вспомогательные утилиты. Верхние слои нужны, потому что дают разбор аргументов, проверки и нормальные коды ошибок; звать `ntdll` напрямую — значит делать всю эту работу самому (чем, кстати, и пользуются авторы вредоносов).

## Что происходит при двойном клике

Это центральный сюжет заметки. `explorer.exe` вызывает `CreateProcess`, и дальше разворачивается длинная цепочка:

1. **Открыть файл образа** — `IoCreateFileEx`.
2. **Сделать из файла section object** — «проектор», который позволяет отобразить файл в память, а не читать его целиком.
3. **Создать процесс** — `PspAllocateProcess` порождает `EPROCESS` (объект процесса), внутри которого лежит `KPROCESS` — часть, видимая только ядру.
4. **Выдать токен доступа** — тот самый «паспорт» с SID пользователя, группами и привилегиями. Обычно это копия токена родителя; создаётся он при логине в LSASS.
5. **Построить адресное пространство** — инициализируется working set (страницы, реально лежащие в физической памяти), создаётся дерево VAD, мапятся образ и `ntdll`.
6. **Создать PEB** — пользовательскую «витрину» процесса: список загруженных DLL, база образа, флаг «меня отлаживают».
7. **Создать первый поток** — `ETHREAD`, пользовательский стек, `TEB`, `KTHREAD`, стек ядра, контекст.
8. **Вставить процесс и поток в списки ядра** и пометить поток готовым к выполнению.
9. **Сообщить подсистеме** — через ALPC отправить `csrss` данные о новом процессе (хэндлы, адрес PEB).
10. **Стартовать поток** — вручную собрать trap frame и выполнить `iretq`, чтобы «вынырнуть» в user mode.
11. **Загрузить DLL** — `LdrInitializeThunk` разбирает каталог импорта, находит нужные библиотеки, заполняет IAT реальными адресами (которые из-за ASLR заранее неизвестны) и в конце передаёт управление точке входа.

## Объекты и права

Почти всё в Windows — объект: процесс, поток, файл, секция. У каждого есть заголовок со счётчиками ссылок и хэндлов: когда оба обнулились, объект уничтожается. Из user mode объект напрямую не потрогать — нужен **хэндл**, то есть пропуск с конкретным набором прав.

А кто какие права имеет — описано в **security descriptor**: владелец, DACL (кому что можно), SACL (что писать в аудит). Внутри — записи ACE, а субъекты задаются через SID, где последняя часть (RID) и есть «кто именно».
