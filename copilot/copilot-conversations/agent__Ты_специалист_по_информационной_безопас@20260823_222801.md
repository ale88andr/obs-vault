## Критичные пробелы (без них защита неполная)

### 1. mDNS — второй «близнец», о котором заметка молчит
LLMNR отключён, а атака всё ещё работает, потому что цепочка резолвинга в Windows: DNS → LLMNR → NetBIOS → **mDNS** (UDP `5353`, мультикаст `224.0.0.251`, имена `.local`). Responder травит его точно так же. Через GPO он не выключается, только реестром:

```powershell
Set-ItemProperty 'HKLM:\SYSTEM\CurrentControlSet\Services\Dnscache\Parameters' -Name EnableMDNS -Value 0
# + перезапуск службы Dnscache или перезагрузка
```

Это самый опасный пробел заметки: читатель выполнит Шаги 1–2 и будет считать сеть защищённой.

### 2. WPAD
Responder из коробки поднимает HTTP-сервер и отдаёт фальшивый `wpad.dat` — трафик жертвы идёт через прокси атакующего, включая перехват кредов. Стоит добавить отдельным пунктом: GPO «Turn off Auto Proxy discovery» + отключение службы `WinHttpAutoProxySvc`.

### 3. IPv6 / mitm6
Классическая ситуация с реальных проектов: админ выключил LLMNR/NetBIOS, пентестер берёт домен через `mitm6` (спуфинг DHCPv6/DNS over IPv6) и релей в LDAPS. Отсюда же — важное уточнение к Шагу 3: **SMB Signing защищает только от релея на SMB**. Для защиты от релея на LDAP нужны LDAP Signing + Channel Binding (по умолчанию в свежих патчах MS они частично ужесточены, но требуют явной проверки), для релея на ADCS — EPA на сервере сертификации (атаки класса ESC8).

### 4. Коэрсия вместо опечаток
Сценарий «бухгалтер опечатался» — учебный. На практике атакующий не ждёт ошибки: `PetitPotam`, `PrinterBug`, `DFSCoerce`, `Coercer` заставляют машину-жертву сама аутентифицироваться на атакующего (учётка компьютера релеится так же хорошо, как пользовательская). Это делает атаку детерминированной, а не вероятностной — и усиливает аргумент «отключить протоколы полностью».

## Что стоит усилить в существующих разделах

### Раздел про хэши
- Указать режимы Hashcat: `-m 5500` (NetNTLMv1), `-m 5600` (NetNTLMv2).
- Ключевой факт: **NetNTLMv1 ломается за секунды** через rainbow tables (crack.sh) независимо от длины пароля. Поэтому политика должна не просто «сложные пароли 14+», а жёсткое отключение NTLMv1: GPO «Сетевая безопасность: уровень проверки подлинности LAN Manager» → «Отправлять только NTLMv2-ответы. Отказывать LM и NTLM».
- Добавить тренд 2024–2026: Microsoft официально депрекирует NTLM (в Windows 11 24H2 / Server 2025 ряд сценариев уже заблокирован) — стратегическая цель миграция на Kerberos, плюс аудит использования NTLM через Event ID `4776` / `4624` (имя пакета).

### Раздел SMB Signing
Уточнить актуальное: в Windows Server 2025 и Windows 11 24H2 подпись SMB включена **по умолчанию** (требование обязательное). Но подпись нужна именно на *цели* релея — поэтому проверять надо все legacy-серверы, а не только ставить политику.

### Раздел мониторинга — сейчас самый слабый
Event ID `4697`/`7045` — это общие события создания служб, они поймают уже постэксплуатацию, а не саму отравку. Я бы добавил:
- **Microsoft Defender for Identity** — имеет готовые алерты на LLMNR/NBT-NS/mDNS poisoning;
- **Канареечные имена**: зарегистрировать фейковые хосты (`file-srv`, `backup-share`, `wpad`) — легитимного ответа на их LLMNR-запрос быть не может, любой ответ = атакующий в сегменте. Это самый дешёвый и надёжный детект;
- Сетевые сенсоры (Zeek/Suricata): сигнатура на **несколько ответов на один LLMNR-запрос** (гонка ответов);
- Проверка вручную: Wireshark с фильтром `udp.port == 5355`, сделать заведомо ошибочный запрос и посмотреть, сколько хостов ответило (легитимно — ноль или один).

### Раздел проверки (добавить как новый шаг)
В заметке нет способа проверить, что политика применилась:

```powershell
Get-ItemProperty 'HKLM:\SOFTWARE\Policies\Microsoft\Windows NT\DNSClient'
# Ожидаем: EnableMulticast = 0
```

Плюс контрольный прогон Responder/Inveigh в режиме `--analyze` изнутри сети.
