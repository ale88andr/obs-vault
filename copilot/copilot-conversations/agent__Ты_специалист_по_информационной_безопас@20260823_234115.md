## Конкретные дополнения

### 1. Происхождение
Стоит добавить одну строку истории: концепция пришла из военной стратегии и формализована NSA в white paper «Defense in Depth» (2001). Это сразу задаёт контекст, откуда взялась луковичная модель.

### 2. Классическая модель уровней вокруг актива
Сейчас в заметке три *категории* контроля, но нет классической концентрической модели — данные в центре, вокруг них кольца защиты:

| Слой | Что защищает | Примеры мер |
| --- | --- | --- |
| Данные | Сами активы | Шифрование at rest/in transit, DLP, классификация, бэкапы |
| Приложения | ПО | Secure SDLC, WAF, валидация ввода, SAST/DAST |
| Хост | Конечные точки | EDR, харденинг, патч-менеджмент, контроль приложений |
| Внутренняя сеть | ЛВС | Микросегментация, NAC, внутренние IDS/IPS, VLAN |
| Периметр | Граница | Firewall, DMZ, почтовый шлюз, прокси, VPN |
| Физический | Железо | СКУД, видеонаблюдение, серверные с контролем доступа |
| Политики/люди | Всё сверху | Политики, обучение (security awareness), процедуры |

Важное уточнение к тексту заметки: физическая/техническая/административная — это **категории контрмер**, которые применяются **на каждом** из слоёв выше. Это две разные таксономии, и сейчас они стоят рядом без пояснения.

### 3. Типы контрмер (ключевой блок)
На каждом слое нужны меры разных типов (терминология NIST SP 800-53):

- **Превентивные** — предотвратить атаку (firewall, MFA, EPP)
- **Детективные** — обнаружить факт атаки (SIEM, EDR-алерты, honeypots)
- **Корректирующие** — купировать и восстановиться (изоляция хоста, restore из бэкапов, IR-план)
- **Сдерживающие** — снизить вероятность попытки (предупреждения, видимость камер)
- **Компенсирующие** — замена недоступного контроля эквивалентом

Смысл DiD именно здесь: если превентивный слой пробит, детективный должен сработать; если не сработал — корректирующий ограничивает ущерб. Сейчас заметка об этом молчит.

### 4. Принципы проектирования
- **Нет единой точки отказа** — отказ любого одного контроля не должен компрометировать актив
- **Разнообразие средств** (vendor diversity) — один 0-day или ошибка конфигурации одного вендора не должен отключать несколько колец сразу
- **Соразмерность** — стоимость слоя обоснована ценностью актива (risk-based, а не «всё сразу»)
- **Assume breach** — проектировать исходя из того, что периметр уже пробит; приоритет смещается с предотвращения на обнаружение и локализацию

### 5. Сквозной пример
Один живой пример «атака через все слои» сделает заметку в разы полезнее, чем список аббревиатур. Например, фишинг с вложением: почтовый шлюз с песочницей → не сработало → EDR детективает запуск → карантин хоста → сегментация не дала добраться до файлового ресурса → SOC получает алерт → учётки пользователя с минимальными привилегиями ограничили ущерб → восстановление из бэкапа не потребовалось.

### 6. Связи с современными концепциями
- **[[Zero Trust]]** (NIST SP 800-207) — логичное развитие DiD: «never trust, always verify» вместо доверия внутри периметра. Обязательный линк, учитывая заметку про защиту периметра
- **MITRE ATT&CK** — инструмент проверки покрытия слоёв: какие техники цепочки атаки закрывает ваш стек
- **CIS Controls / NIST CSF** — готовые фреймворки для реализации DiD на практике

### 7. Ограничения и критика
Честный раздел «когда DiD не работает» отличает заметку практиков от пересказа вики:
- Сложность и стоимость эксплуатации, alert fatigue в SOC
- Ложное чувство защищённости: «накупили всего» ≠ защищены, без тестирования (BAS/pentest) покрытие не подтверждено
- Инсайдер проходит сквозь большинство слоёв легитимным доступом — против него работают least privilege и мониторинг, а не новые стены
- Слои могут конфликтовать между собой (например, TLS-инспекция vs приватность/производительность)
