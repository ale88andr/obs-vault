**ai**: # Разбор принципа «простыми словами»

Сразу оговорюсь: этот принцип — сжатая формулировка раздела 4 вашей заметки [[Windows Access Tokens]] («Проверка прав доступа»), но чтобы он «щёлкнул», его надо развернуть в картинку. Давайте по шагам.

## 1. Две сущности, которые нужно различать

Вся модель держится на паре понятий, и если их путать, дальше ничего не сходится.

- **Субъект** — тот, кто *действует*. Это процесс или поток. У него нет «личности» сам по себе, но у него есть **маркер доступа** (Access Token) — «паспорт», выданный при входе в систему (раздел 2 вашей заметки: `lsass.exe` создаёт токен при аутентификации).
- **Объект** — то, на что *действуют*: файл, папка, ключ реестра, принтер, именованный канал, служба. У каждого объекта есть **дескриптор безопасности** (Security Descriptor), а внутри него — **DACL**.

То есть формула звучит так: **паспорт процесса** сравнивается со **списком гостей на двери объекта**.

## 2. Что физически в «паспорте»

Из раздела 3 вашей заметки токен содержит:

- SID пользователя (например, `S-1-5-21-...-1001`);
- список SID групп, в которых он состоит (`Бухгалтерия`, `Пользователи домена`, `Все`);
- привилегии (`SeDebugPrivilege` и т. п.);
- Logon ID и Default DACL.

Для проверки доступа важны первые два пункта: **SID пользователя + SID групп**. Привилегии — это отдельная история, о ней ниже.

## 3. Что физически «на двери»

DACL (Discretionary Access Control List) — упорядоченный список записей **ACE** (Access Control Entry). Каждая запись выглядит примерно так:

| Тип | Кому (SID) | Какие права |
| --- | --- | --- |
| Allow | `S-1-5-21-...-1001` (Алексей) | Full Control |
| Allow | `Бухгалтерия` | Read, Write |
| Deny | `Стажёры` | Write |
| Allow | `Все` (Everyone) | Read |

Каждая ACE — это «разрешить/запретить **кому-то** **что-то**».

## 4. Сама проверка: пошагово

Допустим, пользователь Алексей открывает `C:\Reports\Q3.xlsx` на запись. Происходит вот что:

1. **Запрос.** Процесс (скажем, Excel) просит у ядра: «открой файл с правом `FILE_WRITE_DATA`».
2. **Взять паспорт.** Система берёт токен процесса. Если поток работает под имперсонацией — берётся **impersonation token** этого потока, а не primary token процесса (раздел 5 вашей заметки).
3. **Взять список гостей.** Читается дескриптор безопасности файла и из него — DACL.
4. **Сопоставление.** Система идёт по ACE сверху вниз и ищет первую, где SID из токена совпадает с SID в ACE, а запрашиваемое право покрывается правами в ACE.
5. **Решение.** Нашлась `Allow` с нужным правом → доступ дан. Нашлась `Deny` → отказ. Не нашлось ничего → отказ.

Ключевая деталь, которую новички обычно упускают: **сравнивается не «кто ты», а «есть ли у тебя подходящий SID»**. Алексею не нужно быть лично указанным в файле — достаточно, что он входит в группу `Бухгалтерия`, у которой есть `Allow Write`. Членство в группе «разворачивается» из токена в момент проверки; системе не нужно никуда ходить в Active Directory.

## 5. Три правила, без которых механизм не понять

### 5.1. Deny сильнее Allow, и порядок важен

ACE применяются **по порядку, первое совпадение решает всё**. Канонический порядок, который выставляет Windows:

1. явные `Deny`;
2. явные `Allow`;
3. унаследованные `Deny`;
4. унаследованные `Allow`.

Поэтому если у `Стажёры` стоит `Deny Write`, а у `Бухгалтерия` — `Allow Write`, и Алексей состоит в обеих группах, **победит запрет**: `Deny`-запись стоит выше и срабатывает первой. Это и есть причина старого правила «не назначай права группам, не давай deny — используй allow».

### 5.2. Нет совпадения — значит нет доступа (implicit deny)

DACL — это список **разрешений**, а не «всё разрешено, кроме перечисленного». Если в DACL есть записи, но ни одна не подходит под твой SID — доступ закрыт. Молчание в DACL = отказ.

### 5.3. Пустой DACL ≠ отсутствующий DACL

Тонкий, но важный момент:

- **DACL отсутствует (`NULL`)** — объект доступен **всем** (проверка не выполняется вообще). Так бывает у объектов, созданных без дескриптора безопасности.
- **DACL есть, но без ACE** — объект недоступен **никому** (кроме владельца, который всегда может переписать DACL).

Разница между «нет списка» и «пустой список» здесь противоположна интуиции — запомните её отдельно.

## 6. Откуда берётся DACL у нового файла

Здесь всплывает `Default DACL` из токена (раздел 3). Когда процесс создаёт новый файл и явно не задаёт дескриптор, Windows копирует **Default DACL из токена создателя** в DACL нового объекта (плюс добавляет владельца и права из родительской папки при наследовании). Поэтому папка, созданная под `SYSTEM`, и папка, созданная обычным пользователем, получают разные DACL «по наследству от паспорта».

## 7. Что сравнивается технически — не «право», а маска

Запрос содержит **маску доступа** (access mask) — битовый набор вроде `READ | WRITE | DELETE`. Проверка успешна, только если ACE покрывает **все** запрошенные биты. Отсюда типичная ситуация: у тебя есть `Read`, ты просишь `Read + Write` — отказ, потому что одного бита не хватает. Не «частично пустят», а именно отказ на весь запрос.

## 8. Где этот принцип не работает (важные оговорки)

DACL — не единственный фильтр, и это стоит держать в голове, чтобы не удивляться:

- **Привилегии обходят DACL.** `SeBackupPrivilege` и `SeRestorePrivilege` позволяют читать/писать в обход проверки DACL — именно так работает резервное копирование и, кстати, многие атаки. Здесь в игру вступает вторая часть токена.
- **Mandatory Integrity Control (UAC/IL).** Параллельно проверяется уровень целостности: процессу с `Medium` не дадут писать в объект с `High`, даже если DACL разрешает. Это не DACL-проверка, а отдельный слой.
- **SACL** — это не про доступ, а про **аудит** (кто и когда пытался). Не путайте с DACL.

## 9. Короткая mental model на память

```
Процесс/поток  --(токен: SID юзера + SID групп)-->  [ проверка ]
Объект         --(дескриптор: DACL из ACE)------>  [ проверка ]
                                                        |
                              первая подходящая ACE: Allow → пустить
                                                     Deny  → отказ
                                                     ничего → отказ
```

**Одной фразой:** токен отвечает на вопрос «кем я являюсь и в каких группах состою», DACL — на вопрос «кому что разрешено с этим объектом делать», а решение принимается построчным сравнением этих двух списков, где первое совпадение и есть приговор.

Именно поэтому в заметке сказано, что на этом держится **весь** дискреционный доступ: любой `OpenProcess`, `CreateFile`, `RegOpenKey`, обращение к службе или принтеру проходит через одну и ту же процедуру — `SeAccessCheck` в ядре. Разница только в том, чей токен берётся (primary или impersonation) и какой дескриптор подставляется.
