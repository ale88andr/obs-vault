## 0. Зачем серверу брандмауэр

Любой сервер, подключённый к сети, постоянно сканируется. Каждый открытый порт — это потенциальная точка входа. Брандмауэр нужен, чтобы **явно разрешить только необходимое** и закрыть всё остальное. Главный принцип: _если порт не нужен снаружи — он должен быть закрыт_.

## 1. Что такое брандмауэр и что такое порты

- Брандмауэр фильтрует сетевой трафик по правилам: **источник, назначение, порт, протокол**.
- **Порт** — числовой идентификатор сервиса на хосте. Типовые:
    - **22/tcp** — SSH (удалённое управление);
    - **80/tcp** — HTTP;
    - **443/tcp** — HTTPS;
    - **3306/tcp** — MySQL/MariaDB (наружу обычно не нужен).
- UFW — не отдельный «движок», а **удобная надстройка над iptables/nftables**. Правила хранятся в `/etc/ufw/`, применяются через systemd.

## 2. Установка и проверка UFW

В Ubuntu UFW обычно уже установлен, но **выключен**.

```
sudo apt update
sudo apt install ufw

sudo ufw version
sudo ufw status verbose      # Status: inactive — значит, ещё не включён
```

`status verbose` показывает состояние, политики по умолчанию и уровень логирования.

## 3. Правила по умолчанию

Базовая модель — «запрещаем входящее, разрешаем исходящее»:

```
sudo ufw default deny incoming
sudo ufw default allow outgoing
```

- **incoming** — соединения, инициированные снаружи к серверу;
- **outgoing** — соединения, инициированные сервером (обновления, DNS, API);
- **routed** — транзитный трафик (актуально для шлюзов/VPN).

Политика `deny incoming` означает: всё, что не разрешено явно, будет заблокировано. Это и есть основной принцип безопасности.

## 4. Разрешаем SSH до включения

**Самый важный шаг.** Если включить UFW без правила для SSH, вы потеряете доступ к удалённому серверу.

```
sudo ufw allow OpenSSH          # профиль приложения
# или явно:
sudo ufw allow 22/tcp
```

Если SSH работает на нестандартном порту — разрешать нужно именно его:

```
grep -i '^Port' /etc/ssh/sshd_config
sudo ufw allow 2222/tcp
```

Проверить, что слушает сервер: `ss -tlnp`.

## 5. Включаем UFW (7:24)

```
sudo ufw enable
```

Команда предупредит, что включение может разорвать текущее SSH-соединение (продолжаем только если правило для SSH уже добавлено).

```
sudo ufw status verbose
```

Правила сохраняются между перезагрузками: служба `ufw` включена в автозапуск.

## 6. Разрешаем HTTP и HTTPS (8:27)

```
sudo ufw allow 80/tcp
sudo ufw allow 443/tcp

# либо через профили приложений:
sudo ufw app list
sudo ufw allow 'Nginx Full'     # 80 + 443
sudo ufw allow 'Apache Full'
```

Профили удобнее: они сразу открывают нужные порты и не требуют помнить номера. `ufw app info 'Nginx Full'` покажет, что входит в профиль.

## 7. Блокируем порты (9:53)

```
sudo ufw deny 3306/tcp
```

- **deny** — молча отбрасывает пакеты (клиент видит таймаут);
- **reject** — отвечает отказом (клиент сразу получает ошибку).

MySQL наружу обычно не публикуют: база должна быть доступна только приложению на том же хосте или в приватной сети.

## 8. Доступ с конкретных IP (11:05)

Ограничение по источнику — базовый способ сузить поверхность атаки:

```
# только этот IP может подключаться к SSH
sudo ufw allow from 203.0.113.10 to any port 22 proto tcp

# целая подсеть
sudo ufw allow from 192.168.1.0/24 to any port 3306 proto tcp

# только на конкретный интерфейс
sudo ufw allow in on eth0 to any port 80
```

Типовые сценарии: админский доступ только из офиса/VPN, база — только из подсети приложений.

## 9. Просмотр, управление и удаление правил (12:22)

```
sudo ufw status numbered        # правила с номерами
sudo ufw delete 3               # удалить правило по номеру
sudo ufw delete allow 80/tcp    # удалить по описанию
sudo ufw insert 1 allow from 203.0.113.10 to any port 22
sudo ufw show added             # все добавленные правила
```

Порядок важен: UFW применяет правила сверху вниз, поэтому `insert` позволяет поставить правило выше остальных. После изменений полезно снова смотреть `status numbered`.

## 10. Логирование (13:30)

```
sudo ufw logging low       # off | low | medium | high | full
```

Куда пишутся события:

- `/var/log/ufw.log`;
- дублирование в `/var/log/syslog` и `journalctl -k`.

Что видно в логах: заблокированные пакеты — источник, назначение, порт, протокол, действие (`UFW BLOCK`). Это основной инструмент диагностики: «почему меня не пускает» и «кто стучится».

```
sudo tail -f /var/log/ufw.log
sudo grep 'UFW BLOCK' /var/log/ufw.log | tail
```

## 11. Отключение и сброс (15:07)

```
sudo ufw disable     # выключить, правила сохраняются
sudo ufw reset       # удалить ВСЕ правила и отключить UFW
sudo ufw reload      # перечитать конфигурацию без выключения
```

`reset` — опасная команда: она стирает конфигурацию. Перед сбросом сохраните текущие правила (`ufw status numbered`), а на удалённом сервере держите открытой консоль провайдера.

## 12. Практика: защищаем веб-сервер (16:23)

Итоговая конфигурация для типичного Ubuntu-сервера с сайтом:

```
sudo ufw default deny incoming
sudo ufw default allow outgoing

sudo ufw allow OpenSSH              # или только с админского IP
sudo ufw allow 'Nginx Full'         # 80 + 443

sudo ufw deny 3306/tcp              # база не наружу
sudo ufw logging low
sudo ufw enable

sudo ufw status verbose
ss -tlnp                            # что реально слушает
```

Проверка: сайт открывается по HTTP/HTTPS, SSH работает, MySQL снаружи недоступен, в `ufw.log` видны блокировки сканеров.

Полезное дополнение — ограничение частоты подключений (защита от перебора):

```
sudo ufw limit ssh
```

## 13. Итог и что дальше (18:30)

- UFW = простой интерфейс к iptables/nftables; основная модель — **deny incoming, allow outgoing**.
- Порядок действий: установить → задать политики → **разрешить SSH** → включить → открыть нужные сервисы → закрыть лишнее → включить логирование.
- Главный риск — **заблокировать себя по SSH**: всегда проверяйте правило для 22 (или вашего порта) до `ufw enable`.
- Дальше: профили приложений, ограничение по IP, `ufw limit`, централизованный сбор логов, а на шлюзах — политики `routed`.

## Шпаргалка команд

|Задача|Команда|
|---|---|
|Версия/статус|`sudo ufw version` · `sudo ufw status verbose`|
|Политики|`sudo ufw default deny incoming` · `sudo ufw default allow outgoing`|
|SSH|`sudo ufw allow OpenSSH` / `sudo ufw allow 22/tcp`|
|Веб|`sudo ufw allow 80/tcp` · `sudo ufw allow 443/tcp` · `sudo ufw allow 'Nginx Full'`|
|Заблокировать|`sudo ufw deny 3306/tcp`|
|Только с IP|`sudo ufw allow from 203.0.113.10 to any port 22 proto tcp`|
|Список/удаление|`sudo ufw status numbered` · `sudo ufw delete N`|
|Логи|`sudo ufw logging low` · `tail -f /var/log/ufw.log`|
|Вкл/выкл/сброс|`sudo ufw enable` · `disable` · `reset` · `reload`|
|Антибрутфорс|`sudo ufw limit ssh`|

**Важно помнить:** UFW фильтрует трафик на уровне хоста, но **не заменяет** настройку самих сервисов (SSH-ключи, пароли БД, обновления) и **не защищает** от ошибок в приложениях. И отдельный нюанс: контейнеры Docker публикуют порты в обход UFW — если используете Docker, правила нужно проверять отдельно.

**Главная мысль:** безопасность сервера начинается с простого действия — закрыть всё, что не нужно, и открыть только то, что действительно должно быть доступно снаружи.
