# Как защитить Linux — конспект

---

## Главная мысль

- Защититься на 100% нельзя: завтра найдут уязвимость в софте, которым ты пользуешься, и узнаешь ты о ней не первым.
- Поэтому шаги двух видов:
  1. **Закрыть очевидные дыры** — чтобы бот прошёл мимо и пошёл к другому хосту.
  2. **Научиться видеть** — чтобы заметить, если кто-то всё-таки вошёл, понять как и забрать доступы.
- Защищаемся не от «хакеров в масках», а от **автоматики**, которая проверяет три вещи:
  - есть ли программа с известной уязвимостью;
  - можно ли войти с простым паролем;
  - торчит ли наружу база или Redis без пароля.
- Если сработало хотя бы одно — ставят то, что приносит деньги: **майнер** (чаще всего), **рассылку спама**, **ботнет для DDoS**.

## Насколько быстро начинают атаковать

- Эксперимент Sophos (2019): 10 серверов-приманок (**ханипоты**) в облаках по миру.
- Первую приманку в Сан-Паулу начали атаковать **через 52 секунды** после запуска.
- В среднем — **750 попыток входа в час** (~10+ в минуту, круглосуточно).
- Боты перебирают адреса подряд, находят открытые порты, пробуют стандартные пары логинов/паролей (`root`, `admin`, `test`, `oracle` и т. п.).
- Твой «маленький ненужный сервер» никому не нужен — но боты стучатся во всё подряд.

## 10 шагов

| # | Шаг | Что закрывает |
| --- | --- | --- |
| 1 | Логи: смотреть, что происходит | видимость (основа всего) |
| 2 | Автоматические обновления безопасности | известные уязвимости |
| 3 | Не работать под root, раздать sudo по минимуму | пароли/права |
| 4 | SSH только по ключам, без root, список пользователей | подбор пароля |
| 5 | Проверить, что слушает: `ss -t`, локальные адреса | база/Redis наружу |
| 6 | Firewall (UFW + Security Groups) | лишние порты |
| 7 | fail2ban | перебор паролей снаружи |
| 8 | Права на файлы, пароли в истории команд | пароли на самом сервере |
| 9 | Логи уезжают с сервера (Loki + Grafana) | заметание следов |
| 10 | Метрики и алерты + план разбора инцидента | обнаружение |

Порядок в ролике немного другой (видимость → закрытие → снова видимость):
**1** логи → **2** обновления → **3** пользователи/sudo → **4** SSH → **5** что слушает → **6** firewall → **7** fail2ban → **8** файлы и пароли → **9** централизованные логи → **10** метрики/алерты.

## Шаг 1. Сначала — видимость (логи)

Первый шаг ничего не закрывает. Прежде чем защищать, надо научиться видеть, что с сервером происходит, иначе защита строится наугад.

- Главный источник в современном Linux — журнал **systemd**:
  - `journalctl -u ssh` — всё, что писал SSH-сервер;
  - в Debian/Ubuntu сервис называется `ssh`, в CentOS и родственных — `sshd`.
- **Ловушка дистрибутивов:** во многих инструкциях советуют `/var/log/auth.log`.
  - В Ubuntu файл есть.
  - В Debian по умолчанию нет, потому что не ставится `rsyslog`, который его пишет — всё только в журнале systemd.
  - Команды `last` и `lastb` (старый способ смотреть историю входов) в Debian 13 перестали работать: старый формат файлов не переживёт 2038 год.
  - Вывод: привыкай к `journalctl`, он есть везде.

### Три типа строк, которые надо узнавать сразу

| Строка | Значение | Реакция |
| --- | --- | --- |
| `Failed password` | кто-то ввёл неправильный пароль | фон, боты |
| `Invalid user` | вход под пользователем, которого на сервере нет | фон, боты |
| `Accepted ...` | **успешный вход** | каждая строка должна быть понятна |

Правило: если строка `Accepted` тебя удивила — это не повод удивляться дальше, а повод разбираться (кто, откуда, почему именно в это время).

Настораживает:
- вход в необычное время;
- вход с незнакомого адреса;
- новый пользователь, которого ты не создавал;
- `sudo` от того, кому он не положен (каждый вызов sudo пишется в журнал).

### Команды «под рукой»

```bash
journalctl -u ssh --since "1 day ago" | grep -i accepted   # успешные входы за сутки
journalctl -u ssh -f                                      # live-режим, как tail -f
journalctl -u sudo                                        # кто, что и откуда запускал
w                                                         # кто сидит на сервере прямо сейчас
```

### Время должно быть синхронизировано

Если часы на двух серверах расходятся даже на 5 минут, не поймёшь, что случилось сначала, а что потом — получится расследование, где следствие наступило раньше причины.

```bash
timedatectl    # показывает, синхронизированы ли часы (обычно NTP уже включён)
```

### Две обязательные проверки журнала

1. **Переживает ли журнал перезагрузку.** `journalctl --list-boots` — если в списке только текущая загрузка, журнал живёт в памяти (`/run/log/journal`) и после ребута пропадает. Лечится постоянным хранилищем: создать `/var/log/journal` и применить конфиг journald (`Storage=persistent` в `/etc/systemd/journald.conf` + `systemd-tmpfiles --create --prefix /var/log/journal`).
2. **Не съедят ли логи весь диск.** `journalctl --disk-usage` показывает объём, лимит задаётся в `/etc/systemd/journald.conf`. Сервер, который упал, потому что слишком подробно логировал, — плохой сценарий.

> Каждый следующий шаг проверяется по этим же логам.

## Шаг 2. Известные уязвимости → автообновления

- Массовые взлома идут **не** через хитрую zeroday-уязвимость, а через давно известные дыры: исправление вышло, но его не поставили. Бот проверяет версию и запускает готовый **эксплойт**.
- Дыры находят даже в проверенных программах. Пример: летом 2024 Qualys нашла в **OpenSSH** уязвимость **regreSSHion** (CVE-2024-6387).
  - Позволяла выполнить код с правами root без пароля и без ключа.
  - Уязвимы версии **8.5–9.7**.
  - Больше **14 млн** потенциально уязвимых серверов с доступом из интернета.
  - Исправление вышло сразу — вопрос только в том, кто его поставит.
- Вывод: обновления безопасности должны ставиться **сами**.

```bash
sudo apt install unattended-upgrades
sudo dpkg-reconfigure -plow unattended-upgrades   # включить
```

- `unattended-upgrades` регулярно проверяет репозиторий безопасности и ставит обновления сам.
- Разница дистрибутивов: в **Ubuntu Server** установлен и включён из коробки, в **минимальной установке Debian** его нет.
- Логи обновлений: `/var/log/unattended-upgrades/` — первое, куда смотреть, если «что-то перестало работать».

### Чего он не делает — не перезагружает сервер

- Обновление ядра или системной библиотеки установлено, но работает старая версия, пока не перезапустить сервис или сервер.
- **Формально дыра закрыта, фактически — нет.**
- В Ubuntu о необходимости ребута говорит файл `/var/run/reboot-required`, а `needrestart` покажет, каким сервисам нужен перезапуск.
- Автоперезагрузку можно включить, но сначала подумай, что упадёт, если сервер перезагрузится в момент обновления.

## Шаг 3. Пользователи и sudo

Под root напрямую никто не работает: создаётся обычный пользователь и получает `sudo`.

**Зачем, если root и так доступен через sudo?** Затем, что у каждого действия появляется **автор**: каждый вызов sudo пишется в журнал — кто, когда, какую команду выполнил. Иначе в логе будет «root сделал то-то», что ничем не помогает.

Пример строки журнала: `deploy` из директории X от имени root перезапустил nginx.

```bash
journalctl -u sudo
sudo -l          # что разрешено конкретному пользователю
```

Правила:
- Не раздавать `sudo` без пароля на всё подряд. Запись «все команды, без пароля» — это тот же root, только с лишним шагом.
- Нужно человеку перезапускать один сервис — пусть имеет право только на этот сервис (правило в `sudoers` с ограничением по команде).
- **Удалять ненужных пользователей:** уволившийся сотрудник, подрядчик, закончивший работу, временный тест. Каждый такой пользователь — ещё один способ войти, про который можно забыть.

## Шаг 4. SSH: только ключи

Все попытки подобрать пароль работают только пока вход по паролю разрешён.

Три параметра в `sshd_config`:
- `PasswordAuthentication no` — только ключи;
- `PermitRootLogin no` — root по SSH не заходит никогда;
- `AllowUsers ...` — список тех, кому вообще можно входить по SSH.

### Порядок действий (важно!)

```bash
# 1. на своём компьютере
ssh-keygen -t ed25519
# 2. положить ключ на сервер
ssh-copy-id user@server
# 3. проверить, что вход по ключу работает
ssh user@server
# 4. только теперь выключать пароль
```

Иначе есть риск закрыть вход самому себе — сервер будет идеально защищён от всех, включая владельца.

### Нюанс: побеждает первое значение, а не последнее

- Дописал `PasswordAuthentication no` в конец `sshd_config`, перезапустил — а вход по паролю всё ещё работает.
- Причина: в начале `sshd_config` есть `Include /etc/ssh/sshd_config.d/*.conf`. В облачных образах Ubuntu там часто лежит файл от **Cloud-Init** с `PasswordAuthentication yes`. Он прочитан раньше — и побеждает. Строка в конце файла просто игнорируется.
- Правильно: класть свои настройки в отдельный файл в той же директории с именем, которое идёт **раньше по алфавиту**, например `01_hardening.conf`.

### Проверять не файл, а итог

```bash
sshd -t     # синтаксис конфига
sshd -T     # настройки, с которыми сервер РЕАЛЬНО работает (не то, что написано, а то, что применено)
```

Два правила, чтобы не отрезать себе доступ:
- перед перезапуском проверять `sshd -t`/`sshd -T`;
- **не закрывать текущую сессию, пока не зашёл в новую**.

### Про смену порта

Смена 22-го порта на другой — **не защита**. Это лишь уменьшение шума в логах (часть ботов стучится только в 22). Тот, кто ищет именно твой сервер, найдёт другой порт.

## Шаг 5. Что вообще слушает сервер

Третий путь бота — база или Redis, торчащие наружу без пароля. И начинается это не с firewall, а с вопроса: **что слушает наш сервер?**

```bash
ss -t          # все открытые порты + адреса + программы
ss -tlnp       # то же с процессами
```

Смотреть на адрес:
- `127.0.0.1` — порт доступен только с самого сервера;
- `0.0.0.0` — открыт на всех интерфейсах, в том числе наружу в интернет.

Частый случай: база/Redis поставили для приложения на этом же сервере, а слушают они весь интернет — «очень щедро». А если ещё и без пароля, бот найдёт их быстрее, чем ты.

Сначала правим конфиг программы (слушать `127.0.0.1`, если снаружи не нужно), потом — firewall.

## Шаг 6. Firewall

Принцип: **всё входящее запрещено, кроме того, что явно разрешено.**

```bash
sudo ufw default deny incoming
sudo ufw default allow outgoing
sudo ufw allow ssh          # СНАЧАЛА разрешить SSH
sudo ufw allow 80,443/tcp
sudo ufw enable             # и только потом включать
sudo ufw status verbose
```

Порядок критичен: включишь firewall раньше, чем разрешил SSH — отрежешь доступ себе, и чинить придётся через консоль облачного провайдера.

### Облачный firewall

- У провайдера обычно есть свой firewall — **Security Groups** (группы безопасности).
- Он срабатывает **до** того, как трафик дошёл до сервера, поэтому лишнее закрывать и там.
- Плюс: если кто-то на сервере случайно выключит UFW, внешний firewall останется.

### Ловушка Docker

- Всё закрыто в UFW, запускаем контейнер с опубликованным портом — и порт **доступен из интернета**.
- Docker пишет свои правила так, что трафик к контейнерам идёт **в обход UFW**. UFW честно показывает, что всё закрыто, но это не так.
- Два решения:
  1. публиковать порт только на `127.0.0.1` (`-p 127.0.0.1:8080:80`), если наружу его отдаёт Nginx;
  2. писать ограничения в набор правил **DOCKER-USER**, который Docker оставляет специально для этого.

## Шаг 7. fail2ban

Firewall решает, кого пускать вообще. А что с теми, кто долбится на открытый порт и подбирает пароль?

- `fail2ban` работает **на логах из шага 1**: читает журнал, считает неудачные попытки с каждого адреса и временно банит адрес в firewall.
- Дефолт: 5 неудач за 10 минут → бан на 10 минут.

```bash
sudo apt install fail2ban
sudo fail2ban-client status sshd
sudo fail2ban-client set sshd unbanip 1.2.3.4
```

- Полезная настройка **`ignoreip`** — адреса, которые не банятся никогда (офис, VPN). Иначе однажды пять раз ошибёшься паролем и забанишь сам себя.
- Если вход по паролю уже выключен, fail2ban в основном убирает шум из логов и лишнюю нагрузку.
- А вот для сервисов, где пароль остаётся (почта, веб-панели), он реально помогает — есть готовые правила для многих программ.

## Шаг 8. Пароли и ключи на самом сервере

Здесь речь о паролях, которые не нужно подбирать, — они уже лежат на сервере.

### Права на файлы

- Приватные ключи и файлы с паролями (`.env`) должны быть доступны только владельцу: **`600` вместо `644`**.
- С `644` файл читает любой пользователь на сервере — даже тестовый.

```bash
ls -l ~/.ssh/ .env
chmod 600 .env id_ed25519
```

### История команд

- История лежит в `~/.bash_history`.
- Набрал пароль прямо в команде — он остался там открытым текстом (`Ctrl+R` потом его найдёт, и не только ты).
- Пока команда работает, её аргументы видит **любой** пользователь сервера через `ps`.
- Поэтому пароли не передают в аргументах, а кладут в файл с правами `600` или в переменную окружения (или в менеджер секретов).
- Если очень надо выполнить команду, не оставив её в истории — начать строку с **пробела** (в Debian/Ubuntu bash по умолчанию такие команды не запоминает). Один пробел — и у bash «провал в памяти».

## Шаг 9. Логи должны уезжать с сервера

Логи лежат на том же сервере, который мы защищаем. Если кто-то получил root, одно из первых действий — **почистить логи**.

- Заметание следов настолько стандартный приём, что в **MITRE ATT&CK** очистка системных логов Linux — отдельный пункт (T1070.002).
- Отсюда шаг: логи должны уезжать с сервера сразу, как записаны. То, что уже лежит на другой машине, с этого сервера не удалить.
- Второй аргумент — практический: пока сервер один, можно зайти и погрепать. Когда их 10 — ходить по каждому никто не будет (точнее, будет один раз, а потом поставит Loki).

### Стек Loki + Grafana

- **Loki** (от создателей Grafana) — один из самых популярных вариантов.
- Устройство: на каждом сервере **агент** читает журнал и нужные файлы логов и отправляет в **Loki**; Loki хранит; смотрят и ищут — в **Grafana**.
- Агент сейчас называется **Grafana Alloy**. Если в старых инструкциях видишь **Promtail** — это предшественник, с 2 марта 2026 он больше не поддерживается.

### Loki vs ELK (Elasticsearch + Logstash + Kibana)

- ELK индексирует **весь текст** каждой строки → много памяти и диска.
- Loki индексирует **только метки** (с какого сервера строка и от какого сервиса), а по тексту ищет перебором внутри выбранных меток.
- Поэтому Loki заметно дешевле и проще даже на небольшом проекте.

### Практические вопросы

- **Что отправлять?** Всё: весь системный журнал, логи веб-сервера, логи приложения. Во время расследования заранее не знаешь, какая строка понадобится — обычно это та, которую ты решил не отправлять.
- **Сколько хранить?** С запасом. Взлом замечают не в тот же день, а через неделю/месяц/несколько месяцев. Если логи живут 3 дня, к моменту подозрения вход взломщика уже исчез — логи есть, а ответа в них нет. Старые логи Loki умеет складывать в дешёвые объектные хранилища вроде S3.
- **Права доступа:** агент на сервере должен уметь **только отправлять** логи, ни в коем случае не удалять. Хранилище логов не должно открываться теми же ключами, что и сам сервер — иначе злоумышленник, получивший сервер, дотянется и до логов, и смысл шага пропадёт. Логи, которые можно удалить с того же сервера, — это просто ещё одна директория на том же сервере.

## Шаг 10. Метрики и алерты: кто-то должен посмотреть в логи

Логи отвечают на вопрос «что произошло». Но искать в них начинают, когда **уже знают**, что что-то случилось. Кто тебе об этом скажет? Никто, если не настроить.

### Метрики

- Собирает **Prometheus**, на каждом сервере — **Node Exporter** (CPU, память, диск, сеть).

Метрики, которые выдают взлом:
- **CPU на 100%**, когда на сайте нет посетителей → майнер;
- **резкий рост исходящего трафика** → спам или участие в DDoS;
- **диск, который вдруг начал быстро заполняться**.

Главное: на каждую метрику ставят **алерт** — правило, которое само поднимает тревогу. Пример для CPU в Prometheus: взять время простоя процессора, посчитать из него загрузку и задать условие «больше 90% дольше 15 минут → алерт».

### Алерты на логи

Loki умеет выполнять запросы по расписанию и тоже поднимать тревогу. Три базовых алерта, которые стоит завести на любом сервере:
1. успешный вход по SSH;
2. создание нового пользователя;
3. логи сервера вообще перестали приходить.

Дальше всё уходит в **Alertmanager**, а он отправляет сообщение туда, где его увидишь ты или команда: корпоративный мессенджер, обычный мессенджер, почта. Главное — чтобы это было место, которое **часто проверяют**.

## Разбор инцидента: алерт сработал, что дальше

Сценарий: логи уже уезжают в Loki, из алертов настроен только один — на процессор. Глубокая ночь, CPU 100% уже 20 минут, трафика при этом нет.

### Правило №1: ничего не перезагружать и ничего не удалять

Очень хочется вырубить процесс и пойти спать. Но вместе с процессом пропадут следы: откуда он запущен, от чьего имени, как попал на сервер.

### Порядок разбора

1. **Что за процесс?** `top` — какие процессы грузят CPU и от какого пользователя запущены (`ps aux --sort=-%cpu`).
2. **Как этот пользователь попал на сервер?** Идём в логи и ищем всё по этому пользователю.
3. **Восстановить хронологию:** вход → скачивание файла → запуск.
4. **Проверить две вещи, которые взломщики делают, чтобы вернуться:**
   - задачу в **crontab**, которая перезапустит майнер;
   - свой ключ в **`authorized_keys`** (файлы у всех пользователей).
   То есть он не просто зашёл, а позаботился, чтобы зайти снова.

В примере из ролика картина такая: за сутки — сотни неудачных попыток подобрать пароль к **тестовому** пользователю, потом строка `Accepted password`. Пароль был простой, вход по паролю так и не выключили, fail2ban не стоял.

### Какие алерты поймали бы это раньше

- Алерт на **успешный вход** сработал бы в момент первого входа — задолго до 100% CPU.
- Ещё раньше — алерт на **рост числа `Failed password` для существующего пользователя**: `Invalid user` — это шум (боты перебирают несуществующие имена), а сотни `Failed password` для реального пользователя — это **прицельный подбор**, кто-то знает, что такой пользователь существует.

### Сервер после взлома не «чинят»

- Можно удалить майнер, crontab и ключ — и сервер вроде бы «чистый». **Нет.**
- Не знаешь наверняка, что ещё успели оставить. Сервер считается **полностью скомпрометированным**.
- Что делать:
  1. **отключить от сети** (в облаке — группой безопасности, запретив весь трафик, кроме своего; сам сервер при этом продолжает работать);
  2. **сохранить то, что нужно для разбора** — перед пересборкой сделать снимок диска;
  3. **пересобрать с нуля**;
  4. **сменить все пароли, ключи и токены**, которые на нём лежали — все, даже те, про которые кажется, что их никто не видел;
  5. **закрыть ту дыру, которую показала хронология, на всех остальных серверах** (здесь — забытый пользователь и вход по паролю).

Сам факт взлома неприятен, но это нормально. Ненормально — **не знать**, что это произошло. Без логов и метрик на каждый вопрос ответ «не знаю, в чём проблема»; с ними есть хронология по минутам и спокойный разбор.

## Итоговый чеклист

- [ ] `journalctl` вместо `auth.log`; знаю, как выглядят `Failed password`, `Invalid user`, `Accepted`
- [ ] `timedatectl` — часы синхронизированы
- [ ] журнал переживает перезагрузку (`journalctl --list-boots` — больше одной загрузки)
- [ ] журнал ограничен по размеру (`journalctl --disk-usage` в норме)
- [ ] `unattended-upgrades` установлен и включён; проверил `/var/log/unattended-upgrades/`
- [ ] знаю про `/var/run/reboot-required` и `needrestart`
- [ ] работаю не под root, sudo выдан по минимуму, лишние пользователи удалены
- [ ] SSH: только ключи, `PermitRootLogin no`, `AllowUsers`
- [ ] настройки в `sshd_config.d/01_*.conf`, проверено через `sshd -T`
- [ ] `ss -t` — ничего лишнего на `0.0.0.0`; база/Redis на `127.0.0.1`
- [ ] UFW: deny incoming, разрешён SSH, включён **после** разрешения SSH
- [ ] Security Groups у провайдера закрыты
- [ ] Docker не обходит UFW (`127.0.0.1:port` или `DOCKER-USER`)
- [ ] fail2ban + `ignoreip`
- [ ] `600` на ключи и `.env`; паролей нет в истории и в аргументах команд
- [ ] логи уезжают в Loki, агент не может их удалять, ключи хранилища ≠ ключи сервера
- [ ] Prometheus + Node Exporter, алерты на CPU / исходящий трафик / диск
- [ ] алерты на успешный SSH-вход, нового пользователя, пропажу логов
- [ ] Alertmanager шлёт туда, где реально смотрят
- [ ] есть план на случай инцидента: не ребутать, снять snapshot, пересобрать, сменить всё

**Если делать только два шага из десяти** — пусть это будут **вход только по ключам** и **логи на другой машине**.
