# Часть I. База и термины

Цель курса — снять путаницу в криптографических терминах и показать, как криптография ломается **на практике**, а не в теории. Главный тезис: **алгоритмы почти никогда не ломают математически — ломают пароли, ключи, режимы, реализации и конфигурацию.**

## 1. Пять терминов, которые всегда путают

|Термин|Что это|Ключ|Обратимо|Защищает секрет|
|---|---|---|---|---|
|**Encoding**|Представление данных в другом формате (Base64, hex, URL-encode)|нет|да|**нет**|
|**Encryption**|Сокрытие содержимого|да|да (с ключом)|да|
|**Hashing**|Односторонний «отпечаток» фиксированной длины|нет|нет|нет|
|**MAC/HMAC**|Ключевой «отпечаток» для проверки целостности|да (секретный)|нет|нет, но ловит подмену|
|**Obfuscation**|Запутывание кода/строк|нет|условно|**нет**|

Практический вывод: `echo c2VjcmV0 | base64 -d` доказывает, что Base64 — не шифрование. А обфускация лишь повышает стоимость реверса.

# Часть II. Кодирование и обфускация

## 2. Encoding на практике

- **Base64:** 3 байта → 4 символа (алфавит A–Z, a–z, 0–9, `+`, `/`), выравнивание =. Увеличивает объём на ~33%.
- **Hex:** каждый байт → две hex-цифры. Удобно для дампов и сигнатур.
- **URL-encoding:** `%20`, `%2F` — для передачи в URL.
- **Кодировки текста:** UTF-8 (переменная длина), UTF-16 (Windows «wide»), ASCII, Windows-1251.

```
echo -n "secret" | base64            # c2VjcmV0
echo "c2VjcmV0" | base64 -d
echo -n "secret" | xxd               # hex-дамп
```

PowerShell:

```
[Convert]::ToBase64String([Text.Encoding]::UTF8.GetBytes("secret"))
[Text.Encoding]::UTF8.GetString([Convert]::FromBase64String("c2VjcmV0"))
```

**Зачем нужно:** передача бинарных данных в текстовых протоколах (JSON, JWT, MIME, PEM), совместимость, отладка. **Почему не защита:** декодируется кем угодно без ключа.

## 3. Обфускация на практике

Методы: конкатенация строк, коды символов (`[char]115+[char]101...`), многослойный Base64, «мусорные» переменные, динамическое выполнение (`Invoke-Expression`), упаковка/крипторы.

Смысл: затруднить чтение и обход сигнатур AV/EDR, но **не скрыть данные**. Любой деобфускатор, отладчик или простой скрипт восстановит исходник.

# Часть III. Симметричное шифрование

## 4. Что такое симметричное шифрование

Один ключ для шифрования и расшифрования. Быстрое, подходит для больших объёмов (файлы, диски, сетевой трафик). Примеры: **AES** (128/192/256 бит), **ChaCha20**, из старых — DES/3DES (устарели), RC4 (сломан).

Проблема: **распределение ключа**. Если ключ передать по открытому каналу — его перехватят. Отсюда — асимметрика и гибридные схемы.

## 5. Парольная фраза не является ключом

- Пароль — произвольная строка; ключ — строго N бит (например, 256).
- Пароль прогоняется через **KDF** (Key Derivation Function): **PBKDF2**, **scrypt**, **Argon2**.
- **Соль (salt)** — случайные данные, уникальные для каждого шифрования: исключает одинаковые ключи и предвычисления (rainbow tables).
- **Итерации/стоимость** — замедляют перебор. Argon2 дополнительно требует память, что мешает GPU-атакам.
- Дополнительно: **IV/nonce** — не секрет, но должен быть уникальным.

Мораль: стойкость зашифрованного файла = стойкость **пароля + KDF**, а не «AES-256».

## 6. Шифруем и расшифровываем файлы (13:14)

##### 1. Простой пример
```
# OpenSSL: соль + PBKDF2
openssl enc -aes-256-cbc -pbkdf2 -salt -in secret.txt -out secret.enc
openssl enc -d -aes-256-cbc -pbkdf2 -in secret.enc -out secret.txt
```

Параметры: `-salt` включает соль, `-pbkdf2` — нормальный KDF (без него старый EVP_BytesToKey — плохо), `-iter` задаёт число итераций.

##### 2. Пример со взломом

шифруем:

```shell
gpg --symmetric --cipher-algo AES256 --output secret.enc secret.txt
```
утилита запросит пароль: вводим заранее взламываемый `1337`

проверяем свойства файла:

```shell
file secret.enc
# secret.enc: GPG symmetrically encrypted data (AES256 cipher)
```

дешифруем, потребуется ввод пароля

```
gpg --decrypt secret.enc > encrypted_secret.txt
```

но, что если пароль неизвестен?

пробуем сломать не шифр AES а пароль к нему:
- вытащим хеш из файла утилитой `gpg2john`

```shell
gpg2john secret.enc > hash.txt
```

- пробуем сверять хэши с помощью утилиты `john` и словаря паролей `wordlist.txt`

```shell
john --wordlist=wordlist.txt hash.txt
```

![[{DE5BAA51-ADB4-4B01-85D7-756AAD31752C}.png]]

пароль найден.

Ломают **пароль**, а не шифр:

1. Извлекают проверочный хэш/верификатор формата (например, у ZIP свой заголовок и проверка).
2. Перебирают кандидатов: словарь (rockyou), правила (замена букв, добавление цифр), маски (`?l?l?l?d?d`).
3. Сравнивают результат с верификатором.
4. Инструменты: **hashcat** (GPU), **john the Ripper** (CPU/GPU).

Скорость падает с ростом итераций KDF, длины и энтропии пароля. Поэтому «8 символов с цифрой» ломаются минутами, а длинная парольная фраза — практически нет.

## 7. Подбор пароля к .zip

```
zip2john secret.zip > zip.hash
john --wordlist=/usr/share/wordlists/rockyou.txt zip.hash
john --show zip.hash

fcrackzip -u -D -p rockyou.txt secret.zip
```

`zip2john` конвертирует защищённый архив в формат, понятный John. В курсе показывается, что при слабом пароле архив вскрывается за секунды, а при длинной фразе — нет. Вывод: **7-Zip/WinRAR с AES-256 надёжны ровно настолько, насколько надёжен пароль.**

# Часть IV. Хэширование

## 10. Что такое хэширование

Хэш-функция отображает данные произвольной длины в значение фиксированной длины.

Свойства:

- **детерминированность** — одинаковый вход → одинаковый выход;
- **лавинный эффект** — изменение одного бита меняет ~половину бит хэша;
- **необратимость** — по хэшу нельзя восстановить вход (кроме перебора);
- **устойчивость к коллизиям** — трудно найти два разных входа с одинаковым хэшем;
- **фиксированная длина** — SHA-256 всегда 256 бит.

Алгоритмы: MD5 (сломан), SHA-1 (сломан для коллизий), **SHA-256/384/512**, SHA-3, BLAKE2/BLAKE3.

Применение: целостность файлов, хранение паролей (соль + KDF), HMAC, цифровые подписи, идентификация образцов (IOC, VirusTotal), блокчейн.

```
sha256sum file.txt
md5sum file.txt
sha1sum file.txt
```

Сравнение вывода показывает разную длину и то, что MD5/SHA-1 нельзя использовать для безопасности.

## 11. Просмотр хэша в Windows: 7-Zip

Правый клик → 7-Zip → CRC SHA → SHA-256. Удобно без консоли, но для автоматизации лучше PowerShell.

## 12. Просмотр хэша в Windows: PowerShell

```
Get-FileHash .\file.exe -Algorithm SHA256
Get-FileHash .\file.exe -Algorithm MD5
```

## 13. Просмотр хэша в Windows: CertUtil

```
certutil -hashfile file.exe SHA256
certutil -hashfile file.exe MD5
```

`CertUtil` встроен в Windows и часто доступен там, где нельзя запустить сторонние утилиты (важно для реагирования на инциденты).

**Важно:** хэш проверяет целостность, но не подлинность. Если злоумышленник подменил файл и хэш в источнике — проверка пройдёт. Подлинность даёт подпись.

# Часть V. Асимметричное шифрование

## 14. Как это работает

Пара ключей:

- **публичный** — можно публиковать;
- **приватный** — только у владельца.

Свойства:

- зашифровано публичным → расшифровывается приватным (конфиденциальность);
- подписано приватным → проверяется публичным (подлинность).

На пальцах:

- **RSA** — модуль `n = p·q`, открытая экспонента `e`, закрытая `d`; стойкость на факторизации. 2048–4096 бит.
- **ECC** — стойкость на дискретном логарифме в группе точек кривой; короче ключи (256 бит ≈ RSA-3072). ECDH для обмена, ECDSA/Ed25519 для подписи.

## 15. Житейский пример с Thunderbird

PGP/GPG в почтовом клиенте:

1. Генерируется пара ключей.
2. Публичный ключ публикуется (keyserver/сайт/в письме).
3. Отправитель шифрует письмо **публичным ключом получателя**.
4. Получатель расшифровывает **своим приватным**.
5. Отправитель подписывает **своим приватным**, получатель проверяет **публичным отправителя**.

Так одновременно решаются конфиденциальность и подлинность.

## 16. Подводные камни: «два» публичных ключа

Если в хранилище два ключа для одного человека, клиент не знает, какой настоящий. Атакующий может подсунуть свой публичный ключ (key substitution) и читать переписку (MITM).

Защита:

- сверять **fingerprint** по независимому каналу;
- подписывать чужие ключи (web of trust);
- использовать доверенные keyserver и проверять историю ключа;
- в корпоративной среде — централизованное управление ключами.

## 17. Плюсы и минусы

**+** нет общего секрета, удобно для подписи, обмена ключами, аутентификации. **−** медленнее симметрики, большие ключи/подписи, сложное управление доверием и отзывом.

Поэтому стандарт — **гибридное шифрование**: асимметрикой обмениваются сеансовым ключом, данные шифруются AES/ChaCha20 (так работает TLS, PGP, SSH).

# Часть VI. Практика SSH

## 18. Настройка сервера и вход по ключам

```
sudo apt install openssh-server
ssh-keygen -t ed25519 -C "vasya@lab"      # или -t rsa -b 4096
ssh-copy-id user@server
ssh -i ~/.ssh/id_ed25519 user@server
```

Права:

```
chmod 700 ~/.ssh
chmod 600 ~/.ssh/authorized_keys
chmod 600 ~/.ssh/id_ed25519
```

`sshd_config`:

```
PubkeyAuthentication yes
PasswordAuthentication no
PermitRootLogin prohibit-password
```

Перезапуск: `sudo systemctl restart ssh`.

Механика: сервер хранит публичный ключ в `authorized_keys`; клиент доказывает владение приватным ключом, подписывая challenge. Приватный ключ никогда не передаётся по сети.

## 19. Намеренная компрометация приватного ключа

Сценарий: приватный ключ скопирован/украден (нет passphrase, лежит с правами 644, в бэкапе, в git). Атакующий просто входит:

```
ssh -i stolen_key user@server
```

Последствия: полный доступ без пароля, возможность закрепиться (`authorized_keys`, cron, sudoers).

Защита:

- **passphrase** на приватный ключ + ssh-agent;
- права 600 и шифрование диска;
- ротация ключей и удаление старых из `authorized_keys`;
- аудит `authorized_keys` и логов SSH;
- отдельные ключи под задачи, а не один на всё.

# Часть VII. Цифровая подпись и PKI

## 20. Цифровая подпись

Схема:

1. Хэш сообщения/файла.
2. Хэш шифруется **приватным** ключом → подпись.
3. Проверяющий расшифровывает подпись **публичным** ключом и сравнивает хэши.

Даёт: **аутентичность** (кто подписал) и **целостность** (не изменилось). Не даёт конфиденциальности. Подпись можно ставить отдельно (detached) или вместе с данными.

## 21. Иерархия доверия

**Root CA → Intermediate CA → сертификат сайта/издателя.**

- Корневые сертификаты предустановлены в ОС/браузере.
- Промежуточные подписываются корневыми.
- Конечный сертификат содержит публичный ключ, домен (SAN), срок, назначение.
- Проверка: цепочка, срок, имя, отзыв (**CRL** или **OCSP**), политики.

Проблема доверия: компрометация CA или установка злоумышленником своего корня в trust store ломает всю модель.

## 22. Где Windows хранит корневые сертификаты

```
certmgr.msc                                  # хранилище пользователя
certlm.msc                                   # хранилище компьютера
Get-ChildItem Cert:\LocalMachine\Root
certutil -store Root
```

Сюда смотрят браузеры (через CryptoAPI) и проверка подписей. Поэтому вредоносный корневой сертификат — серьёзная угроза.

## 23. Ломаем сертификат, меняя бинарник

Добавляем пару байт в подписанный файл → хэш меняется → подпись не совпадает. Проверка:

```
Get-AuthenticodeSignature .\app.exe
signtool verify /pa app.exe
```

Результат: `HashMismatch` / недействительная подпись. Именно так detect-системы замечают подмену подписанного файла. Но: подпись проверяет целостность и издателя, **а не безопасность** — легально подписанный malware или украденный сертификат всё равно пройдут проверку.

## 24. Как бинарники получают подпись

**Authenticode**:

- вычисляется хэш PE-файла (с учётом структуры PE и исключением области подписи);
- хэш подписывается приватным ключом издателя;
- сертификат и подпись помещаются в **certificate table** PE;
- добавляется **timestamp** (RFC 3161), чтобы подпись оставалась валидной после истечения сертификата.

Проверка строит цепочку до доверенного корня и сверяет хэш. Отсюда — требования к защите приватного ключа подписи (HSM, отдельное хранилище, аудит).

# Часть VIII. Шифрование файлов инструментами

## 25. age

Современная простая утилита для файлов:

```
age-keygen -o key.txt
age -r <public-key> -o secret.age secret.txt
age -d -i key.txt -o secret.txt secret.age
```

Плюсы: современные примитивы (X25519 + ChaCha20-Poly1305), минимализм, понятный формат. Можно шифровать и паролем (`-p`).

## 26. 7-Zip с AES-256

В диалоге архивации: метод `AES-256`, ввод пароля, опция **шифровать имена файлов** (иначе видно структуру). Важно: 7z использует AES-256 + KDF; стойкость = стойкость пароля.

## 27. OpenSSL (57:58)

```
openssl enc -aes-256-cbc -pbkdf2 -iter 100000 -salt -in f -out f.enc
openssl enc -d -aes-256-cbc -pbkdf2 -iter 100000 -in f.enc -out f
```

Демонстрируются параметры и типичные ошибки: забыть `-pbkdf2`, использовать слабый пароль, путать режимы.

## 28. PowerShell Invoke-AESEncryption (1:01:40)

Скрипт-функция на .NET: PBKDF2 (пароль + соль + итерации) → AES → случайный IV → Base64. Показывает, что «шифрование своими руками» возможно, но легко ошибиться (режим, IV, аутентификация). Для реальных задач лучше проверенные библиотеки/AEAD.

# Часть IX. HTTPS и TLS (1:04:48–1:22:27)

## 29. Протокол HTTPS (1:04:48)

HTTPS = HTTP + TLS. Даёт три вещи:

- **конфиденциальность** — трафик шифруется симметричным сеансовым ключом;
- **целостность** — AEAD/MAC ловит изменение;
- **аутентификацию сервера** — сертификат и цепочка доверия.

## 30. Что такое TLS и как он работает (1:06:33)

Handshake договаривается о версии, алгоритмах и ключах; затем весь трафик шифруется AEAD. Сертификат привязывает домен к публичному ключу.

## 31. TLS 1.2 (1:07:28)

Полный handshake ≈ **2 RTT**:

1. `ClientHello` — версии, cipher suites, random, SNI, расширения.
2. `ServerHello` — выбранные параметры, random.
3. `Certificate` — цепочка сервера.
4. `ServerKeyExchange` — параметры ECDHE + подпись.
5. `ClientKeyExchange` — публичная часть клиента.
6. `ChangeCipherSpec` + `Finished` (обе стороны).
7. Вывод ключей (PRF) → симметричный AEAD-трафик.

Слабые места старых конфигураций: RSA key exchange (нет forward secrecy), CBC-режимы, поддержка RC4/3DES, renegotiation.

## 32. TLS 1.3 (1:13:16)

- **1 RTT** на полный handshake (0-RTT для повторных сессий).
- Только **(EC)DHE** — forward secrecy по умолчанию.
- Убраны слабые алгоритмы; шифруется почти весь handshake.
- **0-RTT** быстрый, но уязвим к **replay** — нельзя для неидемпотентных операций.

## 33. Как ломают TLS (1:17:04)

Сам шифр не ломают — атакуют вокруг:

- **MITM** с поддельным сертификатом (если пользователь нажал «продолжить» или в системе установлен чужой корень);
- **downgrade** до старых версий/алгоритмов;
- ошибки реализации (Heartbleed, POODLE, BEAST, CRIME/BREACH, Lucky13);
- слабая конфигурация (RC4, CBC, короткие ключи, отсутствие HSTS);
- компрометация приватного ключа сервера.

## 34. Основные атаки на TLS (1:19:23)

|Атака|Суть|
|---|---|
|MITM + фальшивый сертификат|перехват при доверии к поддельному CA|
|Downgrade / fallback|навязывание TLS 1.0 или слабого шифра|
|Heartbleed|утечка памяти OpenSSL через heartbeat|
|POODLE|атака на padding в SSL 3.0/CBC|
|BEAST|атака на CBC в TLS 1.0|
|CRIME/BREACH|сжатие + утечка секретов (куки/токены)|
|0-RTT replay|повтор early data|

## 35. Актуальные алгоритмы (1:21:59)

- Шифрование: **AES-GCM**, **ChaCha20-Poly1305**.
- Обмен ключами: **X25519**, ECDHE (P-256).
- Подписи: **Ed25519**, ECDSA P-256, RSA (для совместимости).
- Хэши: **SHA-256/384**; MD5/SHA-1 — только для legacy-проверок, не для безопасности.

# Часть X. MAC, HMAC и JWT (1:22:27–1:28:31)

## 36. MAC / HMAC (1:22:27)

**MAC** — код аутентичности сообщения: `MAC = f(key, message)`. Проверяет целостность и подлинность, ключ общий. **HMAC** — конструкция на хэше: `HMAC(K,m) = H((K⊕opad) || H((K⊕ipad) || m))`. Устойчив к length-extension. HMAC ≠ хэш: без ключа нельзя подделать тег.

## 37. HMAC в JWT (1:24:48)

JWT = три части через точку:

```
header.payload.signature
```

- `header` — `{"alg":"HS256","typ":"JWT"}`;
- `payload` — claims (`sub`, `exp`, `iat`, `role`);
- `signature` — HMAC/RSA/ECDSA от `base64url(header).base64url(payload)`.

`HS256` — общий секрет; `RS256` — приватный ключ подписи и публичный для проверки.

## 38. Как выдают и проверяют токен (1:25:59)

1. Логин → сервер проверяет учётные данные.
2. Формирует claims, подписывает токен.
3. Клиент хранит токен и шлёт в `Authorization: Bearer`.
4. Сервер проверяет **подпись**, затем claims: `exp`, `nbf`, `aud`, `iss`, `scope`.
5. При истечении — refresh-токен/повторный логин.

## 39. Основные уязвимости JWT (1:28:11)

- **`alg: none`** — если библиотека доверяет заголовку и не проверяет подпись.
- **Algorithm confusion** — `RS256` → `HS256`: публичный ключ используют как HMAC-секрет.
- **Слабый секрет** HS256 → офлайн-брутфорс.
- **Нет проверки `exp`/`aud`/`iss`** — токен живёт вечно или принимается чужим сервисом.
- **`kid`/`jku`/`x5u`** — path traversal/SQLi в `kid`, подмена URL с ключом.
- **Хранение** в localStorage → XSS; отсутствие отзыва токена.

# Часть XI. Блочные шифры, XOR, режимы (1:28:31–1:50:14)

## 40. Блочные шифры (1:28:31)

AES шифрует блок **16 байт**; ключ 128/192/256 бит. DES (8 байт) и 3DES устарели. Блочный шифр требует **режима** и **padding** (PKCS#7), если длина не кратна блоку.

## 41. Что такое XOR (1:30:04)

```
A ⊕ K = C
C ⊕ K = A
```

Свойства: обратимость, коммутативность, `A ⊕ A = 0`. Проблема: при повторном использовании ключа одинаковые блоки дают одинаковый шифротекст → частотный анализ. XOR — примитив для потоковых шифров, а не самостоятельное шифрование.

## 42. Кодировки ASCII (1:34:49)

Символ ↔ числовой код (A=65, a=97, 0=48). Понимание байтового представления нужно для XOR-практики и анализа payload'ов.

## 43. Энкодер + XOR на PowerShell (1:36:41)

Схема: строка → байты (UTF-8/ASCII) → XOR с ключом → Base64 для вывода. Демонстрирует, как легко «зашифровать» данные и как легко это неверно реализовать.

## 44. Декодер + XOR (1:39:34)

Обратный порядок: Base64 → байты → XOR тем же ключом → строка. Подтверждает обратимость и то, что ключ — единственный секрет.

## 45. Брут слабого XOR-ключа (1:42:09)

Ключ в 1 байт → 256 вариантов. Перебор + оценка «осмысленности» (печатные символы, частоты, словарь) находит ключ мгновенно. Мораль: короткий ключ = нет шифрования.

## 46. Потоковые шифры (1:43:27)

Генерируют **keystream** из ключа и nonce, затем XOR с данными. Быстрые, без padding. **RC4** сломан; **ChaCha20** — современный. Критично: **nonce нельзя повторять** — иначе XOR двух шифротекстов даёт XOR открытых текстов.

## 47. Режимы шифрования (1:44:49)

|Режим|Как работает|Плюсы|Риски|
|---|---|---|---|
|**ECB**|каждый блок отдельно|простота, параллельность|одинаковые блоки → утечка структуры|
|**CBC**|цепочка: `C_i = E(P_i ⊕ C_{i-1})`, случайный IV|скрывает повторы|padding oracle, нужен случайный IV|
|**CTR**|`C_i = P_i ⊕ E(nonce ‖ counter)`|параллельность, скорость|повтор nonce = катастрофа|
|**GCM**|CTR + GHASH-тег|AEAD, целостность|уникальный nonce|

## 48. ECB (1:47:11)

Одинаковые 16-байтовые блоки шифруются одинаково. Структура данных сохраняется — это видно визуально и используется в криптоанализе.

## 49. CTR (1:47:53)

Счётчик + nonce → keystream. Позволяет параллелить и не требует padding. Повтор пары (key, nonce) полностью ломает конфиденциальность.

## 50. CBC (1:48:32)

Каждый блок зависит от предыдущего; IV рандомный и не секретный. Ошибки: фиксированный IV, отсутствие аутентификации → padding oracle (атака на Oracle-серверы).

## 51. «Классический пингвин» и почему ECB — плохо (1:49:10)

Изображение Linux-пингвина, зашифрованное в ECB: контуры и области сохраняются, потому что одинаковые блоки → одинаковый шифротекст. Наглядная демонстрация утечки структуры. Вывод: **ECB не использовать никогда** для реальных данных.

## 52. AEAD (1:49:39)

**Authenticated Encryption with Associated Data** — шифрование + аутентификация одним примитивом: AES-GCM, ChaCha20-Poly1305, CCM.

- **AAD** (associated data) аутентифицируется, но не шифруется (заголовки, метаданные).
- Тег ловит изменение и подмену.
- Современный стандарт: не «CBC + HMAC вручную», а готовый AEAD.

## 53. Финал (1:50:14)

Чек-лист курса:

1. Кодирование, хэш и обфускация — не шифрование.
2. Пароль → KDF (salt + iterations) → ключ.
3. Симметрика для данных, асимметрика для ключей и подписей, на практике — гибрид.
4. Подпись = целостность + авторство; AEAD = конфиденциальность + целостность.
5. TLS ломают через конфигурацию, сертификаты и реализацию; используйте TLS 1.3 и AEAD.
6. JWT — не шифрование: проверяйте `alg`, подпись и claims.
7. Режимы: ECB — никогда; CBC — с IV и осторожно; CTR/GCM — с уникальным nonce.
8. Защищайте приватные ключи и журналы; проверяйте fingerprint и цепочки сертификатов.
