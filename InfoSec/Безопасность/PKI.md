# Принципы PKI

**Public Key Infrastructure (PKI)** - это набор различных технологий, которые используются для обеспечения аутентификации источника, целостности данных и конфиденциальности для пользователя в сети. `PKI` использует пары открытого и закрытого ключей: асимметричная криптография отвечает за аутентификацию (цифровые подписи) и обмен симметричными ключами, а сами данные в больших объёмах шифруются симметричными алгоритмами — шифровать трафик напрямую асимметрикой слишком медленно (подробнее см. [[TLS]]).

В `PKI` открытый ключ обычно связан с цифровой подписью, чтобы добавить доверие и проверить сведения о владельце сертификата. Ниже приведен ключевой жизненный цикл в `PKI`:

- **Генерация ключа**: Этот процесс определяет шифр и размер ключа.
- **Генерация сертификата**: Этот процесс создает цифровой сертификат (на основе запроса на подпись — CSR, см. ниже) и назначает его человеку или устройству.
- **Распространение**: Процесс распространения отвечает за безопасное распространение ключа пользователю или устройству.
- **Хранение**: Этот процесс отвечает за безопасное хранение ключа, чтобы предотвратить любой несанкционированный доступ к нему.
- **Отзыв**: Сертификат или ключ могут быть отозваны, если они скомпрометированы субъектом угрозы.
- **Срок действия**: Каждый сертификат имеет срок службы.
- **Обновление (renewal)**: Продление срока действия сертификата до истечения; рекомендуется выполнять его на свежесгенерированной паре ключей.
- **Архивирование и уничтожение**: Депонирование (escrow) ключей шифрования для возможности восстановления данных либо гарантированное уничтожение ключей по окончании жизненного цикла.

Каждый день мы посещаем различные веб-сайты, такие как социальные сети, стрим, новости, спорт, блоги и другие платформы. Однако задумывались ли вы когда-нибудь о проверке подлинности веб-сайтов, которые вы посещаете? Вы, наверное, думаете, что всему, что находится в Интернете, нельзя доверять. Хотя это отчасти правда, мы можем доверять только ограниченному числу веб-сайтов, например, доверять веб-сайту вашего банка. Главный вопрос заключается в том, как мы можем проверить подлинность веб-сайтов, которые мы посещаем? Именно здесь как `PKI`, так и цифровые сертификаты помогают установить доверие между хостом в Интернете и нашим компьютером.

### Центр сертификации

`PKI` играет жизненно важную роль в Интернете, поскольку многим пользователям и устройствам требуется метод установления доверия в самой ненадежной сети в мире – Интернете. Понимание компонентов, которые помогают `PKI` обеспечить доверие, необходимую как пользователям, так и устройствам, имеет важное значение для любого специалиста по безопасности.

Вы можете рассматривать `PKI` как набор процедур, правил, аппаратного и программного обеспечения, а также людей, которые работают вместе для управления цифровыми сертификатами. Цифровой сертификат-это официальная форма идентификации объекта, которая проверяется доверенной стороной. Эти цифровые сертификаты выдаются доверенной стороной в сети или Интернете. Они известны как **Центр сертификации (Certificate Authority - CA)**.

В каждой стране существует государственное учреждение, которое обычно отвечает за проверку личности своих граждан и выдачу удостоверений личности, такой как паспорт.

Этот паспорт будет содержать важную информацию о владельце и сроке действия, например, дату окончания срока действия. В сети и в Интернете центр сертификации выполняет похожую роль и функции. В Интернете есть множество поставщиков, которые являются доверенными центрами сертификации, которые позволяют вам приобретать цифровой сертификат для личного использования. Примеры доверенных центров сертификации включают _GoDaddy_, _DigiCert_, _Let's Encrypt_, _Comodo_, _Cloudflare_ и многие другие.

> [!note] Важное примечание
> Цифровой сертификат создаётся при объединении ключа и цифровой подписи. Сертификат будет содержать сведения о владельце сертификата, например, об организации.

ЦС выдаст объекту цифровой сертификат только после того, как его личность будет проверена. После того, как ЦС создает цифровой сертификат, он сохраняется в базе данных сертификатов, которая используется для безопасного хранения всех утвержденных ЦС цифровых сертификатов.

> [!warning] Истечение срока ≠ отзыв
> Сертификат попадает в список отзыва (Certificate Revocation List — CRL), только когда его нужно **досрочно** признать недействительным: компрометация закрытого ключа, смена данных владельца, компрометация ЦС. Истёкший сертификат просто перестаёт быть действительным сам по себе и в CRL не вносится.

Цифровой сертификат форматируется с использованием стандарта **X.509**, который содержит следующие сведения:

- Номер версии
- Серийный номер
- Идентификатор алгоритма подписи
- Название эмитента
- Срок годности
- Не раньше, чем
- Не после
- Имя субъекта
- Информация об открытом ключе субъекта
- Алгоритм открытого ключа
- Открытый ключ субъекта
- Уникальный идентификатор эмитента (необязательно)
- Уникальный идентификатор субъекта (необязательно)
- Расширения (необязательно)
- Алгоритм подписи сертификата
- Подпись сертификата

Особую практическую роль играют необязательные расширения X.509:

- **SAN** (Subject Alternative Name) — список имён/доменов, для которых действителен сертификат; сегодня практически вытеснил поле Subject.
- **Key Usage** и **Extended Key Usage** — допустимые операции с ключом: подпись, шифрование, TLS-сервер, TLS-клиент и т. д.
- **Basic Constraints** — признак `CA:TRUE/FALSE` и максимальная глубина пути; отличает сертификаты ЦС от конечных.
- **AIA** (Authority Information Access) — где скачать сертификат издателя; **CDP** (CRL Distribution Points) — где скачать CRL.
- **Subject Key Identifier / Authority Key Identifier** — идентификаторы ключей для быстрого построения цепочки.

### Типы сертификатов

| Тип | Назначение | Проверка при выпуске |
| --- | --- | --- |
| DV (Domain Validation) | сайты, API | подтверждение контроля над доменом |
| OV (Organization Validation) | сайты организаций | проверка юридического лица |
| EV (Extended Validation) | банки, финтех | расширенная проверка юрлица |
| Wildcard (`*.example.com`) | один сертификат на все поддомены одного уровня | как у базового домена |
| SAN / multi-domain | несколько разных доменов в одном сертификате | перечисление в расширении SAN |
| Code Signing | подпись исполняемого кода и пакетов | проверка разработчика/компании |
| Client (пользовательский) | mTLS, вход в системы, S/MIME | проверка личности владельца |

DV/OV/EV относятся к серверным TLS-сертификатам; современные браузеры отображают их практически одинаково, поэтому выбор чаще определяется автоматизацией выпуска, а не «цветом плашки».

### Компоненты PKI

Помимо ЦС в инфраструктуре работают и другие участники:

- **Регистрирующий орган (Registration Authority, RA)** — выполняет проверку личности заявителя и прав на запрашиваемое имя (домен, организация) от имени ЦС. RA сам не подписывает сертификаты — он верифицирует заявки и передаёт их в ЦС. Это позволяет делегировать проверку, оставив ключ подписи в изолированном ЦС.
- **Репозиторий сертификатов** — база выданных сертификатов и точка распространения информации о статусе (URL из AIA/CDP указывают именно сюда).
- **Конечные субъекты (end entities)** — люди, устройства, сервисы, владеющие сертификатами.
- **Служба штампов времени (TSA)** — выдаёт подписанные метки времени: подпись остаётся доказуемой даже после истечения срока или отзыва сертификата подписавшего.

### Выпуск сертификата: CSR и enrollment

Между генерацией пары ключей и выдачей сертификата есть важнейшее звено — запрос:

1. Заявитель локально генерирует пару ключей. **Закрытый ключ никогда не передаётся никому**, включая ЦС.
2. Заявитель формирует **запрос на подпись сертификата (Certificate Signing Request, CSR, стандарт `PKCS#10`)** — структуру, содержащую открытый ключ, атрибуты субъекта (Subject DN, SAN, запрашиваемое назначение ключа) и подписанную закрытым ключом заявителя (proof-of-possession — доказательство владения закрытым ключом).
3. RA/ЦС проверяет личность заявителя и права на имя: для DV — контроль над доменом (email-, DNS- или HTTP-challenge), для OV/EV — документы организации. Именно этот шаг реализует протокол **ACME**, на котором работает автоматизация Let's Encrypt.
4. ЦС подписывает CSR своим ключом и выпускает сертификат X.509, публикуя его в своём репозитории.
5. Сертификат доставляется заявителю: `PEM`/`DER` для одиночного сертификата, `PKCS#7` для цепочки, `PKCS#12` (`.pfx`) — контейнер с сертификатом и приватным ключом.

При обновлении (renewal) рекомендуется выпускать новый сертификат на свежесгенерированной паре ключей.

### Цепочка доверия и валидация

Когда клиент подключается к серверу по TLS, происходит следующее:

1. Сервер в handshake передаёт свой (листовой) сертификат **вместе с цепочкой промежуточных**. Отсутствие промежуточного сертификата — одна из самых частых причин ошибки «недоверенный сертификат».
2. Клиент строит путь: лист → промежуточные → корневой, который должен найтись в локальном хранилище доверенных корней (trust store).
3. Для каждого звена проверяются: подпись вышестоящего сертификата, срок действия, `Basic Constraints` (`CA:TRUE` у промежуточных) и `Key Usage`, соответствие имени хоста полю SAN, статус отзыва, ограничения `Name Constraints`.
4. Если промежуточного нет в handshake, клиент пытается скачать его по ссылке AIA.

Иногда корневые сертификаты **кросс-подписываются** другими корнями ради обратной совместимости (исторический пример — кросс-подпись Let's Encrypt через IdenTrust): тогда к одному конечному сертификату ведут две параллельные валидные цепочки.

### Проверка статуса сертификата

Отзыв бессмыслен, если клиенты не умеют узнавать о нём. Механизмы проверки:

- **CRL** — полный список отозванных сертификатов, публикуемый ЦС по URL из CDP. Прост, но громоздок при больших объёмах; существуют дельта-CRL, содержащие только изменения с прошлой публикации.
- **OCSP** (Online Certificate Status Protocol) — онлайн-запрос статуса конкретного сертификата. Быстрее CRL, но запрос раскрывает ЦС, какой сайт посещает пользователь; клиенты часто работают в режиме *soft-fail* (недоступный ответчик не блокирует соединение).
- **OCSP Stapling** — сервер сам периодически получает подписанный OCSP-ответ и «пришивает» его к TLS-handshake: клиенту не нужно ходить в ЦА, растут скорость и приватность. Расширение `Must-Staple` требует обязательного наличия stapled-ответа.
- На практике браузеры почти всегда soft-fail, поэтому индустрия смещается к **короткоживущим сертификатам** (Let's Encrypt — 90 дней, обсуждаются ещё меньшие сроки): при таком сроке отзыв теряет актуальность, а выпуск автоматизируется протоколом ACME.
- **Certificate Transparency (CT)** — публичные append-only журналы всех выданных сертификатов (Chrome требует SCT). Позволяет владельцу домена обнаружить несанкционированный выпуск; удобный инструмент мониторинга — crt.sh.

Далее давайте рассмотрим, как создается цифровая подпись и ее роль в PKI.

### Цифровая подпись

При совершении деловых операций на документах требуется подпись, чтобы гарантировать, что сделка санкционирована соответствующим лицом. Такая же концепция требуется в сети, так что цифровая подпись отправляется вместе с сообщением на конечный хост. Затем узел назначения может использовать цифровую подпись для проверки подлинности сообщения.

При использовании `PKI` используются следующие алгоритмы для создания и проверки цифровых подписей:

- `DSA`
- `RSA`
- `Elliptic Curve Digital Signature Algorithm (ECDSA)`
- `EdDSA` (Ed25519) — современная схема на эллиптических кривых, детерминированная и быстрая
- `ГОСТ Р 34.10-2012` — российская схема ЭП (см. раздел «Российская специфика» ниже)

Требования к параметрам: RSA — не менее 2048 бит (лучше 3072), ECDSA — P-256 и сильнее. Хеш-функции для дайджеста — SHA-256 и выше; MD5 скомпрометирован, SHA-1 запрещён после демонстрации практических коллизий (см. [[Хеширование]]).

Чтобы создать цифровую подпись, между Алисой (отправителем) и Бобом (получателем) происходит следующий процесс:

1) Алиса будет использовать алгоритм хеширования для создания хэша (дайджеста) сообщения:![[Pasted image 20240122101001.png]]
2) Затем Алиса будет использовать свой закрытый ключ для шифрования хэша (дайджеста) сообщения:![[Pasted image 20240122101029.png]]
Цифровая подпись используется в качестве доказательства того, что Алиса подписала сообщение.

Чтобы лучше понять, как используются цифровые подписи в реальной жизни, давайте представим, что в сети есть два пользователя. Алиса хочет отправить Бобу сообщение. Алиса может использовать цифровую подпись с сообщением, чтобы заверить Боба в том, что сообщение исходило именно от нее. Это шаги, которые Алиса будет использовать для обеспечения подлинности, целостности и неотрицания:

1. Алиса создаст пару открытых и закрытых ключей для шифрования данных.
2. Алиса даст Бобу только открытый ключ. Таким образом, закрытый ключ хранится у Алисы.
3. Алиса создаст сообщение для Боба и создаст хэш (дайджест) сообщения.
4. Затем Алиса будет использовать закрытый ключ для шифрования хэша (дайджеста) сообщения для создания цифровой подписи.
5. Алиса отправит сообщение и цифровую подпись Бобу.
6. Боб будет использовать открытый ключ Алисы для расшифровки цифровой подписи, чтобы получить хэш сообщения.
7. Боб также сгенерирует хэш сообщения и сравнит его с хэшем, полученным из цифровой подписи Алисы. Как только два значения хэша (дайджеста) совпадают, это просто означает, что сообщение подписано и отправлено Алисой.

Цифровые подписи используются не только для проверки подлинности сообщений. Они также используются в следующих случаях:

- Цифровые подписи для цифровых сертификатов: это позволяет отправителю вставить цифровую подпись в цифровой сертификат.
- Цифровые подписи для подписи кода: это позволяет разработчику приложения вставить свою цифровую подпись в исходник приложения, чтобы помочь пользователям проверить подлинность программного обеспечения или приложения.

### Система доверия PKI

Ранее мы узнали, что организация может получить цифровой сертификат от доверенного центра сертификации в Интернете. Однако во многих крупных организациях вы обычно найдете корневой ЦС и множество промежуточных ЦС. Корневой ЦС отвечает за создание первичного цифрового сертификата, который затем делегируется каждому подчиненному ЦС или промежуточному ЦС. Промежуточный ЦС будет использовать цифровой сертификат корневого сервера для создания новых цифровых сертификатов для конечных устройств, таких как внутренние серверы.

На следующем рисунке показана иерархия корневого и промежуточного ЦС:

![[Pasted image 20240122101137.png]]

Использование этого типа иерархической структуры снимает нагрузку с корневого центра сертификации по управлению всеми цифровыми сертификатами в организации. Некоторые из этих обязанностей делегированы промежуточным серверам ЦС в сети. Представьте, что в вашем головном офисе вы развернули корневой ЦС, а в каждом удаленном филиале развернули промежуточные ЦС. Следовательно, каждый промежуточный ЦС отвечает за управление сертификатами своего собственного домена или филиала. Это также снижает риски взлома корневого ЦС злоумышленником, так что в случае взлома промежуточного ЦС корневой ЦС может быть отключен от сети, не затрагивая другие конечные устройства или промежуточные ЦС.

В небольших сетях можно развернуть один корневой ЦС для предоставления цифровых сертификатов каждому конечному устройству, как показано на следующем рисунке:

### Корпоративная PKI

В крупных организациях PKI разворачивают самостоятельно (Microsoft AD CS, HashiCorp Vault PKI, step-ca и др.):

- **Корневой ЦС держат офлайн**: физически отключённый сервер или ключ в HSM включается только для выпуска/продления промежуточных ЦС. Это резко снижает риск компрометации корня.
- Работающий онлайн промежуточный (issuing) ЦС выпускает все конечные сертификаты.
- **AD CS** (Active Directory Certificate Services): шаблоны сертификатов, интеграция с Active Directory, **автоматическая регистрация (autoenrollment)** пользователей и машин через GPO, Key Recovery Agent для архивации ключей шифрования, NDES/SCEP для сетевого оборудования.
- Точки CDP/AIA публикуют на всегда доступных URL (HTTP/LDAP) — иначе клиенты не смогут проверить статус сертификатов.
- Доверие к корпоративному корню распространяют через GPO. Важно помнить: любой добавленный корень — это полное доверие ко всему, что он подпишет, поэтому сторонние корни в trust store инвентаризируют и контролируют.

---

### Хранение приватных ключей

Компрометация закрытого ключа обнуляет безопасность всей инфраструктуры:

- **HSM** (Hardware Security Module) — аппаратный модуль безопасности: ключи генерируются и используются внутри устройства, извлечь их невозможно; обязательны для корневых и промежуточных ЦС (сертификация FIPS 140-2/140-3).
- **TPM** — чип на плате ПК/сервера для аппаратного хранения ключей устройства.
- Программные хранилища: Windows (CNG/DPAPI, хранилище сертификатов), macOS Keychain, Linux keyring/NSS DB; секрет-менеджеры (HashiCorp Vault, облачные KMS).
- **Неизвлекаемость (non-exportable)** ключей защищает от копирования даже при доступе к системе.
- **Key escrow (депонирование)** — архивная копия закрытого *ключа шифрования* для восстановления зашифрованных данных. Подписные ключи никогда не восстанавливают из архива — их перевыпускают, чтобы сохранить неотрицаемость подписи.
- Операционные процессы: инвентаризация сертификатов и контроль сроков (просрочка — классическая причина аварий), ротация, план реагирования на компрометацию (отзыв + перерегистрация).

### Атаки на PKI и известные инциденты

- **Компрометация ЦС — DigiNotar (2011)**: выпущены поддельные сертификаты `*.google.com`, что позволило проводить MITM против пользователей; все серты удалили из trust store, компания обанкротилась.
- **Недобросовестный ЦС — Symantec (2015–2017)**: систематические нарушения процедур выпуска привели к постепенному исключению всех брендов Symantec из браузеров.
- **Коллизии хешей**: SHAttered (2017) продемонстрировал практическую коллизию SHA-1 → SHA-1 полностью выведен из сертификатов.
- **Слабые ключи**: ROCA (2017, факторуются ключи Infineon TPM), баг Debian OpenSSL (2008) с малой энтропией.
- **Подмена доверия на клиенте**: Superfish (Lenovo, 2015) — предустановленный прокси с собственным корнем в trust store ломал TLS. Корпоративные MITM-прокси делают то же легитимно, но расширяют поверхность атаки (см. [[Атака Man-In-The-Middle]]).
- **Простой из-за просрочки**: Microsoft Teams (2020) — истёкший сертификат положил сервис на часы.

Митигации: Certificate Transparency, короткоживущие сертификаты, pinning на уровне приложений (HTTP HPKP устарел), минимизация числа корней в trust store, офлайн-хранение корневого ключа.

### Где применяется PKI

- **HTTPS/TLS** — базовый сценарий: аутентификация сервера (см. [[Безопасность транспортного уровня (TLS)]]).
- **mTLS** — взаимная аутентификация: обе стороны предъявляют сертификаты; основа service mesh и внутреннего трафика Kubernetes.
- **VPN** (IKEv2/IPsec, SSTP) и доступ в сеть по **802.1X/EAP-TLS**.
- **S/MIME** — шифрование и подпись электронной почты.
- **Подписание кода** (Authenticode, JAR) и документов.
- **Идентичность устройств и людей**: клиентские сертификаты для входа, IDevID (IEEE 802.1AR).
- Подписанные токены: `JWT`/`JWS` могут ссылаться на X.509-цепочку через заголовок `x5c`.

### Российская специфика

- Правовая база — **63-ФЗ «Об электронной подписи»** (см. [[ФЗ 63]]): виды подписей — простая (ПЭП), усиленная неквалифицированная (**УНЭП**) и усиленная квалифицированная (**УКЭП**); УКЭП равнозначна собственноручной подписи без дополнительных соглашений.
- Алгоритмы: **ГОСТ Р 34.10-2012** (электронная подпись), **ГОСТ Р 34.11-2012 «Стрибог»** (хеширование); ГОСТ-TLS требует СКЗИ с поддержкой ГОСТ-наборов шифров (см. [[Криптография]], [[TLS]]).
- Юридическую силу имеет только сертификат **аккредитованного УЦ Минцифры**; корневые сертификаты размещены в ТСПУ (технических средствах проверки ЭП). Международные публичные ЦС для юридически значимых операций в РФ не применяются.
- Типичный стек: КриптоПро CSP / ViPNet CSP как СКЗИ, КриптоПро УЦ / ViPNet УЦ как программные центры сертификации (см. [[Технология ViPNet]], [[ФЗС PKI]], [[Класс СКЗИ]]).

### Шпаргалка команд

```bash
# Посмотреть сертификат сервера и полную цепочку
openssl s_client -connect example.com:443 -servername example.com -showcerts </dev/null

# Разобрать файл сертификата (сроки, SAN, издатель, расширения)
openssl x509 -in cert.pem -text -noout

# Быстрая проверка срока годности (для мониторинга)
openssl x509 -in cert.pem -noout -subject -issuer -enddate

# Создать пару ключей + CSR
openssl req -new -newkey rsa:3072 -nodes -keyout key.pem -out request.csr \
  -subj "/C=RU/O=Example/CN=example.com" \
  -addext "subjectAltName=DNS:example.com"

# Самоподписанный сертификат для тестов
openssl req -x509 -newkey rsa:3072 -nodes -days 365 -keyout key.pem -out cert.pem

# Проверить цепочку
openssl verify -CAfile ca.pem -untrusted intermediates.pem cert.pem

# Экспорт в PKCS#12 (для Windows/IIS)
openssl pkcs12 -export -in cert.pem -inkey key.pem -out bundle.pfx
```

```powershell
# Windows: разбор и проверка сертификатов
certutil -dump cert.cer          # разобрать файл сертификата
certutil -store My               # список личных сертификатов
certutil -verifystore My         # проверить цепочки в хранилище

# Мониторинг истечения сроков
Get-ChildItem Cert:\LocalMachine\My |
  Select-Object Subject, NotAfter |
  Sort-Object NotAfter

# Java: просмотр keystore
# keytool -list -v -keystore keystore.jks
```
