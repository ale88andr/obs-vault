# IPsec

> [!abstract] О чём это
> Конспект по организации VPN на базе набора протоколов **IPsec**: архитектура, IKEv1/IKEv2, SA и SPI, режимы инкапсуляции, аутентификация, актуальные алгоритмы, атаки и чеклист харденинга.

## Концепция VPN

**VPN (Virtual Private Network)** — набор криптографических механизмов, обеспечивающих защищённый двусторонний канал для передачи данных через незащищённую сеть (например, Интернет). Пользователь получает доступ к удалённой сети и работает с её ресурсами так, как если бы находился внутри неё.

Типовые сценарии:

- **Remote access** — дистанционный сотрудник подключается к корпоративной сети.
- **Site-to-site** — постоянный туннель между офисами/ЦОД через Интернет.
- **Защита трафика между сегментами** — шифрование между зонами внутри инфраструктуры (east-west).

## Терминология

| Термин | Значение |
| --- | --- |
| Туннель (tunnel) | Соединение типа point-to-point между двумя участниками |
| Пир (peer) | Участник туннеля; шифрует исходящий и расшифровывает входящий трафик |
| VPN-шлюз | Пир, к которому сходится несколько туннелей |
| Домен шифрования (encryption domain) | Сеть за шлюзом, трафик которой считается «защищаемой» зоной. Сам трафик внутри домена не шифруется |
| VPN-клиент | ПО на устройстве пользователя для установки туннеля |

Примеры клиентов именно для IPsec: strongSwan, встроенные клиенты ОС (IKEv2/L2TP+IPsec в Windows/macOS/Linux), Cisco Secure Client, Shrew Soft.

> [!warning] Не путать
> OpenVPN — это TLS-based VPN, отдельная технология, не IPsec. VyprVPN, TunnelBear и подобные — коммерческие consumer-сервисы, а не корпоративные клиенты.

Установка соединения всегда сводится к трём шагам:

1. Пиры **идентифицируют** друг друга (аутентификация).
2. Согласуют **протоколы и алгоритмы** защиты целостности и конфиденциальности.
3. **Вырабатывают ключи** шифрования.

## Архитектура IPsec

IPsec (RFC 4301) — не один протокол, а фреймворк из четырёх уровней:

![[Pasted image 20240627111359.png]]

1. **Протоколы AH и ESP** — реализуют аутентификацию, целостность и (для ESP) шифрование.
2. **Алгоритмы** — HMAC, AES-GCM и т.д., конкретная реализация функций первого уровня.
3. **DOI (Domain of Interpretation)** — реестр: какие алгоритмы поддерживает какой протокол.
4. **IKE** — согласование политики и управление ключами.

### AH (Authentication Header, RFC 4302)

Обеспечивает:

- Аутентификацию источника;
- Целостность всего пакета, включая неизменяемые поля заголовка IP;
- Защиту от replay (порядковые номера).

Ключевые ограничения:

- **Нет конфиденциальности** — данные читаемы в канале.
- **Несовместим с NAT**: NAT меняет адреса/порты в заголовке IP → контрольная сумма целостности перестаёт сходиться → пакет отбрасывается.

На практике AH почти не используется — его ниша закрыта комбинацией ESP + NAT-T.

### ESP (Encapsulating Security Payload, RFC 4303)

Основной рабочий протокол IPsec. Обеспечивает:

- **Конфиденциальность** — шифрование полезной нагрузки (обязательная функция);
- Целостность и аутентификацию источника (опционально, но обычно включены);
- Анти-replay через номера последовательности.

AH и ESP можно комбинировать, но современная практика — только ESP в связке с AEAD-шифрами (см. [[#Актуальные алгоритмы]]).

## IKE: управление ключами

**IKE (Internet Key Exchange)** работает поверх UDP/500 и отвечает за взаимную аутентификацию пиров, согласование алгоритмов и выработку ключей. Исторически собран из ISAKMP (формат сообщений), Oakley и SKEME (режимы обмена ключами). Ключевой строительный блок — обмен Диффи–Хеллмана для выработки общего секрета по незащищённому каналу.

> [!important] DH ≠ метод аутентификации
> Диффи–Хеллман — механизм *выработки общего секрета*. Он используется в IKE всегда, независимо от способа аутентификации. PSK или сертификат — это способ *удостоверить*, что обмен DH ведётся с настоящим пиром, а не с MITM (см. [[Атака Man-In-The-Middle]]).

### IKEv1 vs IKEv2

| | IKEv1 (RFC 2409) | IKEv2 (RFC 7296) |
| --- | --- | --- |
| Рукопожатие | Phase 1 + Phase 2, до 8+ сообщений | 4 сообщения: `IKE_SA_INIT` → `IKE_AUTH` |
| Фазы | Main / Aggressive mode, затем Quick mode | Единая логика, Child SA создаётся сразу |
| Аутентификация клиента | XAUTH / Mode-CFG (костыли) | EAP нативно |
| Роуминг клиента | Нет | MOBIKE (RFC 4555) — смена IP/Wi-Fi→LTE без разрыва туннеля |
| Надёжность | Нет подтверждения доставки | Счётчики сообщений, ретрансмиссии |
| NAT-T | Пристройка | Встроен в протокол |

Практическое правило: **настраивают только IKEv2**. IKEv1 оставляют лишь там, где старое железо больше ничего не умеет.

### Aggressive Mode — почему он опасен

В IKEv1 Phase 1 есть два режима:

- **Main mode** — 6 сообщений, identity пиров передаётся зашифрованно.
- **Aggressive mode** — 3 сообщения, identity и хеш от PSK передаются **в открытом виде**.

Aggressive mode + PSK = злоумышленник снимает оффлайн-брутфорс словарём без взаимодействия с шлюзом. Если PSK слабый — туннель скомпрометирован. Отсюда правило: PSK только с Main mode (лучше — только IKEv2) либо полный переход на сертификаты.

## SA, SPI, SPD/SAD

- **SA (Security Association)** — однонаправленное защищённое соединение в терминах IPsec. Каждый туннель — минимум две SA: по одной на каждое направление.
- **SPI (Security Parameter Index)** — 32-битный идентификатор SA. Входящий пакет мапится на SA тройкой **{SPI, протокол, dst IP}** из внешнего заголовка.
- **SPD (Security Policy Database)** — база политик: какой трафик защищать, какой пропускать в обход, какой запрещать.
- **SAD (Security Policy Database→SA Database)** — база активных SA.

У каждой SA есть **lifetime** (время жизни по времени/объёму). По истечении выполняется rekey — новая SA поднимается до смерти старой, чтобы туннель не рвался. Живость пиров проверяется **DPD (Dead Peer Detection)**.

## Режимы инкапсуляции

### Туннельный режим (tunnel mode)

Шифруется и инкапсулируется **весь исходный IP-пакет**, включая заголовки; сверху добавляется новый внешний заголовок с адресами шлюзов. Скрывает топологию внутренней сети.

Применение: site-to-site (gateway-to-gateway), remote access. Стандарт де-факто.

![[Pasted image 20240627112024.png]]

Ход пакета:

1. Хост отправляет обычный пакет в свою частную сеть.
2. Шлюз-инициатор инкапсулирует его в ESP и шифрует.
3. Пакет идёт через публичную сеть к шлюзу-получателю.
4. Получатель проверяет целостность, расшифровывает, снимает инкапсуляцию.
5. Исходный пакет доставляется хосту получателя.

### Транспортный режим (transport mode)

Защищается только полезная нагрузка; оригинальный заголовок IP остаётся наружу (видны адреса конечных точек).

Применение: защита связи host-to-host, когда конечные устройства сами завершают IPsec (например, L2TP/IPsec: транспортный ESP поверх L2TP).

![[Pasted image 20240627112058.png]]

### Порты и протоколы для firewall

Разрешать нужно точно это (иначе «туннель не поднимается» чаще всего отсюда):

- IP protocol **50** — ESP
- IP protocol **51** — AH (не нужен, если AH не используется)
- UDP/**500** — IKE
- UDP/**4500** — NAT-T

**NAT-T (NAT Traversal, RFC 3947/3948):** при обнаружении NAT на пути ESP инкапсулируется в UDP/4500 — так решается проблема несовместимости ESP с трансляцией адресов.

## Аутентификация пиров

IPsec не диктует метод — стороны согласовывают. Основные варианты:

### PSK (Pre-Shared Key)

Общий секретный ключ, заранее распределённый между пирами. Используется как секрет для MAC/подписи обмена IKE (поверх DH).

Плюсы: просто настроить, нет зависимости от PKI.
Минусы:

- Масштабируется плохо: каждый новый пир = новый ключ (или один общий у всех);
- Компрометация одного ключа затрагивает все соединения, где он использован;
- Человекочитаемые/слабые PSK брутфорсятся, особенно в Aggressive mode.

Правила гигиены: длина ≥ 25 случайных символов, свой ключ на каждую пару пиров, ротация, никогда не использовать словарные фразы.

### Цифровые сертификаты

Каждому пиру выдаётся сертификат от удостоверяющего центра (см. [[PKI]]). Последовательность:

1. Инициатор предъявляет сертификат и доказывает владение закрытым ключом (подписью данных IKE).
2. Ответчик проверяет цепочку доверия к CA, срок действия, назначение (EKU), CRL/OCSP.
3. При успехе — продолжается установка SA.

Плюсы: масштабируемость, отзыв скомпрометированного узла, привязка identity к инфраструктуре PKI.
Минусы: требует работающего PKI и компетенций по его обслуживанию.

Для remote access поверх сертификатов сервера клиент дополнительно проходит **EAP** (например, EAP-TLS) — так IKEv2 аутентифицирует пользователя, а не только устройство.

### Защита от MITM

Чистый Диффи–Хеллман уязвим к атаке «человек посередине»: атакующий ведёт отдельные DH-обмены с каждым пиром. Поэтому в IKE DH-обмен всегда аутентифицируется (PSK или подписью сертификата) — конструкция SIGMA в IKEv2 спроектирована именно против этого. Подробности — в [[Атака Man-In-The-Middle]].

## Шифрование: симметричное и асимметричное

Распределение ролей строгое:

- **Весь трафик данных шифруется симметрично** (AES и производные): быстро, аппаратно ускоряемо (AES-NI).
- **Асимметричная криптография используется только внутри IKE**: DH для выработки общего секрета, RSA/ECDSA для аутентификации подписью. Полезную нагрузку асимметрично никто не шифрует — это было бы на порядки медленнее.

## Актуальные алгоритмы

| Назначение | Использовать | Не использовать |
| --- | --- | --- |
| Шифрование | AES-GCM-128/256 (AEAD), ChaCha20-Poly1305 (AEAD) | DES, 3DES, AES-CBC без AEAD — legacy |
| Целостность (если не AEAD) | SHA-256/384 (HMAC) | MD5, SHA-1 |
| DH-группы | Group 14+ (MODP 2048+), Group 19/20 (ECP-256/384), Group 31 (Curve25519) | Group 1, 2, 5 (устарели) |

> [!tip] AEAD
> AES-GCM даёт шифрование + целостность одной операцией. При использовании AEAD отдельный HMAC в SA не задаётся вовсе — ни для ESP, ни для IKE. Это текущий стандарт де-факто: быстрее и проще в настройке, меньше мест для ошибки конфигурации.

3DES и SHA-1 прямо запрещены требованиями PCI DSS и исключаются из новых развёртываний.

### PFS (Perfect Forward Secrecy)

Свойство компрометации долгосрочного ключа (PSK/закрытого ключа сертификата): прошлый записанный трафик **не** расшифровывается. Обеспечивается тем, что для каждого Child SA выполняется одноразовый DH-обмен — сессионные ключи нигде не выводятся из долгосрочного секрета. В IKEv2 включается опцией PFS в Child SA; рекомендуется держать включённой.

## Атаки и операционная практика

Типовые векторы против IPsec-развёртываний:

- **Оффлайн-брутфорс PSK** через Aggressive mode (или перехват IKE_AUTH при слабом PSK);
- **DoS на UDP/500 и UDP/4500** — заваливание IKE-демона полуоткрытыми сессиями (смягчается cookie-механизмами IKEv2);
- **Downgrade до IKEv1/слабых алгоритмов**, если разрешено сосуществование версий;
- **Уязвимости реализаций**: история CVE strongSwan и IKE-демонов показывает, что сам факт «включённого IPsec» ничего не гарантирует — нужны регулярные обновления шлюзов.

Split tunnel vs full tunnel:

- **Full tunnel** — весь трафик клиента через корпорацию: контроль полный, но нагрузка на шлюз выше.
- **Split tunnel** — в туннель только корпоративные подсети: экономно, но заражённый клиент становится мостом между Интернетом и внутренней сетью. Решение принимается осознанно, а не «по умолчанию».

MTU/MSS: инкапсуляция добавляет накладные расходы (ESP ~50–70+ байт), из-за чего большие пакеты фрагментируются или отбрасываются. Симптом классический — «часть сайтов через VPN не открывается». Лечится MSS clamping и корректным PMTUD.

Диагностика (минимальный набор):

```bash
# Linux (strongSwan)
ip xfrm state          # активные SA
ip xfrm policy         # политики SPD
swanctl --list-sas     # активные IKE/Child SA
journalctl -u strongswan

# Cisco
show crypto ikev2 sa
show crypto ipsec sa

# Wireshark
udp.port == 500 || udp.port == 4500   # IKE/NAT-T
esp                                    # ESP-трафик
```

## Чеклист харденинга

- Только IKEv2; IKEv1 отключён (или ограничен явно заданными старыми пирами);
- Aggressive mode выключен; аутентификация сертификатами, PSK — как исключение и только сильные;
- Шифры: AES-GCM-128/256 или ChaCha20-Poly1305; DH Group 14+/19/20/31;
- PFS включён для Child SA;
- Rekey и lifetime SA настроены (типично: IKE SA 8h, Child SA 1h);
- DPD включён; неиспользуемые туннели закрываются;
- Пиры ограничены белым списком; на firewall открыты только нужные порты (50, UDP 500/4500);
- Логирование IKE-сессий и алерты на массовые неудачные рукопожатия (признак брутфорса);
- Прошивки/версии шлюзов и клиентов обновляются регулярно;
- Split/full tunnel — осознанное решение, а не дефолт.

## Альтернативы IPsec

| Технология | База | Когда выбирать |
| --- | --- | --- |
| IPsec/IKEv2 | Сетевой уровень (L3) | Site-to-site, зрелая экосистема, поддержка любым роутером |
| TLS-VPN (OpenVPN, SSL VPN) | Транспортный уровень | Remote access через строгие NAT/прокси, простота развёртывания |
| WireGuard | Современный L3 | Быстрый, компактный (~4k строк кода), фиксированный криптонабор (Curve25519, ChaCha20-Poly1305), быстрый роуминг |
| L2TP/IPsec | L2-туннель поверх IPsec | Legacy; сам L2TP не шифрует, вся безопасность — от IPsec |
| SSTP | TLS over TCP/443 | Windows-only сценарии прохождения через прокси |
| PPTP | Legacy | **Не использовать** — криптография сломана (MS-CHAPv2 взламывается) |
