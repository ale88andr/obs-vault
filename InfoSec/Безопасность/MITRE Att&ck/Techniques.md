# Techniques в MITRE ATT&CK: техники и подтехники

**Technique (техника)** — уровень ATT&CK, на котором описан способ действия атакующего: не «зачем» (это тактика), а **«как именно»**. Техника — рабочая единица модели: к ней привязываются детекты, меры защиты, группы, ВПО и кампании. Если тактики нужны для разговора о целях, то техники — для написания правил, приоритизации и измерения покрытия.

Объём в текущей версии **ATT&CK v20.0** (13 октября 2026):

| Домен | Тактики | Техники | Подтехники |
| --- | --- | --- | --- |
| Enterprise | 15 | 227 | 479 |
| Mobile | 12 | 78 | 47 |
| ICS | 12 | 78 | 26 |

В Enterprise к техникам привязано 44 mitigation, 703 detection strategy, 1770 analytics и 106 data components — то есть на одну технику в среднем приходится по нескольку детект-подходов. Это и есть главная практическая мысль: **техника ≠ правило детекта**, одна техника требует набора аналитик под разные платформы.

## Иерархия: от тактики до процедуры

| Уровень | Отвечает на вопрос | ID | Пример |
| --- | --- | --- | --- |
| Tactic | Зачем атакующему это нужно | `TAxxxx` | TA0005 Stealth |
| Technique | Как он это делает в общем виде | `Txxxx` | T1070 Indicator Removal |
| Sub-technique | Какая конкретно разновидность поведения | `Txxxx.yyy` | T1070.006 Timestomp |
| Procedure | Кто и чем это делал в реальности | — | APT5 стирал логи SSL VPN утилитой THINBLOOD |

Уровней ровно три: **подтехник второго порядка не существует** (`T1234.001.002` не бывает). Дальнейшая детализация живёт не в ID, а в двух других местах: в блоке **Procedure Examples** (какая группа или какое ВПО так делало) и в ваших собственных правилах.

## Как устроен ID техники

- **`Txxxx` — базовая техника.** Используется, когда поведение известно в общем виде либо когда детали процедуры не важны: например, «атакующий работал с командной строкой» без уточнения оболочки.
- **`Txxxx.yyy` — подтехника.** Появляется там, где разновидность поведения даёт **отдельную видимость или отдельную меру**. `T1059 Command and Scripting Interpreter` имеет 13 подтехник (PowerShell `.001`, AppleScript `.002`, Windows Command Shell `.003`, Unix Shell `.004`, Visual Basic `.005`, Python `.006`, JavaScript `.007`, Network Device CLI `.008`, Cloud API `.009`, AutoHotKey/AutoIT `.010`, Lua `.011`, Hypervisor CLI `.012`, Container CLI/API `.013`) — потому что для каждой нужен свой источник телеметрии и свои правила.
- **ID не переиспользуются.** Номер закрепляется за объектом навсегда, даже если объект переименовали (T1070 в старых версиях назывался Indicator Removal on Host).
- **Объект может быть deprecated или revoked.** Deprecated — техника больше не используется и не заменена; revoked — заменена другим объектом (в STIX есть поле `revoked-by`). Устаревшие страницы остаются доступны по прямой ссылке.
- **Техника может относиться к нескольким тактикам.** `T1053 Scheduled Task/Job` — Execution, Persistence и Privilege Escalation; `T1078 Valid Accounts` — Initial Access, Persistence, Privilege Escalation и Stealth. Тактики подтехники — подмножество тактик родителя.

## Анатомия страницы техники

Каждая страница на attack.mitre.org построена одинаково, и это удобно для автоматизации (весь контент есть в STIX/JSON).

| Блок страницы | Что это | Зачем SOC-инженеру |
| --- | --- | --- |
| Description | Что делает атакующий, чем это отличается от соседних техник | Понять границы детекта: где заканчивается T1070 и начинается T1685 |
| Sub-techniques | Список дочерних ID | Выбрать уровень маппинга правил |
| Tactic / Platforms | К каким тактикам относится, на каких платформах применима | Отсечь неприменимое: правило для Windows не нужно для ESXi |
| Permissions Required / Effective Permissions | Какие права нужны для выполнения | Оценить, реализуема ли техника в вашей модели прав |
| Procedure Examples | Таблица «группа/ВПО → как именно делали» | Готовые гипотезы для hunting и проверки правил |
| Mitigations (`Mxxxx`) | Классы контролей, закрывающих технику | Маппинг на ваш стек и на требования регулятора |
| Detection Strategy (`DETxxxx`) → Analytics (`ANxxxx`) | Подход к обнаружению + отдельные аналитики по платформам | Прямое ТЗ на правило: что именно искать и в каких данных |
| Version / Created / Last Modified | Ревизия объекта и даты | Отслеживать пересборку правил при обновлении ATT&CK |
| References | Отчёты CTI, на которых построена техника | Первоисточники для проверки формулировок |

Полезная деталь: с версии v18 старые **Data Sources** заменены связкой **Detection Strategy → Analytics → Data Components**. Analytics описывает логику («мониторим последовательность удаления журналов и ключей реестра после подозрительного запуска процесса»), а Data Component — конкретный класс телеметрии (Process Creation, File Deletion, Command Execution, Network Traffic Flow, Windows Registry Key Modification и т.д.). Именно Data Components удобно сопоставлять со своими источниками: Sysmon, `4688`, EDR-события, аудит Linux, логи облака.

## Разбор на примере T1070 Indicator Removal

Хороший образец полной страницы — `T1070` (версия 3.0, создана 31 мая 2017, изменена 12 мая 2026).

- **Тактика:** Stealth. **Платформы:** Windows, Linux, macOS, Containers, ESXi, Network Devices, Office Suite.
- **Подтехники (8):** `.003` Clear Command History, `.004` File Deletion, `.005` Network Share Connection Removal, `.006` Timestomp, `.007` Clear Network Connection History and Configurations, `.008` Clear Mailbox Data, `.009` Clear Persistence, `.010` Relocate Malware.
- **Procedure Examples:** APT42 чистил историю Chrome; APT5 утилитой THINBLOOD удалял логи SSL VPN в `/home/runtime/logs`; SUNBURST убирал значения прокси из реестра; Lazarus возвращал исходный код `KernelCallbackTable` после перехвата; Maze вызывал `Wow64RevertWow64FsRedirection` после удаления теневых копий.
- **Mitigations:** `M1029` Remote Data Storage (пересылка событий на отдельный сервер), `M1041` Encrypt Sensitive Information, `M1022` Restrict File and Directory Permissions.
- **Detection Strategy:** `DET0184` «Behavioral Detection of Indicator Removal Across Platforms» — одна стратегия и шесть аналитик по платформам: `AN0520` Windows (удаление логов, ключей реестра, задач, prefetch), `AN0521` Linux (bash history, syslog, audit, `.ssh`), `AN0522` macOS (unified logs, plist, история Terminal), `AN0523` Containers (`/var/log`), `AN0524` ESXi (команды shell/PowerCLI, история `hostd`/`vpxa`), `AN0525` Office Suite (правила в почте, аудит-ящики).

Практический вывод из устройства этой страницы: **один маппинг «T1070» не даёт детекта** — даёт детект связка «подтехника + платформа + data component», то есть `T1070.004` + Windows + File Deletion. И наоборот: правило «очищен журнал Security» — это конкретно `T1685.005` Clear Windows Event Logs, а не «что-то из удаления следов».

## Что изменилось в v20 по техникам

- **Новые техники (7):** `T1699` Direct Prompt Injection, `T1698` Indirect Prompt Injection, `T1700` AI-Enabled Exfiltration, `T1697` Steal Application Specific Passwords, `T1696` Anti-Automation Evasion (`.001` Automate CAPTCHA Completion, `.002` Avoid CAPTCHA), `T1608.007` AI Result Poisoning, `T1685.007` Impair Autonomous Defenses. Тема релиза — поведение вокруг ИИ-сервисов и автономных защитных механизмов.
- **Консолидация в ICS:** появилась `T1701` Command and Scripting Interpreter с подтехниками, а старые `T0807` Command-Line Interface и `T0853` Scripting отправлены в deprecated.
- **Перестройка дерева:** подтехники `T1070.001` Clear Windows Event Logs и `T1070.002` Clear Linux or Mac System Logs ушли из T1070 и живут теперь как `T1685.005` и `T1685.006`. Правило, помеченное старым ID, формально ссылается на несуществующий объект.
- **Колебания статусов:** Mobile-техника `T1476` Deliver Malicious Application via Other Means вернулась из deprecated (была убрана в v11) — так что «deprecated» не всегда окончательно.

Вывод для процессов: при каждом релизе прогонять changelog (`mitre/cti`, тег вида `ATT&CK-v20.0`) и сверять свои маппинги — иначе heatmap покрытия постепенно расходится с реальностью.

## Почему техник 227, а карточек в матрице 259

Техника живёт в каждой тактике, к которой относится, поэтому сумма карточек по столбцам (259) больше числа уникальных техник (227): 32 техники стоят более чем в одной колонке. Отсюда два следствия:

- «Покрытие по тактике» нельзя считать простым сложением — одна и та же техника закроет сразу несколько столбцов.
- Приоритизация идёт по **поведению, а не по тактике**: если закрыть `T1003 OS Credential Dumping` и `T1550 Use Alternate Authentication Material`, вы снимаете риск сразу в Credential Access и Lateral Movement.

## Куда ведут связи с техники

Страница техники — хаб, из которого расходятся три набора связей:

| Направление | Объекты | Как используется |
| --- | --- | --- |
| Defenses | Mitigation `Mxxxx`, Detection Strategy `DETxxxx`, Analytics `ANxxxx`, Data Components | Настройка средств защиты, ТЗ на детекты, выбор источников телеметрии |
| CTI | Group `Gxxxx`, Software `Sxxxx`, Campaign `Cxxxx` | Приоритизация под своего нарушителя: что реально делает интересующая вас группа |
| Structure | Tactic `TAxxxx`, sub-techniques, deprecated/revoked-ссылки | Навигация по модели и версионирование правил |

Связи многие-ко-многим: у одной техники десятки процедурных примеров, у одной группы — десятки техник. Поэтому «маппинг по группе» без просмотра её страницы почти всегда даёт пробелы: удобнее взять группу, выгрузить её техники, а затем проверить, у каких из них у вас нет ни одного детекта.

## Как применять: рабочий порядок

1. **Выберите технику по своему риску, а не по красоте модели.** Ориентиры: отраслевые отчёты, страницы групп, которые вас реально атакуют, и собственные инциденты за последний год.
2. **Спуститесь на уровень подтехники**, если платформа и способ поведения известны. Остались на базовой `Txxxx` — так и помечайте, это честнее, чем выдуманная точность.
3. **Проверьте Platforms и Permissions** — применима ли техника в вашей среде вообще.
4. **Прочитайте Procedure Examples** — там видно, какие артефакты остаются, и это готовые гипотезы для hunt.
5. **Возьмите Detection Strategy → Analytics** как каркас правила, а Data Components сопоставьте с тем, что у вас реально собирается. Пусто в Data Component — значит, нужен источник данных, а не новое правило.
6. **Пометьте правило ID техники в метаданных** (поле в SIEM, тег в EDR, комментарий в Sigma), иначе heatmap в ATT&CK Navigator придётся собирать вручную.
7. **Проверьте технику эмуляцией** (Atomic Red Team, Caldera) и запишите результат: детект сработал / не сработал / сработал, но не туда.

Для автоматизации: STIX-репозиторий `mitre/cti`, python-библиотека `mitreattack-python`, слои `.json` для ATT&CK Navigator. Это позволяет держать покрытие в виде данных, а не в виде презентации.

## Типичные ошибки

- **Маппинг по инструменту, а не по поведению.** «Mimikatz → T1003» упускает, что тот же запуск попадает в `T1059` (исполнение), `T1027` (обфускация), `T1558` (керберотинг) и `T1003.001` (доступ к LSASS).
- **Путать уровни.** Техника — не уязвимость (это CVE), не инструмент (это `Sxxxx`) и не группа (`Gxxxx`). «APT29» — не техника.
- **Считать покрытие по числу правил.** Метрика — сколько техник из вашего приоритетного списка имеют хотя бы одну аналитику и подтверждены эмуляцией.
- **Детект на уровне тактики.** Правило «подозрительная активность в Defense Impairment» нецелевое; детект строится на подтехнике и платформе.
- **Игнорировать платформу и права.** Аналитика под Linux на хостах без аудита `execve` даёт ноль событий, а не ноль атак.
- **Не следить за версиями.** Переезд `T1070.001` → `T1685.005` и deprecation ICS-техник ломают маппинги молча.
- **Один детект на технику.** У `T1059.001` PowerShell аналитики различаются для интерактивной сессии, доставки в память и скрипта из задачи планировщика.
- **Мапить только то, что есть в отчёте.** Красивая цепочка без Discovery и Credential Access выглядит полной, но не покрывает самый долгий этап присутствия.
