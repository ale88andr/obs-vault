## 1. Как работает LLMNR?

LLMNR — это протокол, разработанный Microsoft (описан в RFC 4795, который так и остался в статусе *Experimental* — полноценным стандартом IETF он не стал), позволяющий компьютерам в одной локальной сети (Link-Local) разрешать имена хостов в IP-адреса, не используя DNS-сервер. Он работает на уровне L2/L3 через мультикаст (IPv4: `224.0.0.252`, UDP-порт `5355`).

Представь стандартную логику Windows, когда пользователь пытается подключиться к какому-то ресурсу (например, вводит в проводнике `\\shared_folder` или делает опечатку вроде `\\shred_folder`):
1. DNS-клиент: Windows сначала стучится к основному DNS-серверу. Если DNS знает этот хост, всё отлично.
2. `LLMNR / NetBIOS / mDNS`: Если DNS-сервер отвечает "Я не знаю такого хоста" (`NXDOMAIN`), Windows не сдается. Она кричит на всю локальную сеть через `LLMNR`: «Эй, у кого-нибудь есть имя `SHRED_FOLDER`? Пришлите мне свой IP!» Нет ответа — пробует `NetBIOS-NS`, затем `mDNS`.
3. Ответ хоста: Если компьютер с таким именем существует, он отвечает напрямую отправителю.

> [!important] Полная цепочка fallback-резолвинга в современных Windows: `DNS → LLMNR → NetBIOS → mDNS`
> Для защиты мало убить один протокол — атака молча переезжает на следующий в очереди. Отключать нужно все три.

## 2. Вектор атаки

Проблема `LLMNR` (и его старого брата `NetBIOS-NS`, а также `mDNS`) в том, что в них полностью отсутствует аутентификация. Любой участник локальной сети может заявить: «Да, `SHRED_FOLDER` — это я! Вот мой IP».

В среде тестирования на проникновение это классическая атака типа `MitM`, которая обычно реализуется с помощью утилиты `Responder` или `Inveigh`.

### Сценарий атаки (LLMNR Poisoning / Spoofing):

1. Опечатка пользователя: Бухгалтер или администратор ошибается в имени сетевого диска: `\\server_backup` вместо `\\server-backup`.
2. DNS молчит: DNS-сервер отвечает, что хоста `server_backup` нет.
3. Крик в сеть: Windows отправляет мультикаст-запрос `LLMNR`: «Кто такой `server_backup`?»
4. Перехват (`Poisoning`): Злоумышленник, запустивший `Responder` в этой же сети, мгновенно реагирует и отправляет ложный ответ: «`server_backup` — это я, отправляй данные на мой IP!»
5. Запрос аутентификации: Windows жертвы думает, что подключается к легитимному файловому серверу, и пытается пройти аутентификацию.
6. Утечка хэша: Windows отправляет атакующему сетевые учетные данные. В зависимости от настроек это будет хэш `NetNTLMv1` или `NetNTLMv2`.

### Атакующему не нужна опечатка: коэрсия аутентификации

Сценарий выше — учебный: он зависит от ошибки пользователя. В реальных проектах атакующий не ждёт, а заставляет машину аутентифицироваться сама — через coercion-техники: `PetitPotam`, `PrinterBug` (MS-RPRN), `DFSCoerce`, `Coercer`. Они провоцируют целевой хост (например, контроллер домена или файловый сервер) подключиться к SMB-шаре атакующего.

Учетные данные компьютера (`machine account`) релеятся так же, как пользовательские, поэтому атака становится детерминированной, а не вероятностной. Это главный аргумент за то, чтобы не «надеяться на пароли», а выключать протоколы полностью.

### Что атакующий делает с хэшем?

- Offline Cracking (Перебор): Если у пользователя слабый пароль, хэш NetNTLMv2 быстро расшифровывается с помощью `Hashcat` (режим `-m 5600` для NetNTLMv2) или `John the Ripper`.
- **NetNTLMv1 ломается за секунды**: через радужные таблицы (crack.sh и аналоги) — независимо от длины и сложности пароля. Поэтому его нужно не «паролить», а запрещать политикой (см. Шаг 5).
- SMB Relay (Реле): Если на целевом сервере отключена подпись `SMB` (SMB Signing), атакующий может не ломать хэш, а просто «переслать» (отрелеить) этот запрос аутентификации на другой сервер в сети и мгновенно получить там доступ с правами жертвы. Если жертва — администратор, то сеть скомпрометирована за секунды.
- Релей работает не только на SMB: цели могут быть `HTTP` (в т.ч. веб-регистрация ADCS — атаки класса `ESC8`), `LDAP/LDAPS`, `IMAP`. Поэтому защита одним лишь SMB Signing не исчерпывается — см. Шаг 5.

### Смежные поверхности: WPAD и IPv6

Даже если LLMNR/NetBIOS/mDNS отключены, у атакующего остаются два классических обходных пути в той же сети:

- **WPAD (Web Proxy Auto-Discovery)**: `Responder` из коробки поднимает HTTP-сервер и отвечает на поиски `wpad.dat`. Жертва получает фальшивую конфигурацию прокси, её трафик идёт через атакующего, включая повторные попытки аутентификации NTLM.
- **mitm6 / IPv6**: Windows предпочитает IPv6, даже если он «не настроен». Инструмент `mitm6` спуфит DHCPv6 и становится DNS-сервером для жертв, после чего релеит их аутентификацию в `LDAPS`/`HTTP`. Отравка LLMNR закрыта, а домен всё равно берётся — классическое продолжение реальных пентестов.

## 3. Как избежать рисков? (Hardening)

Поскольку в современных сетях с настроенным DNS эти протоколы практически не нужны, лучшая практика — вырубить их полностью.

### Шаг 1: Отключение LLMNR через Group Policy (GPO)

Это самый эффективный способ для доменной среды Active Directory.
1. Открой `gpmc.msc` (Редактор управления групповыми политиками).
2. Перейди по пути: `Конфигурация компьютера -> Административные шаблоны -> Сеть -> DNS-клиент` (`Computer Configuration -> Administrative Templates -> Network -> DNS Client`).
3. Найди политику: «`Выключить разрешение имен многоадресной рассылки`» (`Turn off multicast name resolution`).
4. Переведи ее в состояние `Включено` (`Enabled`).

> [!tip] Среда без GPO (гибридная / Entra ID)
> Тот же параметр разворачивается через **Intune** → Settings Catalog → политика `Turn off multicast name resolution` (ADMX DnssClient). Эквивалент в реестре: `HKLM:\SOFTWARE\Policies\Microsoft\Windows NT\DNSClient` → `EnableMulticast = 0`.

### Шаг 2: Отключение NetBIOS над TCP/IP

Раз уж мы закрываем `LLMNR`, нужно закрыть и `NetBIOS`, так как Windows при его активности откатится на него.

- Через DHCP (рекомендуется): В настройках области DHCP-сервера выбери `DHCP Options -> Advanced -> Измени значение параметра 043 Vendor Specific Info` (или в свойствах `IPv4 -> Advanced -> WINS выбери Disable NetBIOS over TCP/IP`).
- Через `GPO` (скриптом): NetBIOS часто отключают через PowerShell-скрипты, распространяемые через GPO, меняя ключи в реестре для сетевых адаптеров: `HKLM:\System\CurrentControlSet\Services\NetBT\Parameters\Interfaces\ (значение NetbiosOptions выставить в 2)`.

### Шаг 3: Отключение mDNS

Через GPO mDNS не выключается — только реестром (раскатать скриптом через GPO/Intune):

```powershell
Set-ItemProperty 'HKLM:\SYSTEM\CurrentControlSet\Services\Dnscache\Parameters' -Name EnableMDNS -Value 0
Restart-Service Dnscache   # или перезагрузка
```

### Шаг 4: Отключение WPAD

- GPO: `Конфигурация пользователя -> Административные шаблоны -> Компоненты Windows -> Internet Explorer` → «Отключить автоматическое определение параметров» (`Disable Auto Proxy discovery`). Дополнительно отключи службу `WinHttpAutoProxySvc`.

### Шаг 5: Митигация, если нельзя отключить (Defense in Depth)

Если в силу каких-то легаси-причин (древние станки или софт) протоколы отключить нельзя:
1. Включи `SMB Signing` (Подпись SMB): Обязательно потребуй подпись SMB на всех серверах и рабочих станциях. Это полностью защитит от атак класса SMB Relay. Нюанс: в Windows Server 2025 и Windows 11 24H2 обязательная подпись включена по умолчанию — проверять вручную нужно legacy-серверы.
2. Включи `LDAP Signing` + `Channel Binding` на контроллерах домена: иначе релей возможен в LDAP/LDAPS (это то, чем добивает `mitm6`).
3. Включи `EPA` (Extended Protection for Authentication): Защищает от релея на другие сервисы (например, `HTTP/LDAP`). Обязательно на серверах ADCS — иначе атака `ESC8` через веб-регистрацию сертификатов.
4. Запрети NTLMv1: Политика «Сетевая безопасность: уровень проверки подлинности LAN Manager» → «Отправлять только NTLMv2-ответы. Отказывать LM и NTLM». NetNTLMv1 не спасает ни один пароль.
5. Сложные пароли: Длинные пароли (**14+ символов**) делают offline-перебор хэшей `NetNTLMv2` бесполезным.
6. Сегментация сети: Изолируй критические серверы от обычных рабочих станций, чтобы широковещательный трафик пользователей до них не долетал.
7. NAC / 802.1X: Корень проблемы — атакующему нужен доступ на L2. Контроль доступа в сеть не даёт чужому устройству вообще подключиться к сегменту.

### Шаг 6: Проверка, что политика применилась

```powershell
Get-ItemProperty 'HKLM:\SOFTWARE\Policies\Microsoft\Windows NT\DNSClient'
# Ожидаем: EnableMulticast = 0

Get-ItemProperty 'HKLM:\SYSTEM\CurrentControlSet\Services\Dnscache\Parameters'
# Ожидаем: EnableMDNS = 0
```

Контрольный прогон изнутри сети: запусти `Responder --analyze` / `Inveigh` и сделай заведомо ошибочный запрос (`ping nonexistent-name-test`). Ответов быть не должно.

### Шаг 7: Мониторинг (Детект)

События создания служб (`4697`/`7045`) ловят уже постэксплуатацию после успешного релея — полезно, но поздно. Лучшая практика — ловить саму отравку:

- **Canary-имена** (самый дешёвый и надёжный детект): зарегистрируй фейковые хосты (`file-srv`, `backup-share`, `wpad`, `isatap`). Легитимного ответа на их LLMNR-запрос не существует — любой ответ означает атакующего в сегменте. Заведи алерт в SIEM.
- **Microsoft Defender for Identity** имеет готовые алерты на LLMNR/NBT-NS/mDNS poisoning.
- Сетевые сенсоры (`Zeek`/`Suricata`): сигнатура на несколько ответов на один LLMNR-запрос (гонка ответов) — признак спуфинга.
- Ручная проверка: Wireshark с фильтром `udp.port == 5355` (и `udp.port == 5353` для mDNS). Сделай ошибочный запрос: легитимно — ноль ответов; два и более — кто-то травит сеть.
- Аномальная активность по UDP-портам `5355`/`5353`.
- События Windows Event ID `4697` или `7045` (попытки создания сервисов — часто при успешном релее с правами админа). Плюс Event ID `4776` для аудита NTLM-аутентификаций.

> [!summary]
> `LLMNR` — это атавизм. В 2026 году его включенное состояние в корпоративной сети — это огромный и неоправданный риск. Вырубай связку `LLMNR + NetBIOS + mDNS + WPAD` через GPO/Intune, закрывай релей (SMB Signing, LDAP Signing, EPA на ADCS), ставь canary-имена на детект и периодически проверяй сеть тем же Responder в режиме анализа.
