## 5.1 Карточки активов

### Что такое карточка актива

> [!note] Карточка = рабочий инструмент
> Карточка актива — это основной интерфейс для анализа конкретного узла. Здесь собрана вся информация об активе: конфигурация, уязвимости, история изменений, принадлежность к группам.

### Структура карточки

> [!info] Как открывается карточка
> Из таблицы активов — щелчком по названию актива. Быстрый просмотр доступен в боковой панели **Актив**. Под именем актива располагаются сведения о его жизненном цикле, интегральная уязвимость и метрика значимости актива (низкая, средняя, высокая или не определена). Ниже — график интегральной уязвимости за выбранный период (по умолчанию за последние 7 дней), на котором отмечаются моменты получения новых данных об активе.

Под графиком расположены вкладки. Для сетевых узлов и служб каталогов Microsoft Active Directory отображаются вкладки **Сводка**, **Уязвимости**, **Конфигурация** и **Метрики CVSS**; для учётных записей — **Сводка**, **Конфигурация** и **Метрики CVSS** ([[Карточка актива]]). Отдельной вкладки «История» в карточке нет: сравнение конфигураций и экспорт истории выполняются отдельными действиями на странице **Активы** (см. ниже).

Интегральная уязвимость — это сумма оценок опасности всех уязвимостей актива. Для расчёта берётся оценка CVSS v3, а если её нет — CVSS v2.

#### Вкладка «Сводка» (Summary)

Краткая сводная информация об активе:

| Поле | Описание | Пример |
| --- | --- | --- |
| Имя / FQDN | DNS-имя хоста | `SRV-DB-01.corp.local` |
| IP-адрес | Текущий IP | `192.168.1.50` |
| ОС | Операционная система | `Windows Server 2022` |
| Тип хоста | Сервер / Рабочая станция | `Server` |
| Вендор | Производитель ОС | `Microsoft` |
| Значимость | Уровень критичности | `H` (High) |
| Последнее сканирование | Дата и время аудита | `2026-08-20 14:30` |
| Collector | Какой Collector собрал данные | `collector-01` |

#### Вкладка «Конфигурация» (Configuration)

Подробная информация об аппаратном и программном обеспечении:

- **Аппаратное обеспечение:** процессор, ОЗУ, диски, сетевые адаптеры
- **Установленное ПО:** полный список программ с версиями и путями установки
- **Сетевые настройки:** IP-адреса, подсети, шлюзы, DNS, открытые порты и сервисы
- **Пользователи:** локальные учётные записи и группы
- **Сервисы:** запущенные службы, тип запуска, учётные записи

#### Вкладка «Уязвимости» (Vulnerabilities)

Список всех уязвимостей, обнаруженных на данном активе. Вкладка содержит блоки **Уязвимости ОС и ПО** и **Уязвимости сетевых служб**; для каждой уязвимости указана оценка опасности и есть ссылка на CVE, по названию открывается карточка уязвимости.

| Столбец | Описание |
| --- | --- |
| Название | Наименование уязвимости |
| CVE | Идентификатор CVE |
| CVSS | Оценка тяжести (0-10) |
| Уровень опасности | Критический / Высокий / Средний / Низкий / Не определен |
| HasFix | Есть ли исправление |
| Статус | Новая / В работе / Исправляется / Требуется проверка / Просрочено / Исключена / Устранена |
| ПО / Сервис | На что повлиял |

Статусы здесь и далее — документированные статусы экземпляров уязвимостей (см. [«Статусы обработки уязвимостей»](#статусы-обработки-уязвимостей) и [[Изменение статуса уязвимостей]]).

#### Вкладка «Метрики CVSS» (CVSS Metrics)

Контекстные метрики CVSS, которые можно настраивать:

> [!tip] Кастомизация CVSS
> Стандартный CVSS не учитывает контекст вашей сети. MaxPatrol VM позволяет изменять метрики CVSS для конкретного актива, чтобы оценка отражала реальный риск.

Значения метрик можно устанавливать и изменять как для актива, так и для группы, в которую он непосредственно входит. Эффективное значение определяется автоматически как **максимум** из значений, заданных для актива и его непосредственной родительской группы; значения метрик из групп, расположенных выше в иерархии, при расчёте метрик актива не учитываются.

| Метрика | Описание | Влияние |
| --- | --- | --- |
| Attack Vector (AV) | Вектор атаки | Network / Adjacent / Local / Physical |
| Attack Complexity (AC) | Сложность атаки | Low / High |
| Privileges Required (PR) | Необходимые привилегии | None / Low / High |
| User Interaction (UI) | Взаимодействие пользователя | None / Required |
| Scope (S) | Область воздействия | Unchanged / Changed |

#### История изменений (Change History)

> [!important] Аудит изменений
> История показывает, что изменилось в конфигурации актива между сканированиями. Это критично для отслеживания нежелательных изменений.

- Добавленное / удалённое ПО
- Изменения в конфигурации ОС
- Изменения в сетевых настройках
- Новые открытые порты / сервисы
- Изменения значимости

**Сравнение конфигураций во времени** — отдельное действие на странице **Активы**, а не вкладка карточки:

1. Главное меню → **Активы**, выберите один или несколько активов.
2. В панели инструментов нажмите кнопку сравнения → откроется окно **Сравнение конфигураций для \<N\> активов**.
3. Выберите два момента времени и нажмите **Сравнить**.
4. При необходимости включите **Только изменения**, чтобы убрать активы без изменений.

История конфигураций также доступна для экспорта в XML-формате (кнопка экспорта истории конфигураций в панели инструментов страницы **Активы**) — см. [[Сравнение конфигураций актива]] и [[Экспорт истории конфигурации актива]].

### Как найти карточку актива

1. **Через поиск:** введите IP, FQDN или имя в строке поиска
2. **Через группу активов:** откройте группу → найдите актив → нажмите на имя
3. **Через PDQL:** `Filter(Host.Fqdn = 'SRV-DB-01') | Select(@Host, Host.Fqdn, Host.IpAddress)` → кликните на результат
4. **Через строку поиска:** введите `SRV-DB-01` в строке поиска и преобразуйте условие поиска в условие фильтрации — это быстрее, чем писать PDQL
5. **Через уязвимость:** откройте паспорт уязвимости → вкладка «Активы» → выберите актив

## 5.2 Паспорта и экземпляры уязвимостей

### Модель данных: два уровня

> [!important] Ключевое понимание
> MaxPatrol VM различает два уровня представления уязвимостей: **паспорт** (описание) и **экземпляр** (конкретный случай на конкретном активе). Это не одно и то же.

Все уязвимости на активах типизированы: у каждого типа есть паспорт с общей справочной информацией обо всех уязвимостях, которые к нему принадлежат. Паспорт выглядит так же и содержит ту же информацию, что и карточка уязвимости, **за исключением** того, что в паспорте нет информации об уязвимостях на конкретных активах — не указаны даты и способы обнаружения, контекстные метрики CVSS ([[Карточка уязвимости]]).

В карточке уязвимости можно менять статус, отмечать уязвимость как важную и проставлять метки. Для уязвимости в карточке отображаются метки ключевых параметров: **Трендовая**, **Есть эксплойт** (для веб-приложений — **Эксплойт подтвержден**), **Удаленно**, **Можно исправить**, **Есть патч**, а также типы последствий эксплуатации — **RCE**, **LPE**, **DoS**.

### Паспорт уязвимости (VulnerPassport)

Паспорт — это **описание** уязвимости, не привязанное к конкретному активу.

| Поле | Описание | Пример |
| --- | --- | --- |
| CVE | Уникальный идентификатор | `CVE-2024-12345` |
| Название | Наименование уязвимости | `Remote Code Execution in OpenSSL` |
| Описание | Подробное описание | `Allows remote attackers to execute...` |
| CVSS Score | Оценка тяжести | `9.8` |
| Уровень | Critical / High / Medium / Low | `Critical` |
| CVSS Vector | Вектор оценки | `CVSS:3.1/AV:N/AC:L/PR:N/UI:N/S:U/C:H/I:H/A:H` |
| Наличие исправления | `@VulnerPassport.Metrics.HasFix` | `true` |
| Возможность эксплуатации | `@VulnerPassport.Metrics.Exploitable` | `true` |
| Эксплуатация по сети | `@VulnerPassport.Metrics.HasNetworkAttackVector` | `true` |
| Дата публикации | Когда CVE был опубликован | `2024-03-15` |
| Метод устранения | Рекомендации | `Обновить OpenSSL до версии 3.0.15` |
| Затронутое ПО | Какие продукты уязвимы | `OpenSSL 3.0.x < 3.0.15` |

### Экземпляр уязвимости (Vulner)

Экземпляр — это **конкретный случай** уязвимости на **конкретном активе**.

| Поле | Описание | Пример |
| --- | --- | --- |
| Актив | На каком хосте | `SRV-DB-01 (192.168.1.50)` |
| ПО / Сервис | Что уязвимо | `OpenSSL 3.0.12` |
| Путь установки | Куда установлено | `/usr/lib/x86_64-linux-gnu/` |
| Статус | Состояние обработки (`Host.@Vulners.Status`) | `Новая` |
| Срок устранения | До когда нужно исправить (`Host.@Vulners.DueTime`) | `2026-09-15` |
| Ответственный | Кто отвечает | `ИТ-отдел` |
| Компенсирующие меры | Временные решения | `Изоляция сегмента` |
| Дата обнаружения | Когда нашли | `2026-08-20` |

### Статусы обработки уязвимостей

> [!tip] Жизненный цикл уязвимости
> Каждая уязвимость проходит путь от обнаружения до закрытия. Статусы позволяют отслеживать этот процесс.

Статус хранится в `Host.@Vulners.Status` — по нему можно искать и фильтровать активы (см. [[Псевдонимы уязвимостей]], [[4. Язык PDQL]]).

| Статус (в интерфейсе) | Код `Host.@Vulners.Status` | Описание | Как назначается |
| --- | --- | --- | --- |
| **Новая** | `new` | Впервые обнаружена | Автоматически (при сканировании); также политикой при действии «Устранение вручную» |
| **В работе** | `inProgress` | Принята в работу | Оператор ИБ, вручную |
| **Исправляется** | `awaitingFix` | Запланировано устранение | Политика «Плановое устранение» или вручную |
| **Требуется проверка** | `stale` | Нужно проверить, удалось ли исправить | Автоматически: уязвимость не исправлена в указанный срок |
| **Просрочено** | `overdue` | Истёк запланированный срок исправления | Автоматически: при следующем сканировании уязвимость подтверждена |
| **Исключена** | `excluded` | Исключена из числа подлежащих устранению | Политика «Исключить» (с причиной и сроком) |
| **Устранена** | `fixed` | Исправлена | Автоматически (при проверке/сканировании) или оператор |
| — | `null` | Уязвимость не указана | |

Вместе со статусом фиксируется **тип устранения** (`Host.@Vulners.FixType`) и **срок** (`Host.@Vulners.DueTime`), а для исключения — **уточнение к статусу** (причина):

| Причина (псевдоним `@Vulners.StatusReason`) | Описание |
| --- | --- |
| `AcceptedAsLowRisk` | Низкий риск |
| `CannotFix` | Не может быть устранена |
| `CompensatingControl` | Приняты меры по её устранению |
| `FalsePositive` | Ложное срабатывание |
| `FalsePositiveResolved` | Ложное срабатывание устранено |
| `OfficialFix` | Устранена в штатном режиме либо после нового сканирования неактуальна |

> [!warning] Правила политик и ручные правки
> При ручном изменении уязвимостей правила политик перестают действовать по этим экземплярам. Вернуть управление правилами можно кнопкой **Использовать правила** — см. [[Использование правил]]. Массовое изменение статуса: страница **Активы** → поле `Host.@Vulners` → вкладка **Уязвимость** → **Изменить статус** ([[Изменение статуса уязвимостей]]).

### HasFix — есть ли исправление

| Значение | Описание | Действие |
| --- | --- | --- |
| `true` | Есть патч или обновление | Установить исправление |
| `false` | Исправления нет | Компенсирующие меры или принятие риска |

> [!warning] HasFix = false
> Если для уязвимости нет исправления, единственные варианты — компенсирующие меры (изоляция, экраны, отключение сервиса) или принятие риска. Это должно быть документально оформлено.

### Сроки устранения

Срок задаётся не «автоматически от CVE», а **правилом политики «Статусы уязвимостей»**:

1. В окне создания правила выбирается действие (**Плановое устранение** / **Устранение вручную** / **Исключить**) и **срок** — до какой даты уязвимость должна быть устранена или исключена.
2. Значение срока хранится в `Host.@Vulners.DueTime`, время последнего изменения статуса — в `Host.@Vulners.StatusUpdateTime`, комментарий — в `Host.@Vulners.StatusComment`.
3. Если до указанного срока уязвимость не устранена, статус автоматически становится **Требуется проверка** (`stale`), а при подтверждении проблемы при следующем сканировании — **Просрочено** (`overdue`).
4. Для исключения срок задаётся отдельно; по его истечении экземпляры по умолчанию планируются к устранению в течение **семи дней**.

Создание правил — см. [[Создание правила для статусов уязвимостей]] и [[Настройка политик]].

> [!note] Типовой пример документации
> Документация оговаривает: «Рекомендуем подбирать параметры политик в зависимости от стандартов, принятых в организации». Пример параметров из «Настройки политик»:

| Группа / тип активов | Действие и срок |
| --- | --- |
| Windows | Плановое устранение — **1 месяц** |
| Linux, Unix | Плановое устранение — **1 месяц** |
| Cisco (сетевое оборудование) | Устранение вручную |
| Тестовая инфраструктура | Исключить, уточнение к статусу: низкий риск — **12 месяцев** |

> [!tip] Как проверить сроки
> - Стандартный виджет **Плановое устранение и новые без политики** на дашборде «Управление уязвимостями»;
> - Запрос по псевдониму: `Filter(Host.@Vulners.DueTime < Now())`.

## 5.3 Группы активов

### Назначение групп

> [!note] Группировка — основа управления
> Группы активов позволяют:
> - Организовать инфраструктуру по функциональному / территориальному / бизнес-принципу
> - Назначать политики (значимость, статусы уязвимостей, сроки актуальности) на группы
> - Задавать значимость для групп
> - Фильтровать активы в отчётах и виджетах, а также в таблице активов
> - Управлять сроками устранения уязвимостей

### Статические группы

**Определение:** фиксированный набор активов, добавленных оператором вручную.

**Когда использовать:**
- Разовые проекты (миграция, редизайн сети)
- Временные группы («серверы для аудита», «теневые IT»)
- Активы, которые невозможно найти автоматически

**Как создать:**

1. Главное меню → **Активы** → на странице **Активы** открыть панель **Группы**.
2. Нажать кнопку создания группы.
3. В окне создания указать **Название**, **Расположение** и тип группы — **Статическая**.
4. Добавить активы вручную.

**Недостатки:**
- Требуют ручного обновления
- Новые активы не попадают автоматически
- Трудно поддерживать при большом количестве активов

### Динамические группы

> [!important] Динамические группы — сила MaxPatrol VM
> Динамическая группа определяется PDQL-запросом. При каждом обновлении данных система пересчитывает состав группы автоматически.

**Когда использовать:**
- Постоянные политики (сканирование, значимость, сроки)
- Автоматическая классификация новых активов
- Мониторинг изменений в инфраструктуре

**Как создать:**

1. Главное меню → **Активы** → панель **Группы** → кнопка создания группы.
2. В окне создания выбрать тип **Динамическая**.
3. В поле **Фильтр** ввести PDQL-запрос.

> [!warning] Доступ к активам
> Создать динамическую группу может только пользователь, у которого есть доступ ко **всем** активам системы. Создание групп описано в «Создание группы активов» (раздел «Работа с активами»).

**Примеры PDQL-запросов для динамических групп:**

| Группа | PDQL-запрос |
| --- | --- |
| Все серверы Windows | `WindowsHost and Host.HostType = 'Server'` |
| Рабочие станции Windows | `WindowsHost and Host.HostType = 'Desktop'` |
| Серверы Linux | `UnixHost` |
| Cisco-оборудование | `NetworkDeviceHost and NetworkDeviceHost.Vendor = 'Cisco'` |
| Серверы без сканирования > 30 дней | `Host.@AuditTime < Now() - 30days` |
| Ubuntu-серверы | `UnixHost and Host.OsName = 'Ubuntu'` |
| Активы с уязвимостью CVSS ≥ 9 | `Host[@Vulners.CVSS3Score >= 9]` |
| Активы с известным CVE-эксплойтом | `Host[@Vulners.Metrics.Exploitable]` |
| Активы вне подсети DMZ | `not Host.@IpAddresses.Item in 203.0.113.0/20` |
| Активы, появившиеся за неделю | `Host.@CreationTime >= Now() - 7days` |

> [!note] Почему здесь нет `SeverityRating`
> По официальному документу `@Vulners.SeverityRating` **не поддерживается в динамических группах** — условие с ним сработает в конвейере, но не в группе. Поэтому критичные уязвимости в группах выбираются по `@Vulners.CVSS3Score >= 9`, а группу «Критичные активы» нельзя строить по `@Importance`: используйте `@Vulners.CVSS3Score` или признаки актива (`Host.HostType`, ОС, ПО).

> [!warning] Ограничения псевдонимов для динамических групп
> `@IMPORTANCE`, `@CUMULATIVEVULNERABILITY`, `@VULNERS.SCORE`, `@VULNERS.SEVERITYRATING`, `@VULNERPASSPORT.SCORE`, контекстные оценки и векторы CVSS, а также псевдонимы групп (`@GROUPS*`) в динамических группах **не поддерживаются**. Поэтому группу «Критичные активы» нельзя построить по `@Importance` — используйте `@Vulners.CVSS3Score` или признаки актива (`Host.HostType`, ОС, ПО).
> Полный список ограничений — в [[PDQL — синтаксис по документации PT]], раздел 6.
> Полный синтаксис конвейера — в [[4. Язык PDQL]].

## 5.4 Значимость активов

### Зачем нужна значимость

> [!important] Ключевой принцип
> Приоритизация уязвимостей напрямую зависит от значимости актива. Уязвимость CVSS 9.0 на тестовом стенде менее критична, чем уязвимость CVSS 7.0 на сервере с базой данных клиентов.

### Уровни значимости

| Уровень | Обозначение | Описание | Критичность |
| --- | --- | --- | --- |
| Высокая | **H** (High) | Критичные для бизнеса системы | Немедленное внимание |
| Средняя | **M** (Medium) | Важные, но заменяемые системы | Плановое устранение |
| Низкая | **L** (Low) | Вспомогательные системы | По возможности |
| Не определена | **ND** (Not Determined) | Значимость не назначена | Требует классификации |

> [!note] Названия в интерфейсе и в запросах
> В паспорте актива значимость отображается как **High / Medium / Low / Undefined**, в примерах запросов PDQL используются значения **H / M / L / ND** (см. [[Общие псевдонимы активов]]). Для новых активов значимость не определяется автоматически, поэтому она становится обязательным полем для классификации ([[Присвоение значимости активам]]).

### Методы присвоения значимости

#### Ручное присвоение

1. Главное меню → **Активы**, выбрать активы.
2. В панели инструментов нажать кнопку изменения значимости → окно **Изменение значимости <N> активов**.
3. Выбрать уровень значимости и нажать **Применить**.
4. Из карточки актива значимость задаётся кнопкой **Установить значимость** (или **Редактировать** → вкладка **Паспорт**).

**Недостаток:** не масштабируется при большом количестве активов.

#### Автоматическое через политику «Значимость активов»

> [!tip] Политика значимости
> Политика **«Значимость активов»** (раздел **Система → Политики**) — это набор правил, каждое из которых автоматически назначает значимость активам, соответствующим критериям. Создание правил — см. [[Создание правила для значимости активов]] и [[Страница «Политики»]].

**Пример правила:**

| Правило | Критерий | Значимость |
| --- | --- | --- |
| Серверы с БД | `Host.Softs.Name like '%SQL Server%'` | **H** |
| Контроллеры домена | `WindowsHost[HostRoles.Role = 'Domain Controller']` | **H** |
| Серверы Exchange | `Host.Softs.Name like '%Exchange%'` | **H** |
| Рабочие станции руководства | `WindowsHost` и пользовательское поле отдела = «Руководство» | **M** |
| Тестовые стенды | `Host.Fqdn like '%TEST%'` | **L** |
| Принтеры | `NetworkDeviceHost` и `@Devicetype` = принтер | **L** |

> [!note] Пример условия из документации
> В окне создания правила активы выбираются по отдельным активам, группам активов, динамическим группам и/или условию PDQL ([[Создание правила для значимости активов]]). Пример условия из документации: активы с общими критически важными ролями через запрос `Host.HostRoles.Role in ['DNS Server', 'Mail Server', 'DHCP Server']` — можно скопировать из стандартных запросов папки **Определение значимости** в панели **Запросы** на странице **Активы** ([[Настройка политик]]).

> [!warning] Не стройте условие на `@Importance`
> Критерий правила должен опираться на признаки актива — роль хоста, ПО, тип устройства, `@Vulners.CVSS3Score`. Справочник PDQL прямо указывает: «Псевдоним значимости не может использоваться для объединения активов в динамическую группу» ([[Общие псевдонимы активов]]); при этом в разделе «Настройка политик» приведён пример запроса динамической группы по `Host.@Importance` — документация противоречит сама себе, поэтому полагаться на `@Importance` в группах не стоит.

**Порядок создания правила:**

1. Главное меню → **Система → Политики** → политика **«Значимость активов»**.
2. Нажать **Создать правило** — настройка политик доступна только пользователям с правами администратора.
3. Указать название правила.
4. Выбрать активы: по отдельным активам, группам активов, динамическим группам и/или по PDQL-условию (кнопка **Вставить условие**).
5. Выбрать значимость в выпадающем списке.
6. Нажать **Сохранить**.
7. Нажать **Применить изменения** — до этого момента созданное правило не работает.

> [!note] Правила внутри политики
> Применение правил внутри политики происходит **согласно установленному порядку**, установленному при создании. Если в правилах есть ошибки, политика становится недействующей.

### Активы без назначенной значимости

> [!warning] Риск
> Активы без значимости не имеют приоритета. Уязвимости на них обрабатываются в последнюю очередь, что создаёт слепую зону.

**Как найти:**

- Стандартный запрос **«Значимость не задана»** из папки **Определение значимости** (панель **Запросы** на странице **Активы**).
- Значение состояния «не определена» в запросах — `ND` (в паспорте — `Undefined`).
- На дашборде «Управление уязвимостями» — виджет **Значимость активов**: он показывает общее число активов и количество активов, для которых значимость не указана.

> [!note] Ограничение `@IMPORTANCE`
> В справочнике PDQL указано, что псевдоним значимости **не может использоваться для объединения активов в динамическую группу** ([[Общие псевдонимы активов]]), поэтому поиск активов без значимости делается стандартным запросом или фильтром интерфейса, а не динамической группой.

Через PDQL можно оперировать только документированными значениями значимости:

```text
Filter(Host.@Importance in ['H', 'M'])
| Select(@Host, Host.Fqdn, Host.IpAddress, Host.@Importance)
```

> [!tip] Практический приём
> Разделите активы на две группы: те, что попали в фильтр по значимости `['H', 'M', 'L']`, и все остальные (`Host` минус первая группа). Второй набор и есть «без значимости». Либо заведите статическую группу и пополняйте её по итогам инвентаризации.

**Что делать:**
1. Найти активы без значимости (через фильтр интерфейса)
2. Проанализировать назначение каждого
3. Назначить значимость (вручную или через политику)
4. Настроить автоматическое назначение для новых активов — через политики значимости на признаках актива (роль, ПО, тип узла), а не через `@Importance`
