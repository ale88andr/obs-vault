## 1. Общие положения

### 1.1. Цель документа

Настоящий Регламент устанавливает порядок выявления, оценки, приоритизации и устранения уязвимостей в информационной инфраструктуре [Организация]. Регламент направлен на минимизацию рисков реализации угроз безопасности информации через эксплуатацию известных уязвимостей программного и аппаратного обеспечения.

### 1.2. Область применения

Регламент распространяется на все информационные системы, серверное и сетевое оборудование, рабочие станции и средства защиты информации, находящиеся в зоне ответственности [Организация], включая:

- Технологические процессы АСУ ТП
- Государственные информационные системы (ГИС) всех классов защищённости
- Информационные системы, подлежащие защите персональных данных (ИСПДн)
- Значимые объекты критической информационной инфраструктуры (КИИ)
- Облачные ресурсы (IaaS/PaaS/SaaS)
- Тестовые и desarrollo-среды с доступом к продуктивным данным

## 2. Термины и определения

| Термин | Определение |
| --- | --- |
| **Уязвимость** | Ошибка (совокупность ошибок) в реализации компонента информационной системы, которая может быть использована для нарушения политики безопасности |
| **CVSS** (Common Vulnerability Scoring System) | Методика оценки критичности уязвимостей, основанная на векторах атаки, воздействии и условиях эксплуатации. Используется версия 3.1 |
| **CVE** (Common Vulnerabilities and Exposures) | Международный реестр публично известных уязвимостей |
| **БДУ ФСТЭК** | База данных уязвимостей ФСТЭК России — основной национальный реестр уязвимостей |
| **BDU** (Bugtraq Database Unique) | Идентификатор уязвимости в БДУ ФСТЭК |
| **SLA** (Service Level Agreement) | Гарантированный уровень качества обслуживания — максимальный допустимый срок устранения уязвимости |
| **VM** (Vulnerability Management) | Процесс управления уязвимостями |
| **RACI** | Модель распределения ответственности: Responsible (исполнитель), Accountable (ответственный), Consulted (консультируемый), Informed (информируемый) |
| **MTTR** (Mean Time To Remediate) | Среднее время устранения уязвимости |
| **Компенсирующая мера** | Совокупность организационных и технических мер, снижающих риск эксплуатации уязвимости при невозможности её устранения |
| **Виртуальный патчинг** | Применение правил IPS/WAF для блокирования векторов эксплуатации уязвимости без внесения изменений в ПО |
| **Эксплойт** | Программная реализация уязвимости, используемая для проведения атаки |
| **Нулевая уязвимость (0-day)** | Уязвимость, не имеющая официального исправления на момент обнаружения |
| **Актив** | Любой информационный ресурс, обладающий ценностью для организации (система, данные, оборудование, услуга) |
| **Критичность актива** | Степень важности актива для деятельности организации, определяемая при классификации |
| **Верификация** | Процедура подтверждения факта устранения уязвимости путём повторного сканирования |

## 3. Организационная структура и роли

### 3.1. Определение ролей

В процессе управления уязвимостями участвуют следующие роли:

**3.1.1. Руководитель направления ИБ (CISO)**

Руководит процессом управления уязвимостями в целом. Утверждает приоритеты устранения, принимает решения об эскалации, подписывает отчёты для руководства. Имеет право инициировать внеплановое сканирование при получении информации о критической уязвимости (0-day). Утверждает компенсирующие меры при невозможности установки патча.

**3.1.2. Аналитик ИБ (VM-оператор)**

Проводит регулярное сканирование инфраструктуры, регистрирует уязвимости в системе учёта, выполняет оценку критичности по CVSS v3.1 с учётом контекста актива, формирует задачи на устранение для ИТ-подразделения, контролирует соблюдение SLA, проводит верификацию после устранения. Осуществляет мониторинг обновлений БДУ ФСТЭК не реже одного раза в сутки.

**3.1.3. Администратор ИТ**

Устанавливает обновления безопасности, применяет компенсирующие меры, обеспечивает доступ к системам для сканирования. При невозможности установки патча в срок — инициирует запрос на компенсирующую меру с обоснованием. Уведомляет аналитика ИБ о невозможности соблюдения SLA не позднее чем за 4 часа до истечения срока.

**3.1.4. Владелец системы**

Владеет рисками, связанными с уязвимостями в подконтрольной системе. Принимает решение о принятии риска при отклонении от SLA. Утверждает компенсирующие меры и план remediation для критических уязвимостей. Несёт ответственность за наличие ресурсов для устранения уязвимостей в установленные сроки.

**3.1.5. Руководство организации**

Контролирует исполнение регламента через регулярные отчёты. Утверждает стратегические решения по управлению рисками. Обеспечивает ресурсное сопровождение процесса.

### 3.2. RACI-матрица

| Этап процесса | CISO | Аналитик ИБ | Администратор ИТ | Владелец системы | Руководство |
| --- | --- | --- | --- | --- | --- |
| Мониторинг БДУ/CVE | A | R | I | I | I |
| Проведение сканирования | A | R | C | I | I |
| Верификация результатов сканирования | A | R | C | I | I |
| Оценка критичности (CVSS + контекст) | A | R | C | C | I |
| Приоритизация уязвимостей | R | C | C | C | I |
| Постановка задачи на устранение | I | R | I | A | I |
| Установка патча / обновления | I | I | R | A | I |
| Применение компенсирующих мер | A | R | R | C | I |
| Верификация устранения | A | R | C | I | I |
| Отчётность | R | R | I | I | A |
| Эскалация при срыве SLA | R | C | I | C | A |
| Принятие решения о принятии риска | A | C | I | R | I |

> **Ключевой принцип:** ИБ выявляет и приоритизирует, ИТ устраняет, владелец системы принимает риск при отклонении от SLA.

## 4. Классификация активов

### 4.1. Уровни критичности активов

Для расчёта SLA устранения уязвимостей все активы организации классифицируются по уровням критичности в соответствии с таблицей:

| Уровень критичности | Описание | Примеры активов |
| --- | --- | --- |
| **Критический** | Активы,whose компрометация ведёт к катастрофическим последствиям для деятельности организации, нарушению нормативных требований или угрозе жизни/здоровью людей | Продуктивные серверы с БД, содержащие ПДн; системы КИИ; ГИС 1 класса защищённости; внешний периметр (Web-серверы, шлюзы); серверы с критичными бизнес-процессами; АСУ ТП |
| **Высокий** | Активы,whose компрометация ведёт к серьёзному ущербу для организации или нарушению ключевых бизнес-процессов | Внутренние бизнес-системы (ERP, CRM); почтовые серверы; серверы аутентификации (AD/LDAP); серверы фоновых задач; ГИС 2 класса защищённости; ИСПДн 3 уровня |
| **Средний** | Активы,whose компрометация ведёт к ограниченному ущербу или затрагивает отдельные бизнес-процессы | Рабочие станции сотрудников; тестовые среды с доступом к продуктивным данным; серверы некритичных сервисов; сетевое оборудование внутренней сети |
| **Низкий** | Активы,whose компрометация ведёт к минимальному ущербу или изолированы от влияния на деятельность организации | Изолированные тестовые среды; лабораторные стенды; файловые серверы общего доступа без конфиденциальной информации |

### 4.2. Процедура присвоения критичности

1. При приобретении/вводе в эксплуатацию актива владелец системы заполняет форму классификации актива в системе учёта.
2. Аналитик ИБ присваивает уровень критичности на основе критериев из п. 4.1.
3. Критичность пересматривается при изменении конфигурации актива или при внедрении новых бизнес-процессов, но не реже 1 раза в год.
4. По умолчанию новый актив получает уровень критичности «Средний» до проведения классификации.

## 5. Выявление уязвимостей

### 5.1. Источники данных об уязвимостях

Процесс выявления уязвимостей основывается на следующих источниках:

| Источник | Описание | Периодичность проверки |
| --- | --- | --- |
| **БДУ ФСТЭК** | Основной российский реестр уязвимостей. Мониторинг обновлений обязателен для ГИС, ИСПДн и КИИ | Не реже 1 раза в сутки |
| **NVD (NIST) / CVE** | Международные базы данных уязвимостей. Используются для продуктов без записи в БДУ | Не реже 1 раза в сутки |
| **Бюллетени вендоров** | Официальные уведомления о уязвимостях (Microsoft Patch Tuesday, Oracle Critical Patch Update, Cisco Security Advisories и др.) | По графику публикации вендоров (как правило, ежемесячно) |
| **CERT-уведомления** | Рассылки ГосСОПКА и отраслевых CERT | По поступлении |

### 5.2. Внеплановые триггеры сканирования

Внеплановое сканирование инициируется при наступлении одного из следующих событий:

- Публикация критической уязвимости (CVSS ≥ 9.0) в БДУ ФСТЭК или NVD, затрагивающей используемые в организации продукты
- Обнаружение признаков эксплуатации уязвимости (indicators of compromise, эксплойты в открытом доступе)
- Изменение конфигурации критичного или высококритичного актива
- Инцидент информационной безопасности, связанный с эксплуатацией уязвимости
- Получение уведомления от ГосСОПКА, отраслевого CERT или вендора
- По решению CISO

### 5.3. Периодичность планового сканирования

| Категория актива | Плановое сканирование | Внеплановое (по триггерам) |
| --- | --- | --- |
| Критический (КИИ, ГИС 1 класса) | Еженедельно | При выходе критической уязвимости в БДУ/NVD |
| Высокий (внутренние системы) | Раз в 2 недели | При изменении конфигурации |
| Средний (рабочие станции) | Ежемесячно | По решению CISO |
| Низкий (изолированные стенды) | Ежеквартально | При инциденте |

### 5.4. Инструменты сканирования

В организации используются следующие инструменты для выявления уязвимостей:

| Инструмент | Назначение | Режим |
| --- | --- | --- |
| **MaxPatrol VM** | Комплексное сканирование серверов, рабочих станций, сетевого оборудования и веб-приложений | Автоматическое по расписанию + ручное по запросу |
| **RedCheck** | Сканирование веб-приложений и API | По расписанию + после каждого изменения кода |
| **ScanOVAL** | Бесплатный сканер ФСТЭК для проверки соответствия БДУ (для малых инфраструктур и ГИС) | По расписанию |
| **Средства мониторинга СУБД** | Проверка уязвимостей на уровне баз данных | Ежемесячно |

> **Примечание:** Для малых ГИС и объектов без коммерческого сканера допускается использование бесплатного ScanOVAL. Результаты сканирования (HTML-отчёт) импортируются в систему учёта уязвимостей.

### 5.5. Верификация результатов сканирования

Не все «находки» сканера являются реальными уязвимостями. Обязательная процедура верификации включает:

1. Аналитик ИБ анализирует результаты сканирования и исключает ложноположительные срабатывания.
2. Уязвимости с CVSS ≥ 9.0 подлежат ручному подтверждению до постановки задачи на устранение.
3. Для подтверждения проверяется доступность уязвимости (выполнимость вектора атаки в конкретной конфигурации), наличие эксплойта в открытом доступе, критичность затронутого актива.
4. Результаты верификации фиксируются в системе учёта с указанием статуса: «Подтверждена», «Ложноположительная», «Неактуальна».

## 6. Оценка и приоритизация

### 6.1. Методика оценки критичности

Оценка критичности уязвимостей проводится на основе следующих факторов:

**6.1.1. Базовая оценка CVSS v3.1**

Каждой уязвимости присваивается базовый балл по шкале CVSS v3.1:

| Категория | Диапазон баллов | Описание |
| --- | --- | --- |
| Критическая | 9.0 — 10.0 | Лёгкая эксплуатация, максимальное воздействие |
| Высокая | 7.0 — 8.9 | Эксплуатация возможна, серьёзное воздействие |
| Средняя | 4.0 — 6.9 | Ограниченная эксплуатация или воздействие |
| Низкая | 0.1 — 3.9 | Сложная эксплуатация, минимальное воздействие |

**6.1.2. Контекстуальная оценка**

Помимо базового балла CVSS, при приоритизации учитываются:

- Критичность затронутого актива (раздел 4)
- Наличие эксплойта в открытом доступе (повышает приоритет)
- Наличие активной эксплуатации в природе (повышает приоритет)
- Используется ли уязвимость в реальных атаках (по данным БДУ и CERT)
- Влияние на конфиденциальность, целостность и доступность (CIA)
- Роль актива в сети (доступность из внешней среды повышает приоритет)

**6.1.3. Итоговый приоритет**

Итоговый приоритет уязвимости определяется комбинацией CVSS и контекстуальной оценки. При равных баллах приоритет определяется критичностью актива.

### 6.2. Категории приоритетов

| Приоритет | Критерии | Действия |
| --- | --- | --- |
| **P1 — Критический** | CVSS ≥ 9.0 на критичном/высоком активе; наличие эксплойта; активная эксплуатация | Немедленная регистрация; задача на устранение в рамках SLA для критических уязвимостей; уведомление CISO |
| **P2 — Высокий** | CVSS 7.0–8.9 на критичном/высоком активе; CVSS ≥ 9.0 на среднем активе | Регистрация в течение 24 часов; задача в рамках SLA для высоких уязвимостей |
| **P3 — Средний** | CVSS 4.0–6.9 на активе любого уровня; CVSS 7.0–8.9 на низком активе | Регистрация в течение 3 рабочих дней; задача в рамках стандартного SLA |
| **P4 — Низкий** | CVSS 0.1–3.9 на активе любого уровня | Регистрация в плановом порядке; задача при наличии ресурсов |

## 7. SLA устранения

### 7.1. Требования регулятора

Если организация является оператором ГИС, ИСПДн или значимым объектом КИИ, SLA-матрица должна соответствовать приказам ФСТЭК:

**Приказ ФСТЭК № 239 (значимые объекты КИИ):**

- Критические уязвимости — **24 часа**
- Высокие уязвимости — **168 часов (7 дней)**
- Средние уязвимости — **720 часов (30 дней)**

**Приказ ФСТЭК № 559 (ГИС):**

- Критические уязвимости — **24 часа**
- Высокие уязвимости — **168 часов (7 дней)**

**Приказ ФСТЭК № 21 (ИСПДн):**

- Критические уязвимости — **72 часа**
- Прочие уязвимости — **720 часов (30 дней)**

> **Важно:** SLA организации не должны превышать сроки, установленные применимиым приказом ФСТЭК. Документ может предусматривать более строгие, но не мягче регуляторных требований.

### 7.2. SLA-матрица устранения

Максимально допустимые сроки устранения уязвимостей определяются в соответствии с Таблицей 1.

**Таблица 1 — SLA-матрица устранения уязвимостей**

| Критичность уязвимости (CVSS v3.1) | Критический актив | Высокий актив | Средний актив | Низкий актив |
| --- | --- | --- | --- | --- |
| **Критическая** (9.0–10.0) | 24 часа | 48 часов | 72 часа | 7 дней |
| **Высокая** (7.0–8.9) | 168 часов (7 дн.) | 7 дней | 14 дней | 21 день |
| **Средняя** (4.0–6.9) | 14 дней | 21 день | 30 дней | 60 дней |
| **Низкая** (0.1–3.9) | 30 дней | 60 дней | 90 дней | Следующее ТО |

### 7.3. Порядок исчисления SLA

- Отсчёт SLA начинается с момента первичной регистрации уязвимости в системе учёта (не с момента публикации в БДУ).
- При наличие применимого приказа ФСТЭК, SLA рассчитывается в соответствии с ним, если он строже, чем матрица из п. 7.2.
- SLA исчисляется в **рабочих часах** (для критических уязвимостей — в **календарных часах**, включая выходные и праздничные дни).

### 7.4. Дополнительные положения

- При невозможности устранения в установленный срок ответственный исполнитель обязан не позднее чем за **4 часа** до истечения SLA инициировать процедуру эскалации в соответствии с разделом 8 настоящего Регламента.
- Установка патча осуществляется в порядке, согласованном с процедурой управления изменениями. Для критических уязвимостей (P1) допускается упрощённый (ускоренный) порядок согласования Emergency Change.
- После устранения уязвимости проводится верификация (повторное сканирование) в течение **3 рабочих дней**.

## 8. Эскалация и компенсирующие меры

### 8.1. Порядок эскалации при срыве SLA

При невозможности устранения уязвимости в установленные сроки применяется следующая процедура эскалации:

| Уровень эскалации | Условие | Получатели уведомления | Действия |
| --- | --- | --- | --- |
| **1 уровень** | Превышение SLA на 25% | CISO, Аналитик ИБ | Анализ причин задержки; утверждение плана восстановления; ускорение работ |
| **2 уровень** | Превышение SLA на 50% | CTO, Владелец системы | Принятие решения о выделении дополнительных ресурсов; рассмотрение альтернативных мер |
| **3 уровень** | Превышение SLA на 100% | Руководство организации | Обязательное принятие риска; утверждение компенсирующих мер; фиксация решения |

### 8.2. Процедура эскалации

1. За **4 часа** до истечения SLA (или при невозможности устранения) администратор ИТ уведомляет аналитика ИБ с обоснованием.
2. Аналитик ИБ проводит первичную оценку и в случае необходимости инициирует 1 уровень эскалации.
3. Эскалация оформляется в системе учёта уязвимостей с указанием: причины задержки, предполагаемого срока устранения, предлагаемых компенсирующих мер.
4. На каждом уровне эскалации ответственный принимает решение и фиксирует его в системе учёта.
5. При наступлении 3 уровня эскалации обязательно заполняется Форма принятия риска.

### 8.3. Компенсирующие меры

Компенсирующие меры применяются, когда установка патча невозможна или нецелесообразна в установленные сроки. Допустимые компенсирующие меры:

| Мера | Описание | Примеры |
| --- | --- | --- |
| **Сегментация сети** | Изоляция уязвимого актива на уровне сетевой инфраструктуры | Перевод на отдельный VLAN; ограничение правил firewall; блокировка маршрутов |
| **Ограничение доступа** | Минимизация привилегий и отключение неиспользуемых сервисов | Отключение удалённого доступа; ограничение по IP; отключение ненужных сервисов; снижение уровня привилегий |
| **Усиленный мониторинг** | Дополнительные правила обнаружения на признаки эксплуатации | Создание правил SIEM; добавление логов в мониторинг; настройка алертов на индикаторы компрометации |
| **Виртуальный патчинг** | Применение правил IPS/WAF, блокирующих вектор эксплуатации | Создание сигнатур WAF; настройка правил IPS; блокировка HTTP-параметров |

### 8.4. Ограничения по компенсирующим мерам

- Компенсирующая мера **не отменяет** необходимость установки патча — она продлевает допустимый срок устранения на согласованный период.
- Срок действия компенсирующей меры фиксируется в системе учёта и согласовывается с CISO.
- Для объектов КИИ и ГИС срок действия компенсирующей меры не может превышать допустимого срока, установленного применимым приказом ФСТЭК.
- По истечении срока действия компенсирующей меры проводится повторная оценка: если патч по-прежнему невозможен, процедура эскалации повторяется.

## 9. Отчётность и метрики

### 9.1. Периодичность и формат отчётов

| Отчёт | Периодичность | Получатель | Содержание |
| --- | --- | --- | --- |
| Операционный дашборд | Ежедневно | Аналитик ИБ, CISO | Открытые уязвимости по приоритетам; просроченные SLA; статус критических задач |
| Еженедельный отчёт | Пятница, 17:00 | CISO, CTO | Динамика закрытия уязвимостей; топ-10 рисков; статус по критическим уязвимостям |
| Ежемесячный отчёт | 5-е число месяца | Руководство, аудит | MTTR; SLA compliance; покрытие сканирования; тренды; сводка по эскалациям |
| Квартальный обзор | По графику | Комитет ИБ | Сводный анализ; план улучшений; анализ повторяющихся уязвимостей |

### 9.2. Ключевые метрики эффективности

| Метрика | Описание | Целевое значение |
| --- | --- | --- |
| **SLA Compliance** | Доля уязвимостей, устранённых в установленные сроки | ≥ 95% |
| **MTTR (Mean Time To Remediate)** | Среднее время устранения уязвимости по критичностям | Критические: ≤ 24 ч; Высокие: ≤ 7 дн. |
| **Coverage (Покрытие сканирования)** | Доля активов, охваченных сканированием | ≥ 98% |
| **Backlog** | Количество незакрытых уязвимостей | Тренд снижения |
| **False Positive Rate** | Доля ложноположительных результатов сканирования | ≤ 15% |
| **Reopen Rate** | Доля уязвимостей, повторно открытых после закрытия | ≤ 5% |

### 9.3. Формы представления отчётов

Отчёты формируются на основе данных системы учёта уязвимостей и предоставляются в следующих формах:

- **Операционный дашборд** — интерактивный дашборд в системе учёта или SGRC-платформе.
- **Еженедельный отчёт** — документ в формате PDF/Excel, включая таблицы и графики динамики.
- **Ежемесячный отчёт** — развёрнутый документ с анализом трендов, получателям направляется по электронной почте и хранится в системе управления документами.
- **Квартальный обзор** — презентация для Комитета ИБ с выводами и рекомендациями.

### 9.4. Хранение отчётов

Все отчёты хранятся в системе управления документами в течение **не менее 3 лет** с момента формирования. Доступ к отчётам осуществляется в соответствии с политикой доступа организации.

## 10. Порядок пересмотра

### 10.1. Плановый пересмотр

Настоящий Регламент подлежит плановому пересмотру **не реже 1 раза в год** с целью:

- Актуализации нормативных ссылок и требований ФСТЭК
- Корректировки SLA-матрицы на основе накопленных метрик
- Внесения изменений в инструменты и источники данных
- Уточнения ролей и RACI-матрицы

### 10.2. Внеплановый пересмотр

Внеплановый пересмотр проводится при наступлении одного из следующих событий:

- Вступление в силу нового приказа ФСТЭК, изменяющего требования к управлению уязвимостями
- Инцидент ИБ, связанный с эксплуатацией уязвимости, выявивший недостатки регламента
- Значительные изменения в ИТ-инфраструктуре (миграция, внедрение новых систем)
- По решению руководства организации или CISO

### 10.3. Процедура пересмотра

1. Аналитик ИБ инициирует пересмотр и формирует предложения по изменениям.
2. CISO рассматривает предложения и утверждает проект изменений.
3. Проект согласовывается с владельцами систем и ИТ-подразделением.
4. Изменения утверждаются руководством организации.
5. Обновлённый Регламент вступает в силу с даты, указанной в приказе об утверждении.
6. Все сотрудники, участвующие в процессе VM, знакомятся с изменениями в течение **5 рабочих дней** с момента вступления в силу.

## Приложение A. Чек-лист полноты регламента

Перед утверждением регламента необходимо проверить каждый пункт:

### Общая часть

- [ ] Указаны цели и область применения документа
- [ ] Перечислены нормативные ссылки (ФСТЭК, ISO, внутренние документы)
- [ ] Определены термины и сокращения (CVSS, SLA, VM, RACI, БДУ)
- [ ] Указана дата вступления в силу и порядок ознакомления

### Организация процесса

- [ ] Определены все роли участников процесса
- [ ] Составлена RACI-матрица для каждого этапа
- [ ] Описана классификация активов по критичности (минимум 3–4 уровня)
- [ ] Указана периодичность сканирования для каждой категории активов

### SLA и эскалация

- [ ] SLA-матрица «критичность уязвимости × критичность актива» заполнена
- [ ] Определён момент начала отсчёта SLA
- [ ] Описан порядок эскалации при срыве SLA (3+ уровня)
- [ ] Определены допустимые компенсирующие меры и срок их действия

### Процедуры

- [ ] Описан порядок выявления (сканеры, ручной мониторинг, БДУ/CVE)
- [ ] Описана процедура оценки и приоритизации (CVSS + контекст)
- [ ] Описан порядок устранения (патч, компенсирующая мера, принятие риска)
- [ ] Описана процедура верификации (повторное сканирование, закрытие тикета)

### Отчётность и контроль

- [ ] Определены метрики эффективности (MTTR, SLA compliance, покрытие)
- [ ] Указана периодичность и получатели каждого типа отчёта
- [ ] Определён порядок планового пересмотра (не реже 1 раза в год)
- [ ] Предусмотрен лист регистрации изменений документа
