# Автоматические задачи MaxPatrol VM: сбор активов, аудит и пентест

> [!important] Главный принцип
> Автоматизация в MaxPatrol VM — это связка из трёх слоёв: **задач сканирования** (что и когда собираем), **политик** (как данные превращаются в процесс) и **интеграций** (откуда данные и куда уходят уведомления). Только вместе они превращают систему из «сканера» в «систему управления».
>
> Связанные заметки: [[6. Автоматизация и политики]], [[3. Сбор данных и сканирование]], [[4. Язык PDQL]], [[8. Контроль соответствия и HCC]]. Готовые запросы для всех динамических групп — в [[Приложение: PDQL-запросы для динамических групп]] в конце файла.

---

## Слой 0. Фундамент — сначала, до создания задач

Прежде чем создавать задачи, настройте три вещи, иначе автоматика будет собирать мусор:

- **Учётные записи** — отдельные, минимальных привилегий, свои на Windows / Linux / сетевое оборудование / СУБД. Ключевой факт: у рабочей станции Windows обычно 500–1000 уязвимостей, а Discovery без учёток даёт в 10–100 раз меньше данных, чем Audit с учётками.
- **Группы активов** — статические и динамические по PDQL (например `@WindowsHost and WindowsHost.HostType = 'Server'`). На них привязываются все политики и задачи.
- **Политики значимости (H/M/L/ND)** — чтобы критичные активы (контроллеры домена, СУБД, файрволы, Exchange) получали приоритет автоматически. Без этого «просрочка» и эскалация считаются неверно.

## Блок 1. Сбор активов (инвентаризация)

> [!note] Цель
> Держать актуальный список «что вообще есть в сети», включая теневые IT и новые узлы, чтобы ни один актив не стал слепой зоной.

| Задача | Тип | Группа / цели | Профиль | Расписание | Приоритет |
| --- | --- | --- | --- | --- | --- |
| Discovery по всей сети | Discovery | Все IP-диапазоны компании | Discovery top-1000 портов | Еженедельно (напр. суббота) | Низкий |
| Синхронизация Active Directory | Импорт | Домен | LDAP/LDAPS | Ежедневно | Высокий |
| Импорт гипервизоров | Импорт | VMware vCenter / Hyper-V | HTTPS API / WMI | Ежедневно | Высокий |
| Обнаружение новых (ND) активов | Audit ❲базовый❳ | Группа «ND-значимость» | Базовый | Ежедневно | Высокий |

**Почему так:**

- Discovery без учёток — это «обзор»: видит только открытые сервисы, не видит установленное ПО, реестр и патчи. Его роль — поиск теневых узлов и сегментов, недоступных аудиту.
- Полноценные данные об активах дают **импорт из AD/гипервизоров** (не дублируем то, что уже есть в CMDB) и **ежедневный аудит новых неклассифицированных активов** — быстро вводим их в процесс, пока они не стали слепой зоной.

### Детализация параметров задач сбора данных

> [!note] Модель параметров задачи
> Любая задача сканирования создаётся по единому шаблону (см. [[3. Сбор данных и сканирование]]): **Название → Тип → Цели → Профиль → Учётные записи → Расписание → Приоритет**. Ниже — конкретные значения по каждой задаче сбора активов.

#### Задача 1. «Discovery по всей сети»

| Параметр       | Значение                                   | Пояснение                                              |
| -------------- | ------------------------------------------ | ------------------------------------------------------ |
| Название       | Discovery по всей сети                     | Понятное имя, отражающее назначение                    |
| Тип задачи     | Discovery                                  | Чёрный ящик, без учётных данных                        |
| Цели           | Все IP-диапазоны компании                  | Перечислить все подсети (или импортировать из AD/CMDB) |
| Профиль        | Discovery top-1000 портов                  | Только открытые сервисы без глубокого анализа          |
| Порты          | Стандартный набор top-1000                 | TCP-скан; UDP — по необходимости                       |
| Скорость       | Нормальная                                 | Влияет на нагрузку на сеть                             |
| Учётные записи | Не требуются                               | Discovery не аутентифицируется                         |
| Модули         | TCP-скан, UDP-скан, banner grabbing        | Определение ОС/сервисов по ответам                     |

| Параметр | Значение | Пояснение |
| --- | --- | --- |
| Название | Синхронизация Active Directory | — |
| Тип задачи | Импорт (интеграция) | Не скан, а импорт из внешнего источника |
| Источник | Домен | LDAP/LDAPS |

| Расписание | Ежедневно | Структура меняется постоянно |

| Особенности | Импортированные группы → основа динамических групп | Не дублировать скан того, что уже в AD |

| --- | --- | --- |

| Цели | Гипервизоры и их ВМ | Виртуальные машины, конфигурации |
| Учётные записи | Администратор гипервизора (отдельная) | Права чтения |
| Расписание | Ежедневно | Автообнаружение новых ВМ |
| Приоритет | Высокий | Контроль несанкционированных ВМ |
| Особенности | Средняя глубина, минимальная нагрузка | Используйте вместо повторного сканирования ВМ |

#### Задача 4. «Обнаружение новых (ND) активов»

| Параметр | Значение | Пояснение |
| --- | --- | --- |
| Название | Аудит новых неклассифицированных активов | — |
| Тип задачи | Audit (базовый) | С учётными данными, но облегчённый |
| Цели | Группа «ND-значимость» | Активы, у которых значимость не определена |
| Профиль | Базовый (Default) | Минимальный набор проверок |
| Учётные записи | Стандартные для сканирования | Windows/Linux/сетевое |
| Расписание | Ежедневно | Быстрый ввод новых узлов в процесс |
| Приоритет | Высокий | Пока актив не классифицирован — он потенциальный риск |
| Ожидания | Поверхностный аудит достаточен | Глубокий — на ежемесячном этапе по значимости |
| Действие после | Политика значимости назначает H/M/L | ND-активы перетекают в нужную группу |

> [!tip] Правило нагрузки
> Задачи сбора активов не должны пересекаться по времени с аудитом: Discovery в субботу, импорты — ранним утром или ночью, аудит новых ND — в воскресенье. Это снижает нагрузку на сеть и Collector'ы.

## Блок 2. Аудит (регулярная оценка уязвимостей и конфигураций)

| Задача | Тип | Группа | Профиль | Расписание | Приоритет |
| --- | --- | --- | --- | --- | --- |
| Полный аудит критичных серверов (H) | Audit | «Критичные серверы» | Windows/Linux Server Full | Еженедельно | Высокий |
| Аудит серверов M/L | Audit | Остальные серверы | Стандартный | Ежемесячно | Нормальный |
| Аудит рабочих станций | Audit | Windows WS | Базовый | Ежемесячно | Нормальный |
| Аудит сетевого оборудования | Audit | Network devices | Специализированный (Cisco/FortiGate) | Ежемесячно | Нормальный |
| Аудит СУБД | Audit | Серверы БД | Database Server | Ежемесячно | Высокий |
| Аудит гипервизоров | Audit | VMware/Hyper-V | VMware ESXi | Ежемесячно | Высокий |

**Принципы оптимальности:**

- **Не сканировать всё одинаково.** Разные группы — разная частота: критичные — каждую неделю, остальное — раз в месяц. Снижает нагрузку на сеть и Collector'ы.
- **Разнести по дням/часам**, не запускать все политики разом. Пример недели:

| День | Время | Политика / задача |
| --- | --- | --- |
| Понедельник | 02:00 | Критичные серверы |
| Вторник | 02:00 | Серверы M/L |
| Среда | 02:00 | Сетевое оборудование |
| Четверг | 02:00 | Рабочие станции |
| Пятница | — | Выходной |
| Суббота | 02:00 | Discovery по всей сети |
| Воскресенье | 02:00 | Новые активы (ND) |

- **Классифицировать просрочку:** статус «Просрочена» с эскалацией по критичности настраивается политикой обработки, а не вручную.

> [!note] Общие параметры Audit-задачи
> Audit — «белый ящик» с учётными данными. Глубина результата прямо зависит от привилегий учётной записи: «чтение» покажет установленное ПО, полные привилегии — конфигурации и политики. Все Audit-задачи привязываются к отдельной учётной записи под каждый тип системы.

## Блок 3. Пентест (имитация атак, чёрный ящик с агрессивными проверками)

> [!warning] Аудит ≠ пентест
> Аудит — это «белый ящик» с учётными данными: есть ли патчи, как настроены конфигурации. Пентест — проверка exploitable-состояния «снаружи», без учёток, профилем с агрессивными эвристиками (PT Essentials и продвинутые набора проверок из опыта пентеста Positive).

| Задача | Тип | Группа / цели | Профиль | Расписание | Приоритет |
| --- | --- | --- | --- | --- | --- |
| Пентест критичных серверов | Пентест / чёрный ящик | «Критичные серверы» | PT Essentials + агрессивные проверки | Еженедельно (или раз в 2 недели) | Высокий |
| Пентест периметра / DMZ | Пентест | Внешний периметр, публичные сервисы | Пентест-профиль периметра | Ежемесячно | Высокий |
| Пентест веб-/прикладных сервисов | Пентест | Web/API-группы | Профиль типа PT Application | Ежемесячно | Нормальный |
| Пентест инфраструктуры (обходной) | Пентест | Все активы (фоновый) | Базовая агрессивная проверка | Ежеквартально | Низкий |

**Почему пентесту нужен отдельный слой:**

- **Другая свежесть данных.** Для пентеста результаты устаревают быстрее: срок актуальности 7 дней у пентеста против 30 у аудита. Пентест-задачи должны перезапускаться минимум еженедельно на критичных активах.
- **Агрессивные проверки нагружают сеть и цели** — их нельзя делать каждый день по всему периметру. Основная массовая частота — раз в неделю/месяц, полный обход — реже.
- **Профиль пентеста ≠ профиль аудита.** Не смешивайте: аудит читает, пентест «атакует». Держите их как отдельные задачи с отдельными профилями, чтобы не раздувать длительность и не ловить ложные срабатывания на «мягких» проверках.

## Слой сопровождения — политики, делающие систему оптимальной

Отдельно от задач — автоматические **политики**, иначе задача соберёт данные, но не поднимет процесс:

1. **Политики значимости** — автоприсвоение H/M/L по PDQL (контроллеры домена, СУБД, файрволы → H; рабочие станции → L; тестовые стенды → L и т.д.).
2. **Политики обработки уязвимостей** — автопризначение статусов и сроков:
   - «Патчинг Windows-серверов» — `HasFix = true`, срок 1 месяц от даты публикации CVE;
   - «Патчинг рабочих станций» — срок 2 месяца;
   - «Уязвимости без фикса» — `HasFix = false` → ручной анализ;
   - исключения для тестового сегмента — осознанный приём риска.
3. **Политики актуальности данных** — пентест 7 дней, критичные серверы 30, остальные 60–90 дней; действие — уведомление + автоскан при устаревании. Страховка от «слепых зон».
4. **Интеграции** — VM→SIEM для корреляции, VM→ITSM для заявок на устранение, AD для синхронизации. Без них собранные уязвимости не доходят до владельца актива.

# Приложение: PDQL-запросы для динамических групп

> [!tip] Как создать динамическую группу
> **Активы → Группы → Создать группу → Динамическая** → вставить PDQL-запрос. Группа автоматически пересчитывается при каждом обновлении данных.
>
> Синтаксис группы — это `@Алиас and <условие>` (без конвейера `|`). Если запрос нужен для анализа/отчёта, используйте полную форму с `select(...) | filter(...)`.

## Группы для сбора активов (Блок 1)

| Группа | PDQL-запрос (динамическая группа) | Назначение |
| --- | --- | --- |
| Неклассифицированные (ND) | `@Host and Host.@Importance = 'ND'` | Ежедневный аудит новых/неклассифицированных активов; ввод в процесс |
| Компьютеры из домена | `@ActiveDirectory` | Импорт структуры OU, компьютеров, пользователей |
| Серверы VMware | `@Host and (Host.OsName contains 'VMware ESXi' or Host.Softs.Name contains 'VMware ESXi')` | Импорт/аудит гипервизоров |

## Группы для аудита (Блок 2)

| Группа | PDQL-запрос (динамическая группа) | Назначение |
| --- | --- | --- |
| Критичные серверы (H) | `(@WindowsHost and WindowsHost.HostType = 'Server' or @UnixHost) and Host.@Importance = 'H'` | Еженедельный полный аудит |
| Остальные серверы (M/L) | `(@WindowsHost and WindowsHost.HostType = 'Server' or @UnixHost) and Host.@Importance in ('M','L')` | Ежемесячный стандартный аудит |
| Рабочие станции Windows | `@WindowsHost and WindowsHost.HostType = 'Desktop'` | Ежемесячный базовый аудит |
| Сетевое оборудование | `@NetworkDeviceHost` | Ежемесячный аудит коммутаторов/роутеров/МЭ |
| Серверы СУБД | `@Host and (Host.Softs.Name contains 'SQL Server' or Host.Softs.Name contains 'PostgreSQL' or Host.Softs.Name contains 'Oracle')` | Ежемесячный аудит баз данных |
| Все активы | `@Host` | Общая цель для фоновых/обходных задач |

## Группы для пентеста (Блок 3)

| Группа | PDQL-запрос (динамическая группа) | Назначение |
| --- | --- | --- |
| Критичные цели пентеста | `@Host and Host.@Importance = 'H'` | Еженедельный пентест |
| Периметр / DMZ | `@Host and Host.IpAddress in 172.16.0.0/16` *(замените на вашу подсеть)* | Ежемесячный пентест периметра |
| Web/API-сервисы | `@Host and (Host.Softs.Name contains 'IIS' or Host.Softs.Name contains 'Apache' or Host.Softs.Name contains 'Nginx')` | Ежемесячный пентест прикладного слоя |
| Тестовые стенды | `@Host and Host.Name contains 'TEST'` | Исключение тестового сегмента; сканирование по требованию |

## Группы для политик значимости (Слой 0/сопровождение)

Эти же PDQL-условия используются как **фильтры политик значимости** (автоприсвоение H/M/L):

| Политика значимости | PDQL-фильтр активов | Значимость | Приоритет |
| --- | --- | --- | --- |
| Контроллеры домена | `Host.HostRoles.Role = 'Domain Controller'` | H | 1 |
| Серверы с БД | `Host.Softs.Name like '%SQL Server%' or Host.Softs.Name like '%PostgreSQL%' or Host.Softs.Name like '%Oracle%'` | H | 1 |
| Межсетевые экраны | `NetworkDeviceHost.HostRoles.Role = 'Firewall'` | H | 1 |
| Серверы Exchange | `Host.Softs.Name like '%Exchange%'` | H | 1 |
| Маршрутизаторы | `NetworkDeviceHost.HostRoles.Role = 'Router'` | M | 2 |
| Коммутаторы | `NetworkDeviceHost.HostRoles.Role = 'Switch'` | M | 2 |
| Рабочие станции | `WindowsHost.HostType = 'Desktop'` | L | 3 |
| Принтеры | `NetworkDeviceHost.Type = 'Printer'` | L | 3 |
| Тестовые стенды | `Host.Name contains 'TEST'` | L | 3 |

> [!note] Приоритет политик значимости
> Если актив попадает под несколько политик, побеждает политика с **наименьшим** номером приоритета (1 > 2 > 3). При равных приоритетах — политика, созданная позже.

## Полезные запросы для мониторинга

Не для групп, но для дашбордов и контроля процесса:

- **Активы, не сканировавшиеся более 30 дней** (слепые зоны):
  ```sql
  select(@Host, Host.@LastAuditTime, Host.Fqdn) | filter(Host.@LastAuditTime < days(-30))
  ```
- **Новые активы за 7 дней**:
  ```sql
  select(@Host, Host.@CreationTime, Host.Fqdn, Host.IpAddress) | filter(Host.@CreationTime > days(-7))
  ```
- **Критичные уязвимости на критичных активах**:
  ```sql
  select(@Host, Host.Fqdn, Host.@Importance, Host.@Vulners) | filter(Host.@Importance = 'H' and Host.@Vulners[@Vulners.Severity = 'Critical'])
  ```
- **Уязвимости с эксплойтами (CVSS ≥ 7)**:
  ```sql
  select(@VulnerPassport, VulnerPassport.CVEs, VulnerPassport.Name, VulnerPassport.Score, VulnerPassport.HasExploit) | filter(VulnerPassport.HasExploit = true and VulnerPassport.Score >= 7) | sort(VulnerPassport.Score DESC)
  ```

## Чек-лист внедрения

- [ ] Настроены отдельные учётные записи для сканирования (Windows, Linux, сетевое, СУБД) и проверено подключение.
- [ ] Созданы группы активов (статические + динамические по PDQL).
- [ ] Настроены политики значимости (H/M/L/ND), ND-активы классифицируются.
- [ ] Созданы задачи сбора активов (Discovery + импорт AD/гипервизоров + ND-аудит).
- [ ] Созданы задачи аудита по группам с разной частотой.
- [ ] Созданы задачи пентеста с отдельными (агрессивными) профилями.
- [ ] Задачи разнесены по дням/часам, чтобы не перегружать сеть и Collector'ы.
- [ ] Настроены политики обработки уязвимостей (патчинг, исключения, без фикса).
- [ ] Настроены политики актуальности данных (7–30–90 дней по типам).
- [ ] Настроены интеграции SIEM / ITSM / AD.
- [ ] Настроены дашборды и уведомления о просрочках с эскалацией по критичности.
