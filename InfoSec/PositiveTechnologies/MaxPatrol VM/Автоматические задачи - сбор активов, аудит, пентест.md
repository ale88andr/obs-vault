# Автоматические задачи MaxPatrol VM: сбор активов, аудит и пентест

> [!important] Главный принцип
> Автоматизация в MaxPatrol VM — это связка из трёх слоёв: **задач сканирования** (что и когда собираем), **политик** (как данные превращаются в процесс) и **интеграций** (откуда данные и куда уходят уведомления). Только вместе они превращают систему из «сканера» в «систему управления».
>
> Связанные заметки: [[6. Автоматизация и политики]], [[3. Сбор данных и сканирование]], [[8. Контроль соответствия и HCC]].

---

## Слой 0. Фундамент — сначала, до создания задач

Прежде чем создавать задачи, настройте три вещи, иначе автоматика будет собирать мусор:

- **Учётные записи** — отдельные, минимальных привилегий, свои на Windows / Linux / сетевое оборудование / СУБД. Ключевой факт: у рабочей станции Windows обычно 500–1000 уязвимостей, а Discovery без учёток даёт в 10–100 раз меньше данных, чем Audit с учётками.
- **Группы активов** — статические и динамические по PDQL (например `@WindowsHost and WindowsHost.HostType = 'Server'`). На них привязываются все политики и задачи.
- **Политики значимости (H/M/L/ND)** — чтобы критичные активы (контроллеры домена, СУБД, файрволы, Exchange) получали приоритет автоматически. Без этого «просрочка» и эскалация считаются неверно.

## Блок 1. Сбор активов (инвентаризация)

> [!note] Цель
> Держать актуальный список «что вообще есть в сети», включая теневые IT и новые узлы, чтобы ни один актив не стал слепой зоной.

| Задача | Тип | Группа / цели | Профиль | Расписание | Приоритет |
| --- | --- | --- | --- | --- | --- |
| Discovery по всей сети | Discovery | Все IP-диапазоны компании | Discovery top-1000 портов | Еженедельно (напр. суббота) | Низкий |
| Синхронизация Active Directory | Импорт | Домен | LDAP/LDAPS | Ежедневно | Высокий |
| Импорт гипервизоров | Импорт | VMware vCenter / Hyper-V | HTTPS API / WMI | Ежедневно | Высокий |
| Обнаружение новых (ND) активов | Audit ❲базовый❳ | Группа «ND-значимость» | Базовый | Ежедневно | Высокий |

**Почему так:**

- Discovery без учёток — это «обзор»: видит только открытые сервисы, не видит установленное ПО, реестр и патчи. Его роль — поиск теневых узлов и сегментов, недоступных аудиту.
- Полноценные данные об активах дают **импорт из AD/гипервизоров** (не дублируем то, что уже есть в CMDB) и **ежедневный аудит новых неклассифицированных активов** — быстро вводим их в процесс, пока они не стали слепой зоной.

## Блок 2. Аудит (регулярная оценка уязвимостей и конфигураций)

| Задача | Тип | Группа | Профиль | Расписание | Приоритет |
| --- | --- | --- | --- | --- | --- |
| Полный аудит критичных серверов (H) | Audit | «Критичные серверы» | Windows/Linux Server Full | Еженедельно | Высокий |
| Аудит серверов M/L | Audit | Остальные серверы | Стандартный | Ежемесячно | Нормальный |
| Аудит рабочих станций | Audit | Windows WS | Базовый | Ежемесячно | Нормальный |
| Аудит сетевого оборудования | Audit | Network devices | Специализированный (Cisco/FortiGate) | Ежемесячно | Нормальный |
| Аудит СУБД | Audit | Серверы БД | Database Server | Ежемесячно | Высокий |
| Аудит гипервизоров | Audit | VMware/Hyper-V | VMware ESXi | Ежемесячно | Высокий |

**Принципы оптимальности:**

- **Не сканировать всё одинаково.** Разные группы — разная частота: критичные — каждую неделю, остальное — раз в месяц. Снижает нагрузку на сеть и Collector'ы.
- **Разнести по дням/часам**, не запускать все политики разом. Пример недели:

| День | Время | Политика / задача |
| --- | --- | --- |
| Понедельник | 02:00 | Критичные серверы |
| Вторник | 02:00 | Серверы M/L |
| Среда | 02:00 | Сетевое оборудование |
| Четверг | 02:00 | Рабочие станции |
| Пятница | — | Выходной |
| Суббота | 02:00 | Discovery по всей сети |
| Воскресенье | 02:00 | Новые активы (ND) |

- **Классифицировать просрочку:** статус «Просрочена» с эскалацией по критичности настраивается политикой обработки, а не вручную.

## Блок 3. Пентест (имитация атак, чёрный ящик с агрессивными проверками)

> [!warning] Аудит ≠ пентест
> Аудит — это «белый ящик» с учётными данными: есть ли патчи, как настроены конфигурации. Пентест — проверка exploitable-состояния «снаружи», без учёток, профилем с агрессивными эвристиками (PT Essentials и продвинутые набора проверок из опыта пентеста Positive).

| Задача | Тип | Группа / цели | Профиль | Расписание | Приоритет |
| --- | --- | --- | --- | --- | --- |
| Пентест критичных серверов | Пентест / чёрный ящик | «Критичные серверы» | PT Essentials + агрессивные проверки | Еженедельно (или раз в 2 недели) | Высокий |
| Пентест периметра / DMZ | Пентест | Внешний периметр, публичные сервисы | Пентест-профиль периметра | Ежемесячно | Высокий |
| Пентест веб-/прикладных сервисов | Пентест | Web/API-группы | Профиль типа PT Application | Ежемесячно | Нормальный |
| Пентест инфраструктуры (обходной) | Пентест | Все активы (фоновый) | Базовая агрессивная проверка | Ежеквартально | Низкий |

**Почему пентесту нужен отдельный слой:**

- **Другая свежесть данных.** Для пентеста результаты устаревают быстрее: срок актуальности 7 дней у пентеста против 30 у аудита. Пентест-задачи должны перезапускаться минимум еженедельно на критичных активах.
- **Агрессивные проверки нагружают сеть и цели** — их нельзя делать каждый день по всему периметру. Основная массовая частота — раз в неделю/месяц, полный обход — реже.
- **Профиль пентеста ≠ профиль аудита.** Не смешивайте: аудит читает, пентест «атакует». Держите их как отдельные задачи с отдельными профилями, чтобы не раздувать длительность и не ловить ложные срабатывания на «мягких» проверках.

## Слой сопровождения — политики, делающие систему оптимальной

Отдельно от задач — автоматические **политики**, иначе задача соберёт данные, но не поднимет процесс:

1. **Политики значимости** — автоприсвоение H/M/L по PDQL (контроллеры домена, СУБД, файрволы → H; рабочие станции → L; тестовые стенды → L и т.д.).
2. **Политики обработки уязвимостей** — автопризначение статусов и сроков:
   - «Патчинг Windows-серверов» — `HasFix = true`, срок 1 месяц от даты публикации CVE;
   - «Патчинг рабочих станций» — срок 2 месяца;
   - «Уязвимости без фикса» — `HasFix = false` → ручной анализ;
   - исключения для тестового сегмента — осознанный приём риска.
3. **Политики актуальности данных** — пентест 7 дней, критичные серверы 30, остальные 60–90 дней; действие — уведомление + автоскан при устаревании. Страховка от «слепых зон».
4. **Интеграции** — VM→SIEM для корреляции, VM→ITSM для заявок на устранение, AD для синхронизации. Без них собранные уязвимости не доходят до владельца актива.

## Чек-лист внедрения

- [ ] Настроены отдельные учётные записи для сканирования (Windows, Linux, сетевое, СУБД) и проверено подключение.
- [ ] Созданы группы активов (статические + динамические по PDQL).
- [ ] Настроены политики значимости (H/M/L/ND), ND-активы классифицируются.
- [ ] Созданы задачи сбора активов (Discovery + импорт AD/гипервизоров + ND-аудит).
- [ ] Созданы задачи аудита по группам с разной частотой.
- [ ] Созданы задачи пентеста с отдельными (агрессивными) профилями.
- [ ] Задачи разнесены по дням/часам, чтобы не перегружать сеть и Collector'ы.
- [ ] Настроены политики обработки уязвимостей (патчинг, исключения, без фикса).
- [ ] Настроены политики актуальности данных (7–30–90 дней по типам).
- [ ] Настроены интеграции SIEM / ITSM / AD.
- [ ] Настроены дашборды и уведомления о просрочках с эскалацией по критичности.
