# Автоматические задачи MaxPatrol VM: сбор активов, аудит и пентест

> [!important] Главный принцип
> Автоматизация в MaxPatrol VM — это связка из трёх слоёв: **задач сканирования** (что и когда собираем), **политик** (как данные превращаются в процесс) и **интеграций** (откуда данные и куда уходят уведомления). Только вместе они превращают систему из «сканера» в «систему управления».
>
> Связанные заметки: [[6. Автоматизация и политики]], [[3. Сбор данных и сканирование]], [[4. Язык PDQL]], [[8. Контроль соответствия и HCC]]. Готовые запросы для всех динамических групп — в разделе «Приложение: PDQL-запросы для динамических групп» в конце файла.

## Слой 0. Фундамент — сначала, до создания задач

Прежде чем создавать задачи, настройте три вещи, иначе автоматика будет собирать мусор:

- **Учётные записи** — отдельные, минимальных привилегий, свои на Windows / Linux / сетевое оборудование / СУБД. Создаются на странице **Сбор данных** → **Учетные записи** (типы: «логин — пароль», «пароль», «сертификат», LAPS). Ключевой факт: у рабочей станции Windows обычно 500–1000 уязвимостей, а чёрный ящик без учёток даёт в 10–100 раз меньше данных, чем Audit с учётками.
- **Группы активов** — статические и динамические по PDQL (например `WindowsHost and Host.HostType = 'Server'`). На них привязываются все политики и задачи. Страница **Активы** → панель **Группы**.
- **Политики значимости (H/M/L/ND)** — чтобы критичные активы (контроллеры домена, СУБД, файрволы, Exchange) получали приоритет автоматически. Политики настраиваются на странице **Система** → **Политики** → политика **Значимость активов** (см. [[Настройка политик]]). Без этого «просрочка» и эскалация считаются неверно.

## Блок 1. Сбор активов (инвентаризация)

> [!note] Цель
> Держать актуальный список «что вообще есть в сети», включая теневые IT и новые узлы, чтобы ни один актив не стал слепой зоной.

| Задача | Тип задачи | Группа / цели | Профиль | Расписание | Приоритет |
| --- | --- | --- | --- | --- | --- |
| Поиск активов по всей сети | Сбор данных (модуль HostDiscovery) | Все IP-диапазоны / подсети компании | HostDiscovery | Еженедельно (напр. суббота) | Низкий |
| Данные Active Directory | Сбор данных (модуль Audit) | Контроллеры домена | Windows DC Audit / Microsoft Active Directory Audit | Ежедневно | Высокий |
| Данные гипервизоров | Сбор данных (модуль Audit) | VMware ESXi / Microsoft Hyper-V | Пользовательский профиль аудита гипервизора | Ежедневно | Высокий |
| Обнаружение новых (ND) активов | Сбор данных (модуль Audit) | Группа «ND» / **Unmanaged hosts** | Быстрый аудит (напр. Windows Updates Discovery) | Ежедневно | Высокий |

**Почему так:**

- HostDiscovery без учёток — это «обзор»: видит только открытые сервисы, не видит установленное ПО, реестр и патчи и **не ищет уязвимости**. Его роль — поиск теневых узлов и сегментов, недоступных аудиту (см. [[Первый поиск активов модулем HostDiscovery]]).
- Полноценные данные об активах дают **аудит контроллеров домена и гипервизоров** (не дублируем то, что уже есть в AD/CMDB) и **ежедневный аудит новых неклассифицированных активов** — быстро вводим их в процесс, пока они не стали слепой зоной.

> [!important] Задачи-«импортеры» в MaxPatrol VM 2.8
> Отдельной задачи «Импорт из AD/гипервизоров» в 2.8 нет. Данные Active Directory собираются модулем Audit в режиме белого ящика профилями **Windows DC Audit** (один контроллер домена) / **Microsoft Active Directory Audit** (несколько контроллеров, по LDAP). Участники домена, клиенты SCCM и Kaspersky Security Center, виртуальные машины ESXi/Hyper-V и другие активы **обнаруживаются автоматически** при аудите исходных активов (косвенный метод обнаружения, см. [[Обнаружение активов]]). Импорт как таковой — это импорт [результатов сканирования](https://help.ptsecurity.com/ru-RU/projects/vm/2.8/help/6218464651) и данных из MaxPatrol 8 (профиль MP8ScanImporter).

| Создание задачи | **Сбор данных** → **Задачи** → **Создать задачу** → **Сбор данных** | Тип задачи — «Сбор данных», режим задаёт профиль |

| Параметр | Значение | Пояснение |
| --- | --- | --- |
| Название | Аудит новых неклассифицированных активов | — |
| Создание задачи | **Создать задачу** → **Сбор данных** | С учётными данными, но облегчённый |
| Цели | Группа «Unmanaged hosts» / ND-активы | Активы, у которых значимость не определена или ОС не определена |
| Профиль | Быстрый аудит — например, **Windows Updates Discovery** (Windows) / пользовательский профиль на базе стандартного | Минимальный набор проверок |
| Учётные записи | Стандартные для сканирования | Windows/Linux/сетевое |
| Расписание | Ежедневно | Быстрый ввод новых узлов в процесс |
| Приоритет | Высокий | Пока актив не классифицирован — он потенциальный риск |
| Ожидания | Поверхностный аудит достаточен | Глубокий — на ежемесячном этапе по значимости |
| Действие после | Политика значимости назначает H/M/L | ND-активы перетекают в нужную группу |

> [!tip] Правило нагрузки
> Задачи сбора активов не должны пересекаться по времени с аудитом: поиск активов (HostDiscovery) в субботу, аудит КД/гипервизоров — ранним утром или ночью, аудит новых ND — в воскресенье. Это снижает нагрузку на сеть и Collector'ы.

## Блок 2. Аудит (регулярная оценка уязвимостей и конфигураций)

| Задача | Тип | Группа | Профиль | Расписание | Приоритет |
| --- | --- | --- | --- | --- | --- |
| Полный аудит критичных серверов (H) | Сбор данных (Audit) | «Критичные серверы» | Windows Audit / Unix SSH Audit | Еженедельно | Высокий |
| Аудит серверов M/L | Сбор данных (Audit) | Остальные серверы | Windows Audit / Unix SSH Audit | Ежемесячно | Нормальный |
| Аудит рабочих станций | Сбор данных (Audit) | Windows WS | Windows Updates Discovery (быстрый) | Ежемесячно | Нормальный |
| Аудит сетевого оборудования | Сбор данных (Audit) | Network devices | Пользовательский профиль на базе стандартного (SNMP/SSH) | Ежемесячно | Нормальный |
| Аудит СУБД | Сбор данных (Audit) | Серверы БД | Пользовательский профиль на базе стандартного | Ежемесячно | Высокий |
| Аудит гипервизоров | Сбор данных (Audit) | VMware/Hyper-V | Пользовательский профиль аудита ESXi/Hyper-V | Ежемесячно | Высокий |

**Принципы оптимальности:**

- **Не сканировать всё одинаково.** Разные группы — разная частота: критичные — каждую неделю, остальное — раз в месяц. Снижает нагрузку на сеть и Collector'ы.
- **Разнести по дням/часам**, не запускать все политики разом. Пример недели:

| День | Время | Политика / задача |
| --- | --- | --- |
| Понедельник | 02:00 | Критичные серверы |
| Вторник | 02:00 | Серверы M/L |
| Среда | 02:00 | Сетевое оборудование |
| Четверг | 02:00 | Рабочие станции |
| Пятница | — | Выходной |
| Суббота | 02:00 | Поиск активов (HostDiscovery) |
| Воскресенье | 02:00 | Новые активы (ND) |

- **Классифицировать просрочку:** статус «Просрочена» с эскалацией по критичности настраивается политикой обработки, а не вручную.

## Блок 3. Пентест (имитация атак, чёрный ящик с агрессивными проверками)

> [!warning] Аудит ≠ пентест
> Аудит — это «белый ящик» с учётными данными: есть ли патчи, как настроены конфигурации. Пентест — проверка exploitable-состояния «снаружи», без учёток: профили модуля Pentest (стандартные **Windows Services Discovery**, **Service Discovery**, **Safe PenTest**) определяют доступные службы и выполняют безопасный пентест. Для проверки конкретных уязвимостей создаётся отдельная задача **Поиск уязвимостей в режиме пентеста** — по CVE-идентификаторам систему, параметры профиля создаст она сама (см. [[Создание задачи на поиск уязвимостей в режиме пентеста]]).

| Задача | Тип | Группа / цели | Профиль | Расписание | Приоритет |
| --- | --- | --- | --- | --- | --- |
| Пентест критичных серверов | Поиск уязвимостей в режиме пентеста / Сбор данных (Pentest) | «Критичные серверы» | Профиль, созданный системой по CVE / Safe PenTest | Еженедельно (или раз в 2 недели) | Высокий |
| Пентест периметра / DMZ | Сбор данных (Pentest) | Внешний периметр, публичные сервисы | Service Discovery / Safe PenTest | Ежемесячно | Высокий |
| Пентест веб-/прикладных сервисов | Сбор данных | Web/API-группы | Web Scan Optimal (модуль WebEngine) | Ежемесячно | Нормальный |
| Пентест инфраструктуры (обходной) | Сбор данных (Pentest) | Все активы (фоновый) | Windows Services Discovery / Service Discovery | Ежеквартально | Низкий |

**Почему пентесту нужен отдельный слой:**

- **Другая свежесть данных.** Для пентеста результаты устаревают быстрее: срок актуальности 7 дней у пентеста против 30 у аудита. Пентест-задачи должны перезапускаться минимум еженедельно на критичных активах.
- **Агрессивные проверки нагружают сеть и цели** — их нельзя делать каждый день по всему периметру. Основная массовая частота — раз в неделю/месяц, полный обход — реже.
- **Профиль пентеста ≠ профиль аудита.** Не смешивайте: аудит читает, пентест «атакует». Держите их как отдельные задачи с отдельными профилями, чтобы не раздувать длительность и не ловить ложные срабатывания на «мягких» проверках.

## Слой сопровождения — политики, делающие систему оптимальной

Отдельно от задач — автоматические **политики**, иначе задача соберёт данные, но не поднимет процесс:

1. **Политики значимости** — автоприсвоение H/M/L по PDQL-фильтрам активов (контроллеры домена, СУБД, файрволы → H; рабочие станции → L; тестовые стенды → L и т.д.). Настраиваются на странице **Система** → **Политики** → политика **Значимость активов** (см. [[Создание правила для значимости активов]]). При нескольких совпадениях побеждает политика с наименьшим номером приоритета.
2. **Политики обработки уязвимостей** — автопризначение статусов и сроков:
   - «Патчинг Windows-серверов» — `HasFix = true`, срок 1 месяц от даты публикации CVE;
   - «Патчинг рабочих станций» — срок 2 месяца;
   - «Уязвимости без фикса» — `HasFix = false` → ручной анализ;
   - исключения для тестового сегмента — осознанный приём риска.
3. **Политики актуальности данных** — сроки актуальности данных для аудита и пентеста (например, пентест 7 дней, критичные серверы 30, остальные 60–90); действие — уведомление + автоскан при устаревании ([[Создание правила для сроков актуальности данных]]). Страховка от «слепых зон».
4. **Интеграции** — VM→SIEM для корреляции, VM→ITSM для заявок на устранение, AD для синхронизации. Без них собранные уязвимости не доходят до владельца актива.

# Приложение: PDQL-запросы для динамических групп

> [!tip] Как создать динамическую группу
> **Активы** → панель **Группы** → создать группу (тип **Динамическая**) → вставить PDQL-условие в поле **Фильтр** → **Сохранить**. Группа автоматически пересчитывается при каждом обновлении данных.
>
> Условие динамической группы — это **предикат без конвейера**: `WindowsHost and Host.HostType = 'Server'`. Конвейер (`Select(...)`, `Group(...)`, `Sort(...)`) в условии группы не нужен. Для анализа и отчётов используйте полную форму с конвейером.
>
> Синтаксис — в [[4. Язык PDQL]], все псевдонимы — в [[PDQL — синтаксис по документации PT]].

> [!warning] Два правила, которые ломают половину условий групп
> **1. Не используйте `@Importance` и другие псевдонимы значимости.** `@IMPORTANCE` не поддерживается в динамических группах — иначе политика значимости зациклится на самой себе. Приоритетные группы стройте на признаках актива: роль хоста, ПО, тип узла, `@Vulners.CVSS3Score`.
> Полный список неподдерживаемых псевдонимов: `@Importance`, `@CumulativeVulnerability`, `@Vulners.Score`, `@Vulners.SeverityRating`, `@VulnerPassport.Score`, контекстные оценки и векторы CVSS, все `@Groups*`.
>
> **2. Объект модели — без `@`, псевдоним — с `@`.** `WindowsHost` и `Host` — объекты модели, `@Vulners.CVSS3Score` и `@IpAddresses.Item` — псевдонимы.

## Группы для сбора активов (Блок 1)

| Группа | PDQL-условие (динамическая группа) | Назначение |
| --- | --- | --- |
| Новые активы за неделю | `Host.@CreationTime >= Now() - 7days` | Ежедневный аудит новых активов; ввод в процесс |
| Не классифицированы за 30 дней | `Host.@CreationTime < Now() - 30days` | Разбор забытых активов; код состояния «значимость не задана» в PDQL не выражается — см. предупреждение выше |
| Компьютеры из домена | `ActiveDirectory` | Импорт структуры OU, компьютеров, пользователей |
| Серверы VMware | `Host.OsName like '%VMware ESXi%' or Host.Softs.Name like '%VMware ESXi%'` | Импорт/аудит гипервизоров |

## Группы для аудита (Блок 2)

Частоту аудита привязывайте к роли актива, а не к `@Importance` — псевдоним значимости в динамических группах не работает (см. предупреждение выше).

| Группа | PDQL-условие (динамическая группа) | Назначение |
| --- | --- | --- |
| Критичные серверы | `(WindowsHost and Host.HostType = 'Server') or UnixHost` | Еженедельный полный аудит |
| Серверы с уязвимостями ≥ 9 | `Host[@Vulners.CVSS3Score >= 9]` | Еженедельный аудит повышенного приоритета |
| Рабочие станции Windows | `WindowsHost and Host.HostType = 'Desktop'` | Ежемесячный базовый аудит |
| Сетевое оборудование | `NetworkDeviceHost` | Ежемесячный аудит коммутаторов/роутеров/МЭ |
| Серверы СУБД | `Host.Softs.Name like '%SQL Server%' or Host.Softs.Name like '%PostgreSQL%' or Host.Softs.Name like '%Oracle%'` | Ежемесячный аудит баз данных |
| Все активы | `Host` | Общая цель для фоновых/обходных задач |

## Группы для пентеста (Блок 3)

| Группа | PDQL-условие (динамическая группа) | Назначение |
| --- | --- | --- |
| Критичные цели пентеста | `Host[@Vulners.CVSS3Score >= 9] or WindowsHost[HostRoles.Role = 'Domain Controller']` | Еженедельный пентест |
| Периметр / DMZ | `Host.@IpAddresses.Item in 172.16.0.0/16` *(замените на вашу подсеть)* | Ежемесячный пентест периметра |
| Web/API-сервисы | `Host.Softs.Name like '%IIS%' or Host.Softs.Name like '%Apache%' or Host.Softs.Name like '%Nginx%'` | Ежемесячный пентест прикладного слоя |
| Тестовые стенды | `Host.Fqdn like '%TEST%'` | Исключение тестового сегмента; сканирование по требованию |

## Группы для политик значимости (Слой 0/сопровождение)

Эти же PDQL-условия используются как **фильтры политик значимости** (автоприсвоение H/M/L):

| Политика значимости | PDQL-фильтр активов | Значимость | Приоритет |
| --- | --- | --- | --- |
| Контроллеры домена | `Host.HostRoles.Role = 'Domain Controller'` | H | 1 |
| Серверы с БД | `Host.Softs.Name like '%SQL Server%' or Host.Softs.Name like '%PostgreSQL%' or Host.Softs.Name like '%Oracle%'` | H | 1 |
| Межсетевые экраны | `NetworkDeviceHost.HostRoles.Role = 'Firewall'` | H | 1 |
| Серверы Exchange | `Host.Softs.Name like '%Exchange%'` | H | 1 |
| Маршрутизаторы | `NetworkDeviceHost.HostRoles.Role = 'Router'` | M | 2 |
| Коммутаторы | `NetworkDeviceHost.HostRoles.Role = 'Switch'` | M | 2 |
| Рабочие станции | `WindowsHost and Host.HostType = 'Desktop'` | L | 3 |
| Принтеры | `NetworkDeviceHost` | L | 3 |
| Тестовые стенды | `Host.Fqdn like '%TEST%'` | L | 3 |

> [!note] Приоритет политик значимости
> Если актив попадает под несколько политик, побеждает политика с **наименьшим** номером приоритета (1 > 2 > 3). При равных приоритетах — политика, созданная позже.

## Полезные запросы для мониторинга

Не для групп, но для дашбордов и контроля процесса:

Это запросы для анализа и дашбордов, а не условия групп — здесь конвейер и `@Importance` допустимы.

- **Активы, не сканировавшиеся более 30 дней** (слепые зоны):
  ```text
  Filter(Host.@AuditTime < Now() - 30days) | Select(@Host, Host.Fqdn, Host.@AuditTime)
  ```
- **Новые активы за 7 дней**:
  ```text
  Filter(Host.@CreationTime >= Now() - 7days) | Select(@Host, Host.Fqdn, Host.@IpAddresses)
  ```
- **Активы, которые скоро устареют (удалить данные в течение недели)**:
  ```text
  Filter(Host.@DeletionTime <= Now() + 7days) | Select(@Host, Host.Fqdn, Host.@DeletionTime)
  ```
- **Критичные уязвимости на высокозначимых активах**:
  ```text
  Filter(Host.@Importance in ['H', 'M'] and Host[@Vulners.SeverityRating = 'Critical'])
  | Select(@Host, Host.Fqdn, Host.@Importance, Host.@Vulners.CVEs)
  | Sort(Host.Fqdn ASC)
  ```
- **Уязвимости с эксплойтами (CVSS3 ≥ 7)**:
  ```text
  Filter(@Vulners.Metrics.Exploitable)
  | Select(@Vulners.CVEs, @Vulners.Name, @Vulners.CVSS3Score, @Vulners.HowToFix)
  | Sort(@Vulners.CVSS3Score DESC)
  ```
- **Просроченные уязвимости**:
  ```text
  Filter(Host[@Vulners.DueTime < Now()]) | Select(@Host, Host.Fqdn, Host.@Vulners.CVEs, Host.@Vulners.DueTime)
  ```
- **Динамика критичных уязвимостей по дням** (для виджета с распределением по времени):
  ```text
  Filter(Host[@Vulners.CVSS3Score >= 9])
  | Timeseries(30d, 1d, Endofday())
  | Select(@Host, Host.@Time)
  | Group(Host.@Time, Count(*))
  ```

## Чек-лист внедрения

- [ ] Настроены отдельные учётные записи для сканирования (Windows, Linux, сетевое, СУБД) и проверено подключение.
- [ ] Созданы группы активов (статические + динамические по PDQL).
- [ ] Настроены политики значимости (H/M/L/ND), ND-активы классифицируются.
- [ ] Созданы задачи сбора активов (HostDiscovery + аудит КД/гипервизоров + ND-аудит).
- [ ] Созданы задачи аудита по группам с разной частотой.
- [ ] Созданы задачи пентеста (Safe PenTest / Поиск уязвимостей в режиме пентеста).
- [ ] Задачи разнесены по дням/часам, чтобы не перегружать сеть и Collector'ы.
- [ ] Настроены политики обработки уязвимостей (патчинг, исключения, без фикса).
- [ ] Настроены политики актуальности данных (7–30–90 дней по типам).
- [ ] Настроены интеграции SIEM / ITSM / AD.
- [ ] Настроены дашборды и уведомления о просрочках с эскалацией по критичности.
