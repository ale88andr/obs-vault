Prime — веб-платформа: каждый модуль живёт на своём доменном имени и общается по HTTPS, поэтому сертификаты и DNS — это не сопутствующая мелочь, а инфраструктурный фундамент установки. Именно здесь чаще всего «падает» первый запуск (`check.sh` ругается на DNS или проверку authority). Заметка собирает схему сертификации Prime в одном месте.

> [!info] Место заметки в плане обучения
> Относится к этапу 2 плана [[План изучения ViPNet Prime]]. Теоретическая база по PKI — [[PKI]] и [[ФЗС PKI]], механика защиты каналов — [[TLS]]. Установочные команды — в [[2. Установка и настройка ViPNet Prime -  пошаговая инструкция по модулям]].

## Два контура сертификации

Для работы платформы нужны **два набора сертификатов**:

| Контур | Алгоритм | Что защищает |
| --- | --- | --- |
| АРМ администратора ↔ сервер Prime | **ГОСТ** | Канал подключения администратора к веб-интерфейсу (требование регулятора) |
| Внутренняя коммуникация компонентов Prime | **RSA** | Взаимодействие ядра и модулей между собой |

Оба комплекта оформляются в формате **PEM**: сертификат конечного узла, закрытый ключ узла, сертификаты главного удостоверяющего центра и промежуточных центров для построения полной цепочки.

## Поля сертификатов: CN и SAN

- `Common Name (CN)` — имя ядра системы ViPNet Prime Core.
- `Subject Alternative Name (SAN)` — доменные имена всех используемых модулей.

Пример заполнения:

```text
CN:  core.prime.myorg
SAN: DNS:vpn.prime.myorg,
     DNS:pmm.prime.myorg,
     DNS:nvs.prime.myorg,
     DNS:core.prime.myorg
```

## Раздельные сертификаты или wildcard

| Вариант | SAN содержит | Когда удобен |
| --- | --- | --- |
| Раздельные сертификаты | По записи на каждый модуль: `prime.prime.local`, `vpn.prime.local`, `nvs.prime.local`, … | Строгие политики безопасности, разные владельцы модулей |
| Wildcard-сертификат | Одну строку: `*.prime.local` | Один поддомен, единая зона ответственности, меньше административной работы |

## Кто выпускает сертификаты: три варианта УЦ

1. **Корпоративный УЦ** — основной вариант для внутренних имён вида `*.prime.local`. Корневой сертификат устанавливается в доверенные хранилища рабочих мест администраторов.
2. **Публичный УЦ** — сможет выпустить сертификат только на подтверждаемое публичное доменное имя; для внутренних имён не подходит.
3. **Собственная цепочка УЦ прямо на узле Prime** — когда удостоверяющего центра в организации нет. Создаётся в процессе подготовки узла.

## DNS — обязательная пара к сертификатам

Имена в SAN должны резолвиться. Для каждого модуля прописывается своя запись на частном DNS-сервере:

| Адрес | Доменное имя |
| --- | --- |
| IP ВМ 1 | `prime.prime.local` |
| IP ВМ 1 | `vpn.prime.local` |
| IP ВМ 1 | `nsms.prime.local` |
| IP ВМ 1 | `rollout.prime.local` |
| IP ВМ 1 | `pmm.prime.local` |
| IP ВМ 1 | `connect.prime.local` |

> [!warning] Обходной путь через hosts имеет предел
> Без DNS-сервера можно прописать пары «IP — имя» в файл hosts, но тогда вход в Prime будет возможен только с тех устройств, где эти записи сделаны. Для распределённых команд и сервисов это тупик — планируйте нормальный DNS заранее.

## Доверенные хранилища

Чтобы браузер и ОС принимали сертификаты внутреннего УЦ:

- корневой сертификат корпоративного УЦ устанавливается в хранилище доверенных ЦС операционной системы;
- для некоторых браузеров цепочку дополнительно загружают в настройки браузера;
- на Linux-узлах (например, сборщик данных NVS): скопировать сертификат УЦ в `/usr/local/share/ca-certificates` и выполнить `sudo update-ca-certificates`.

Типовое проявление проблемы при входе в модуль VPN — сообщение *«Подключиться ли к недоверенному ресурсу?»*: причина почти всегда в отсутствии корневого сертификата в хранилище.

## Диагностика через check.sh

Скрипт проверки установки показывает, какой именно контур сломан (см. [[2. Установка и настройка ViPNet Prime -  пошаговая инструкция по модулям]]):

- `DNS resolving` — разрешение имён вашего домена;
- `DNS resolving (ViPNet)` — то же через защищённую сеть (до установки совместимого клиента и ключей статус `fail` допустим);
- `Check authority` — работа сервиса аутентификации и корректность сертификатов;
- `Check health` — состояние контейнеров.

## Роль ViPNet PKI Client

PKI Client ставится на АРМ администратора и решает две группы задач:

1. **Защита канала АРМ ↔ Prime.** Строит односторонний ГОСТ TLS-канал; для класса защиты КС3 добавляется личный сертификат администратора — канал становится двусторонне аутентифицируемым, администратор идентифицируется по ГОСТ-сертификату вместо/вместе с паролем.
2. **Работа с подписями и доверием.** Проверка электронных подписей обновлений и экспертных данных модулем File Unit, загрузка списков отзыва сертификатов (CRL), импорт цепочек доверия (рекомендуется продублировать их в настройках браузера).

Лицензирование PKI Client (полугодовая бесплатная / покупка по числу АРМ) разобрано в [[4. Лицензирование ViPNet Prime]].

## Чек-лист перед установкой

- [ ] Выбран вариант УЦ (корпоративный / публичный / собственная цепочка)
- [ ] Выпущены два набора сертификатов: ГОСТ и RSA, формат PEM
- [ ] CN = имя Core, SAN покрывает все модули (или куплен wildcard `*.prime.local`)
- [ ] Есть закрытые ключи и полные цепочки (корень + промежуточные)
- [ ] Настроен DNS: все имена модулей резолвятся с АРМ и внутри сети
- [ ] Корневой сертификат УЦ разложен в доверенные хранилища: ОС, браузеры, Linux-узлы
- [ ] На АРМ установлен PKI Client, для КС3 подготовлен сертификат администратора
