Кластер горячего резервирования (failover) — штатный механизм отказоустойчивости ViPNet Coordinator HW. Два одинаковых координатора образуют кластер: один узел активен и обслуживает трафик, второй находится в пассивном режиме и получает от активного конфигурацию, ключи и журналы. При отказе активного узла (или принудительном переключении) пассивный становится активным и принимает на себя его адреса.

#### Архитектура и принцип работы (F_STP / Failover)

#### Кластер горячего резервирования в ViPNet Coordinator HW/XFirewall обычно строится по схеме **Active-Passive** (Активный-Пассивный) и использует следующие компоненты:

- **Демон `failoverd`** — «мозг» кластера. Он обменивается heartbeat-пакетами с соседним узлом, отслеживает состояние интерфейсов и генерирует системные события с тегом `<F_STP>` (например, `Command: failover stop` или `failover start`).
- **Протокол VRRP** — используется для того, чтобы оба узла имели общий виртуальный MAC-адрес и IP-адрес. Шлюз по умолчанию для клиентов всегда указывает на этот виртуальный VRRP IP.
- **Канал синхронизации (Sync Link)** — выделенный физический интерфейс, по которому узлы обмениваются состояниями сессий (stateful failover), таблицами маршрутизации и конфигурациями.
- **Watchdog-драйвер (`itcswd`)** — аппаратно-программный сторожевой таймер, который перезагружает узел, если ядро ОС или драйвер ViPNet «зависли», чтобы пассивный узел мог перехватить управление.
- **Служба `iplircfg`** — управляет сетевыми интерфейсами и туннелями; именно её перезапускает `failoverd` при смене ролей узлов.



В заметке описан порядок настройки такого кластера на координаторах HW1000: модель адресации, конфигурация службы `failover` для обоих узлов, запуск, приёмочные тесты и диагностика типовых ошибок.

> [!info] Область применимости
> Проверено на ViPNet Coordinator HW1000. Состав параметров `failover.ini`, имена скриптов и набор команд могут отличаться на других платформах и версиях ПО — сверяйте с РЭ к вашей версии. Команды выполняются в привилегированном режиме CLI (вход — `enable`).

## Термины и модель адресации

| Термин | Что это |
|---|---|
| Активный адрес | «Плавающий» адрес интерфейса: одинаков на обоих узлах, назначается тому узлу, который в данный момент активен |
| Пассивный адрес | Служебный адрес узла в пассивном состоянии: свой у каждого узла на каждом интерфейсе |
| Перемычка (crosslink) | Отдельный интерфейс и физический линк между узлами, по которому идёт синхронизация и проверка доступности соседа |

Ключевая особенность технологии: **на каждый интерфейс, участвующий в кластере, нужно три адреса** — один активный (общий) и два пассивных (по одному на узел). В сетевом окружении виден только активный адрес: он назначен на интерфейс активного узла. Пассивные адреса наружу не маршрутизируются — они нужны исключительно для работы кластера. Активная нода обменивается по перемычке данными с пассивной, на интерфейсе которой в этот момент установлен её пассивный адрес.

Пример распределения адресов для стенда с двумя рабочими интерфейсами и перемычкой:

| Интерфейс | Назначение | Активный адрес (общий) | Пассивный, узел 1 | Пассивный, узел 2 |
|---|---|---|---|---|
| `eth0` | внешний, за ним шлюз по умолчанию | `10.26.0.6/29` | `198.18.0.6/0` | `198.18.0.7/0` |
| `eth2` | внутренний | `10.26.0.129/25` | `198.18.0.129/0` | `198.18.0.130/0` |
| `eth3` | перемычка | — | `192.168.26.1/24` | `192.168.26.2/24` |

> [!warning] Почему пассивные адреса взяты из 198.18.0.0/15
> Пассивные адреса — условные: маска `/0` означает не «сеть нулевой длины», а признак адреса, который не должен попадать в реальную маршрутизацию. Логика выбора — «зеркалить» реальный адрес, меняя старшие октеты: `10.26.0.6` → `198.18.0.6`.
> Встречающиеся в примерах адреса вида `21.26.0.x` относятся к публичному пространству `21.0.0.0/8` — так делать не следует. `198.18.0.0/15` зарезервирован для тестовых/benchmark-целей (RFC 2544), в интернете не маршрутизируется, конфликтов с реальными сетями не создаёт.
> Требования к пассивным адресам: уникальность в пределах кластера и отсутствие пересечений с любыми реально маршрутизируемыми префиксами.

> [!important] Кто владеет адресами после включения кластера
> После `failover start` адреса на интерфейсах назначает служба `failover`. Правка адреса командой `inet ifconfig` будет перезатёрта при следующей смене роли. Менять адрес нужно в `failover.ini` (параметр `activeip`), причём одинаково на обоих узлах. Значение `activeip` в конфиге должно совпадать с тем, что реально настроено на интерфейсе, иначе служба начнёт перенастраивать интерфейс и можно потерять доступ к web-интерфейсу.

## Предусловия

| Что | Требование |
|---|---|
| Платформа | Одинаковые модели и версии ПО на обоих узлах |
| Лицензия | Кластер (горячее резервирование) должна быть разрешена лицензией |
| Время | Синхронизация по NTP на обоих узлах, см. [[7. Максимальная разница времени]] — иначе расходятся журналы и метки в `failover view` |
| Перемычка | Отдельный порт на каждом узле, соединённый **прямым кабелем** (без коммутатора), сегмент изолирован |
| Адресация | Заполненная таблица из трёх адресов на каждый интерфейс (см. выше) |
| Доступ | Консоль/SSH и web-интерфейс по активному адресу |
| Резервная копия | `admin config save <имя>` до начала работ, см. [[12. Сохранение конфигурации HW]] |

> [!warning] Перемычка — единственный канал синхронизации
> По перемычке передаются конфигурация, **ключи** и журналы, поэтому сегмент должен быть физически изолирован: прямой кабель, отсутствие коммутаторов и постороннего трафика, ограничение физического доступа.
> При обрыве перемычки узлы перестают видеть друг друга — это риск split-brain (оба узла станут активными). Порт `10090` должен быть одинаковым на обоих узлах и не фильтроваться.

## Порядок настройки

### 1. Подготовка узла

```shell
enable
admin config save before-cluster
admin config list
failover show info
failover show config
ls -l /sbin/change_route.sh
```

- `failover show info` до настройки должен показывать одиночный режим (служба не в кластере).
- `failover show config` — текущий `failover.ini`, полезно сохранить как эталон.
- `ls -l /sbin/change_route.sh` — убедиться, что скрипт, который будет указан в `beforeifconf`/`afterifconf`, существует. Путь к несуществующему скрипту приводит к тем же циклическим перезагрузкам, от которых он должен защищать. На разных версиях ПО имя и расположение скрипта могут отличаться.

### 2. Конфигурация узла 1

```shell
failover stop
failover config mode cluster
failover config edit
```

`failover config edit` открывает `failover.ini` в редакторе `vi`: вход в режим вставки — `i`, выход с сохранением — `Esc`, затем `:wq`.

```ini
[network]
checktime = 30
timeout = 4
activeretries = 5
channelretries = 5
synctime = 5
fastdown = yes
beforeifconf = /sbin/change_route.sh before
afterifconf = /sbin/change_route.sh after

[channel]
device = eth0
ident = iface-0
activeip = 10.26.0.6/29
passiveip = 198.18.0.6/0
testip = 10.26.0.1
checkonlyidle = yes

[channel]
device = eth2
ident = iface-2
activeip = 10.26.0.129/25
passiveip = 198.18.0.129/0
testip = 127.0.0.1
checkonlyidle = no

[sendconfig]
activeip = 192.168.26.2
sendtime = 60
device = eth3
config = yes
keys = yes
journals = yes
port = 10090

[misc]
activeconfig = /etc/iplirpsw
passiveconfig = /etc/iplirpsw
maxjournal = 30 #days
reboot = yes

[debug]
debuglevel = 3
debuglogfile = syslog:daemon.debug

[events]
```

Что изменяется относительно заводской конфигурации:

| Место | Значение | Зачем |
|---|---|---|
| `[network]` | добавлены `beforeifconf`, `afterifconf` | Скрипты вызываются до и после переназначения адресов при смене роли: регистрируют маршруты и журналируют переключение. Без них маршруты не перерегистрируются при смене роли, а по наблюдениям это приводило к циклическим перезагрузкам |
| `[channel]` ×2 | `device`, `ident`, `activeip`, `passiveip`, `testip` | Описание интерфейсов, участвующих в кластере. По одной секции `[channel]` на интерфейс |
| `[sendconfig]` | `activeip`, `device` | Адрес перемычки **соседнего** узла и локальный интерфейс перемычки |

Разбор по секциям:

**[network]** — тайминги и хуки смены роли. Значения из примера рабочие; менять их без понимания не нужно: они определяют, как быстро кластер обнаруживает отказ, а слишком агрессивные значения дают ложные переключения.

**[channel]** — по секции на каждый интерфейс:

- `device` — имя интерфейса как в системе (`eth0`, `eth2`, `eth2:0`, `eth1.72`);
- `ident` — имя канала, см. правило ниже; **обязано совпадать на обоих узлах** для одного и того же линка, иначе каналы не спарятся;
- `activeip` — активный (плавающий) адрес вместе с маской реальной подсети;
- `passiveip` — пассивный адрес узла, маска `/0`;
- `testip` — адрес, доступность которого проверяется, чтобы понять, что канал жив. Обычно это шлюз за данным интерфейсом (в примере для `eth0` — `10.26.0.1`). Если проверка невозможна, указывают петлю `127.0.0.1`;
- `checkonlyidle` — проверять канал только когда по нему нет трафика (`yes` снижает вероятность ложного переключения на загруженных каналах).

Правило именования `ident`: `iface-` плюс имя интерфейса без префикса `eth`.

| `device` | `ident` |
|---|---|
| `eth0` | `iface-0` |
| `eth2` | `iface-2` |
| `eth2:0` (дополнительный адрес) | `iface-2:0` |
| `eth1.72` (VLAN 72 на `eth1`) | `iface-1.72` |

> [!warning] Осторожно с testip
> `testip = 127.0.0.1` означает, что проверка канала фактически отключена: петля доступна всегда, поэтому отказ сети не приведёт к переключению. Это осознанный компромисс (лучше, чем ложные переключения), а не равноценная альтернатива нормальной проверке.
> `testip` не должен указывать на адрес, доступность которого зависит от активного узла. Иначе возникают «качели»: узел становится активным → адрес пропадает → узел уходит в пассив → адрес возвращается → узел снова становится активным.
> Неверный `testip` в сочетании с `checkonlyidle = no` — самая частая причина циклических перезагрузок обоих узлов.

**[sendconfig]** — синхронизация конфигурации, ключей и журналов:

- `activeip` — адрес перемычки соседнего узла. `192.168.26.2` назначен не на настраиваемом узле, а на втором, который настраивается позже. Не путать с `activeip` в секции `[channel]` — это разные параметры;
- `device` — локальный интерфейс перемычки (`eth3`);
- `sendtime` — период синхронизации, с;
- `config`, `keys`, `journals` — что синхронизировать. `keys = yes` критично: без синхронизации ключей после переключения часть защищённых соединений не восстановится.

**[misc]**, **[debug]**, **[events]** — служебные параметры, оставлены без изменений. Пустая секция `[events]` — норма.

Проверить, что файл прочитался корректно, до запуска службы:

```shell
failover show config
```

### 4. Запуск и первичная проверка

После того как оба узла настроены, на **каждом** узле:

```shell
failover start
```

Один или оба узла после запуска перезагрузятся — это ожидаемо: смена роли влечёт переназначение адресов на интерфейсах, служба перезапускает сетевой стек. Возможны несколько перезагрузок подряд. Надо выждать и убедиться, что перезагрузки прекратились, а `failover uptime` растёт.

```shell
failover show info
failover show sync-connections
failover show active-mac-address
failover view <начало> <конец>
```

Состояние корректно работающего кластера (обратная картина должна наблюдаться на соседнем узле):

| Параметр | local | remote |
|---|---|---|
| failover mode | active | passive |
| failover uptime | 15d 7:47 | 15d 7:46 |
| total cpu | 22% | 2% |
| total memory | 2014032 kB | 2014032 kB |
| free memory | 1632852 kB | 1662048 kB |
| failover state | works | works |
| failover cpu | 0% | 0% |
| iplir state | works | works |
| iplir cpu | 3% | 2% |
| mftp state | works | works |
| mftp cpu | 34% | 0% |
| alg state | works | stopped |
| alg cpu | 0% | 0% |
| webgui state | works | stopped |
| webgui cpu | 0% | 0% |

> [!note] Что считается нормой
> Зеркальность касается `failover mode` и `failover state`: на одном узле `active`, на другом `passive`, состояние службы — `works` на обоих.
> Службы `alg` и `webgui` в состоянии `stopped` на пассивном узле — **норма**, а не ошибка. `webgui` работает только на активном узле, поэтому web-интерфейс доступен по активному адресу и только на активной ноде.
> Растущий `failover uptime` — главный признак того, что узел не перезагружается циклически.

### 5. Приёмочные тесты

Кластер настроен не тогда, когда `failover show info` показывает ожидаемую картину, а когда проверены оба направления переключения.

1. **Прямое переключение.** На активном узле:
   ```shell
   failover start passive
   ```
   В течение `checktime` + `timeout` соседний узел должен стать активным: активный адрес отвечает, web-интерфейс открывается. Проверить `failover show info` на обоих узлах и запись в `failover view`.
2. **Обратное переключение.** Вернуть прежний узел (перезагрузка или `failover start`), убедиться, что он перешёл в пассивный режим и **не отбирает** активность обратно. Самопроизвольный возврат активности («качели») — признак неверного `testip` или нестабильного канала.
3. **Отказ линка.** Отключить кабель на одном из рабочих интерфейсов активного узла и убедиться, что произошло переключение, а после восстановления линка состояние стабилизировалось.
4. **Синхронизация.** `failover show sync-connections` показывает соединения с соседом; после переключения конфигурация, ключи и журналы на новом активном узле должны быть актуальны.

## Справочник параметров failover.ini

Формулировки — по смыслу и по практике эксплуатации; точные определения сверяйте с РЭ вашей версии ПО.

| Параметр | Секция | Смысл |
|---|---|---|
| `checktime` | network | Период проверки состояния каналов и соседа, с |
| `timeout` | network | Таймаут ожидания ответа при проверке, с |
| `activeretries` | network | Число неудачных проверок до попытки узла стать активным |
| `channelretries` | network | Число неудачных проверок до признания канала отказавшим |
| `synctime` | network | Период обмена состоянием между узлами, с |
| `fastdown` | network | Ускоренное обнаружение отказа при явном обрыве линка (не ждать `checktime`) |
| `beforeifconf` / `afterifconf` | network | Скрипты, выполняемые до и после переназначения адресов при смене роли |
| `device` | channel | Имя интерфейса (`eth0`, `eth2:0`, `eth1.72`) |
| `ident` | channel | Имя канала; одинаково на обоих узлах |
| `activeip` | channel | Активный (плавающий) адрес: одинаков на обоих узлах |
| `passiveip` | channel | Пассивный адрес узла; уникален; маска `/0` |
| `testip` | channel | Адрес для проверки доступности канала; `127.0.0.1` — проверка отключена |
| `checkonlyidle` | channel | Проверять канал только когда он простаивает |
| `activeip` | sendconfig | Адрес перемычки **соседнего** узла |
| `sendtime` | sendconfig | Период синхронизации конфигурации/ключей/журналов, с |
| `device` | sendconfig | Локальный интерфейс перемычки |
| `config` / `keys` / `journals` | sendconfig | Что синхронизируется: конфигурация, ключи, журналы |
| `port` | sendconfig | Порт синхронизации (по умолчанию `10090`), одинаков на обоих узлах |
| `activeconfig` / `passiveconfig` | misc | Файлы конфигурации `iplir` для активного и пассивного состояния |
| `maxjournal` | misc | Глубина хранения журналов, дни |
| `reboot` | misc | Разрешить автоматическую перезагрузку узла |
| `debuglevel`, `debuglogfile` | debug | Уровень и приёмник отладочного вывода |

## Транковые и дополнительные интерфейсы

Если на координаторе поднят транковый интерфейс или на существующий интерфейс назначена дополнительная адресация, такие интерфейсы тоже описываются в `failover.ini`. Нотация ViPNet: `1.72` — VLAN 72 на интерфейсе `eth1` (цифра до точки — номер интерфейса, после точки — идентификатор VLAN); `2:0` — дополнительный адрес на `eth2` (цифра до двоеточия — номер интерфейса, после — порядковый номер адреса, начиная с нуля). Подробнее про нотацию — [[9. Дополнительный IP-адрес и VLAN]].

```ini
[channel]
device = eth2:0
ident = iface-2:0

[channel]
device = eth1.72
ident = iface-1.72
```

> [!important] Все интерфейсы, кроме перемычки
> В `[channel]` должны быть перечислены **все** интерфейсы, адреса которых должны переезжать вместе с ролью, — включая интерфейс управления. Интерфейс перемычки в `[channel]` не включается: его адрес статичен и не переключается. Если интерфейс управления не описать в `[channel]`, после переключения web-интерфейс окажется недоступен.

## Диагностика

| Симптом | Вероятная причина | Что проверить |
|---|---|---|
| Циклические перезагрузки одного или обоих узлов | Неверный `testip`; несуществующий путь в `beforeifconf`/`afterifconf`; `activeip` не совпадает с реальной адресацией интерфейса | `ls -l /sbin/change_route.sh`, `ping <testip>` с узла, `failover view` |
| Оба узла активны (split-brain) | Обрыв или некорректная перемычка; разные `ident` на одном линке; разные `port` | `failover show sync-connections`, пинг адресов перемычки, `failover show active-mac-address` |
| Оба узла пассивны | Ни один узел не может стать активным: не проходит проверка `testip`; трафик проверки блокируется фильтрами | `ping <testip>`, сетевые фильтры на пути к `testip` |
| Web-интерфейс недоступен | Интерфейс управления не описан в `[channel]`; обращение к пассивному адресу или к пассивному узлу | Состав секций `[channel]`, обращение по активному адресу |
| Ключи/журналы не синхронизируются | `journals = no`, `keys = no`; закрыт `port`; неверный адрес в `[sendconfig] activeip` | `failover show sync-connections`, `failover view`, доступность перемычки |
| Переключение занимает слишком долго | Большие `checktime`/`timeout`; `checkonlyidle = yes` на простаивающем канале | Значения секции `[network]` |
| Узел «качается»: активность возвращается сама | `testip` зависит от активного узла; нестабильный канал | См. предупреждение про `testip` |

Полезные команды (полный перечень — [[Список команд по разделам (HW5)]], [[Список команд по разделам]]):

| Команда | Назначение |
|---|---|
| `failover show info` | Текущее состояние кластера |
| `failover show config` | Действующая конфигурация `failover.ini` |
| `failover show sync-connections` | Соединения синхронизации с соседним узлом |
| `failover show active-mac-address` | Доступность интерфейса активного узла со стороны пассивного |
| `failover view <начало> <конец>` | Журнал переключений за период |
| `failover start [active \| passive]` | Запуск службы / принудительное переключение |
| `failover stop` | Остановка службы |
| `failover config mode {single \| cluster}` | Режим работы службы |

## Обслуживание и откат

**Плановые работы на активном узле.** Сначала перевести активность на соседа, дождаться, что он стал активным и синхронизировался, затем обслуживать бывший активный узел. После возврата узла в строй убедиться, что он перешёл в пассивный режим, синхронизация восстановлена, а активность осталась на нужном узле.

```shell
failover start passive
failover show info
failover show sync-connections
```

**Мониторинг.** Состояние узлов кластера можно опрашивать по SNMP: `inet snmp cluster node <IP-адрес> community <строка>`. Отладочный вывод службы уходит в syslog (`debuglogfile = syslog:daemon.debug`). Минимальный набор для контроля — `failover state`, `failover mode` и рост `failover uptime`.

**Откат конфигурации.** Если кластер нужно разобрать:

```shell
failover stop
failover config mode single
```

После перевода в режим `single` адреса на интерфейсах возвращаются в обычное управление — адресацию нужно назначить вручную. Если до начала работ была сохранена резервная копия, конфигурацию можно восстановить из неё: `admin config load <имя>`, см. [[12. Сохранение конфигурации HW]].

## Что важно помнить

- На каждый интерфейс кластера — три адреса: активный (общий) и два пассивных (по одному на узел).
- Активный адрес в `[channel]` и `activeip` в `[sendconfig]` — разные параметры: первый плавающий адрес узла, второй адрес перемычки соседа.
- `ident` одного и того же линка обязан совпадать на обоих узлах.
- Перемычка — единственный канал синхронизации ключей и журналов; в `[channel]` её включать нельзя, а сам сегмент должен быть изолирован.
- `testip = 127.0.0.1` отключает проверку канала; `testip`, зависящий от активного узла, даёт «качели».
- После `failover start` адресами управляет служба `failover` — правки `inet ifconfig` будут перезатёрты.
- Кластер считается настроенным после проверки обоих направлений переключения, а не после появления `active/passive` в `failover show info`.

### Часть 1: Настройка кластера ViPNet Coordinator

#### Шаг 1. Подготовка интерфейсов

Согласно технологии **ViPNet,** для каждого интерфейса в кластере необходимо задать три адреса

![[Pasted image 20261118130019.png]]

#### Шаг 2. Редактирование failover.ini

Остановите службу отказоустойчивости и откройте редактор конфигурации:

```
hostname# failover stop
hostname# failover config mode cluster
hostname# failover config edit
```

#### Пример конфигурации для Первой ноды:

```
[network]
checktime = 30
timeout = 4
activeretries = 5
channelretries = 5
synctime = 5
fastdown = yes
beforeifconf = /sbin/change_route.sh before
afterifconf = /sbin/change_route.sh after

[channel]
device = eth0
ident = iface-0
activeip = 10.26.0.6/29
passiveip = 21.26.0.6/0
testip = 10.26.0.1
checkonlyidle = yes

[channel]
device = eth2
ident = iface-2
activeip = 10.26.0.129/25
passiveip = 21.26.0.129/0
testip = 127.0.0.1
checkonlyidle = no

[sendconfig]
activeip = 192.168.26.2  ; ← IP-адрес перемычки ВТОРОЙ ноды
device = eth3
sendtime = 60
config = yes
keys = yes
journals = yes
port = 10090

[misc]
activeconfig = /etc/iplirpsw
passiveconfig = /etc/iplirpsw
maxjournal = 30
reboot = yes
syncconnections = yes
```

#### Конфигурация Второй ноды:

- activeip — те же, что на первой ноде
- passiveip — измените последний октет (например, 21.26.0.7/0)
- В [sendconfig] укажите activeip = 192.168.26.1 (IP перемычки первой ноды)

#### Важно:

- Параметры **beforeifconf** и **afterifconf** в секции [network] критичны — без них возможны циклические перезагрузки нод

#### Шаг 3. Применение конфигурации и запуск

```
# На обеих нодах:
hostname# failover config mode cluster
hostname# failover start active    ; на первой ноде
hostname# failover start passive   ; на второй ноде
```

#### Шаг 4. Проверка состояния кластера

```
# Просмотр конфигурации:
hostname# failover show config

# Проверка MAC-адресов активных интерфейсов:
hostname# failover show active-mac-address

# Общая информация о кластере:
hostname# failover show info
```

#### Ожидаемый вывод failover show info:

```
failover mode: cluster
local: active / remote: passive
failover state: works
iplir state: works
```

### Часть 3: Настройка ViPNet Client для подключения к кластеру

#### Шаг 1. Установка и базовая настройка клиента

- Установите **ViPNet Client** на рабочую станцию
- Импортируйте ключевой дистрибутив (*.dst), выданный администратором сети
- Запустите **ViPNet** Монитор

---

#### Шаг 2. Настройка подключения к координатору

#### В окне ViPNet Монитор:

- Перейдите: Настройка → Подключение к сети **ViPNet**
- В поле «Адрес координатора» укажите виртуальный (active) **IP-адрес кластера** (например, 10.26.0.6)
- При необходимости настройте приоритеты адресов доступа (если координатор имеет несколько интерфейсов)
- Сохраните настройки и выполните подключение

> Клиент автоматически переподключится к пассивной ноде при отказе активной — переключение прозрачно для пользователя, время восстановления сессии ≤ 1 секунды

#### Шаг 3. Проверка подключения

- В **ViPNet Монитор** должен отображаться статус **«Подключено»**
- Проверьте доступность защищённых ресурсов сети
- При необходимости просмотрите журнал событий: **Администрирование → Журнал событий**
