## Общий принцип: драйвер перехватывает пакет до стека TCP/IP

Ключевой момент — трафик координатора-отправителя обрабатывает **ViPNet-драйвер (iplir)** ещё до того, как пакет попадёт в сетевой стек и на прикладной уровень. Поэтому координатор встраивается «между» отправителем и внешней сетью:

1. Приложение/узел за координатором формирует обычный IP-пакет с адресом назначения.
2. Драйвер `iplir` перехватывает пакет и **по адресу назначения определяет, что адресат защищён**, — сравнением с загруженными в него адресами доступа (`accessip`) защищённых узлов.
3. Если адресат защищён — пакет **шифруется**, а заголовок перестраивается (см. ниже).
4. Готовый пакет отдаётся в сетевой стек и уходит наружу.

Если адресат не защищён — пакет уходит как есть (либо блокируется правилами МЭ).

## Адресная модель: accessip → firewallip

Для каждого удалённого защищённого узла/координатора в `iplir.conf` хранится пара адресов:

- **`accessip`** — адрес, по которому **наш** координатор обращается к удалённому (может быть реальным IP или виртуальным). Он **единственный** для узла.
- **`firewallip`** — адрес, по которому удалённый координатор **виден из внешних сетей** (адрес на внешнем МЭ или внешнем интерфейсе). Именно на него пойдут зашифрованные пакеты.

Схема подмены при отправке (это и есть ядро передачи между координаторами):

> наш координатор берёт пакет с адресом назначения = `accessip` удалённого → **заменяет адрес назначения на `firewallip`** удалённого → адрес источника становится адресом того сетевого интерфейса, с которого уйдёт трафик по таблице маршрутизации.

На принимающей стороне всё происходит в обратном порядке.

## Варианты инкапсуляции

Дальше зашифрованный пакет нужно «завернуть» так, чтобы он прошёл через неуправляемую сеть:

|Ситуация|Инкапсуляция|
|---|---|
|Узлы в одном широковещательном домене (напр. два клиента в одной подсети)|протокол **IP/241**|
|Между узлами есть устройства сетевого уровня (маршрутизаторы/МЭ)|**IP + UDP**, по умолчанию порт **55777**|
|По UDP связаться не удалось|**TCP** (по умолчанию порт 80) — актуально для клиентов; между координаторами пока только UDP|

По служебным портам: `2046-2047` (UDP/TCP) — синхронизация между узлами ViPNet, `55777/UDP` — установление защищённого соединения по умолчанию, `5000-5001/TCP` — транспортный модуль MFTP (доставка справочников и ключей).

Особенность драйвера: **принимать** шифрованные пакеты он может на **любом** порту, а **отправлять** — всегда с порта, указанного в строке `port` конфигурации.

## Режимы протокола IPlir и накладные расходы

Сам `IPlir` умеет работать в трёх режимах: **туннельный** (шифруется исходный IP-пакет целиком), **транспортный** (заголовок IPlir добавляется после IP-заголовка) и **лёгкий туннель** (вариант транспортного с нюансами версионности). Настроить это у пользователя возможности нет — фактически всегда используется **туннельный**.

Заголовок `IPlir` — до 57 байт. Итого типовые накладные расходы:

- L3 VPN через интернет (UDP не запрещён) — около **65 байт**;
- L2 VPN (L2overIP) через выделенный канал — около **93 байт** (36 байт надстройки: 22 — EtherIP, +14 — исходный Ethernet-заголовок).

Эти накладные расходы важны для MTU: увеличенный пакет может фрагментироваться во внешней сети.

## Пошаговый путь между двумя координаторами (прямая схема)

Возьмём пример из конспекта: Coordinator 1 (`172.0.0.2`, внешний адрес `4.4.4.1`), Coordinator 2 (`172.0.1.2`, внешний адрес `4.4.4.2`), между ними «интернет» `4.4.4.0/24`.

1. Coordinator 1 хочет обратиться к Coordinator 2. Он использует `accessip` удалённого узла (напр. `172.0.1.2`).
2. Драйвер `iplir` на C1 по `accessip` понимает, что это защищённый узел, **шифрует пакет** и меняет адрес назначения на `firewallip` C2 = `4.4.4.2`.
3. Пакет инкапсулируется в **UDP 55777** и по таблице маршрутизации уходит на шлюз по умолчанию (внешний МЭ).
4. Внешний МЭ делает **NAT**: во внешнюю сеть уходит уже обмен между `4.4.4.1` и `4.4.4.2` по UDP 55777 — со стороны кажется, что два публичных адреса просто обмениваются трафиком.
5. МЭ на стороне C2 делает **статическую трансляцию** и перенаправляет пришедшее на `4.4.4.2` на внутренний `172.0.1.2`.
6. Драйвер C2 принимает пакет (на любом порту), **расшифровывает**, восстанавливает исходную адресацию и отдаёт пакет адресату. Ответ идёт по той же цепочке в обратном порядке.

На этом маршруте исходные IP-адреса защищённых узлов наружу не видны — их скрывает туннелирование, а сам обмен защищён криптографией (ГОСТ 28147-89 в 4-м поколении, «Магма»/«Кузнечик» — в 5-м).

## Сценарий с динамическим NAT и сервером соединений

Если один координатор (C2) стоит за **динамическим NAT**, инициативное соединение к нему извне невозможно. Тогда:

- C2 периодически (по умолчанию **раз в 25 секунд**) шлёт тестовые пакеты на `firewallip` координатора C1 — это держит сессию открытой на МЭ C2 (иначе она закроется за 1-5 минут).
- C1 в этой схеме выступает **сервером соединений**: он организует соединения между клиентами/координаторами по кратчайшему пути.
- Возможны варианты: направлять **весь** защищённый трафик через свой сервер соединений либо устанавливать прямое соединение (или через сервер соединений удалённой стороны).
- Если за МЭ много узлов, вместо источника `55777` после NAT может появиться любой порт из диапазона `1024-65535` — на стороне C1 этот порт фиксируется, и ответные пакеты идут именно на него.

Именно поэтому для межсетевого взаимодействия HW5 с сетью на Administrator требуется, чтобы **шлюзовый координатор был доступен напрямую, а не через сервер соединений**.

## Туннелирование сегментов за координаторами

Когда за координатором находятся целые подсети, их адреса прописываются в параметр **`tunnel`** конфигурации (настраивается в свойствах координатора, вкладка «Туннелирование»). Чтобы клиент добрался до ресурса, надо иметь **связи со всеми координаторами в цепочке** до него. Видимостью туннелируемых адресов управляет параметр `tunneldefault` в секции `[visibility]`: `real` (по реальным адресам), `auto`, `virtual` (по виртуальным). Режим `virtual`/`real` влияет на то, какой адрес используется как `accessip`, — и, соответственно, уйдёт ли пакет шифрованным или нет.

## Как контролировать прохождение трафика

- **`iplir ping <идентификатор>`** — перебирает все адреса узла (по UDP, порт 2046 внутри, наружу — шифруется и упаковывается в `port`, напр. 55777); ответ придёт **только от нужного защищённого узла**.
- **`inet ping <ip>`** — обычная проверка по таблице маршрутизации; ответить может **любой** узел с этим адресом, и пакет может уйти незашифрованным, если `accessip` стал виртуальным.
- **`iplir view`** — журнал IP-пакетов (по каждому интерфейсу): флаги `<`/`>` (исходящий/входящий), `C` — шифрованный, `D` — заблокированный, `B` — broadcast, `T` — транзитный, `R`/`N` — пакет под/после NAT. По умолчанию логируются только заблокированные; регистрацию пропущенных включают через `registerall`.

## Коротко общая картина

Трафик между координаторами проходит так: **драйвер iplir перехватывает IP-пакет → по `accessip` определяет защищённого адресата → шифрует и подменяет заголовок на `firewallip` → инкапсулирует (IP/241 в одном сегменте, иначе UDP 55777 или TCP) → отдаёт в сеть; на другой стороне всё происходит в обратную сторону после расшифровки.** А как именно стороны «находят» друг друга (статический NAT, динамический NAT через сервер соединений) — это уже определяется выбранным режимом подключения к внешней сети.

Если хотите, могу нарисовать схему этого пути для ваших конкретных адресов или собрать отдельную заметку «Путь пакета между координаторами» с этой раскладкой.
