# Принципы работы VPN ViPNet: идентификация, поиск адресов и выбор пути

**Цель темы:** понять, как два узла, которые ничего не знают о текущих IP-адресах друг друга, находят контакт и почему в одних топологиях соединение устанавливается напрямую, а в других — только через координатор-посредник.

## 1. Четыре функции координатора в ViPNet

Координатор — не просто «шифровальный ящик». В сети ViPNet он одновременно выполняет четыре роли:

|Функция|Что делает|Где «живёт»|
|---|---|---|
|**VPN-шлюз**|Шифрует/дешифрует трафик, L3 и L2 туннелирование|`iplir.conf`, справочники Prime|
|**Маршрутизатор VPN-пакетов**|Выбирает путь по **ViPNet ID**, а не по IP|Таблица связей из справочников|
|**Сервер IP-адресов**|Регистрирует и рассылает адреса и состояния защищённых узлов|Справочники, `client_pollinterval` / `server_pollinterval`|
|**Сервер соединений**|Сводит узлы, которые не могут связаться напрямую (NAT, разные подсети)|`[dynamic] forward_id`, `iplir option mode dynamic`|

Ключевая идея: **IP меняется, ViPNet ID — нет**. Маршрутизация защищённого трафика идёт по идентификатору, поэтому смена адреса узла не ломает связи.

## 2. Три адресных плоскости

Это главный источник путаницы. Различайте:

```
Приложение узла
   │  192.168.1.2 (виртуальный адрес удалённого узла)
   ▼
ViPNet-драйвер
   │  подменяет virtual → real, шифрует, добавляет ViPNet ID получателя
   ▼
Координатор →stalker UDP-пакет → другой координатор
   │  дешифрует, ID → реальный адрес, подменяет source на свой IP
   ▼
Открытый/защищённый узел назначения
```

|Плоскость|Пример|Где задаётся|Для чего|
|---|---|---|---|
|**ViPNet ID**|`0x15ea000b`|ViPNet Prime|Маршрутизация в сети ViPNet (4 байта: сеть 2 + узел 2)|
|**Адрес доступа**|`89.135.15.2:55777`|`accessiplist` / `iplir node access-point`|Куда UDP-пакет реально уходит в открытой сети|
|**Виртуальный IP**|`11.0.0.5`|Generator виртуальных адресов|Как приложение обращается к узлу при конфликте частных подсетей|

Подмена адреса обратно (`real` → `virtual`) происходит **только после успешной расшифровки** пакета ключами отправителя. Это защита от подмены источника.

Параметры трансляции адресов для уже защищённого трафика **изменить нельзя** — координатор всегда подставляет свой IP как источник.

## 3. Сервер IP-адресов и сервер соединений

### Сервер IP-адресов

Функциональность координатора по регистрации, рассылке и предоставлению сведений о состоянии защищённых узлов.

- При появлении сведений о новом клиенте координатор рассылает их связанным клиентам и координаторам.
- При взаимодействии с другой сетью ViPNet шлюзовой координатор получает состояние всех узлов своей сети, связанных с узлами другой сети.
- Для каждого ViPNet-клиента его сервер IP-адресов — это его координатор.
- Опрос: `client_pollinterval` = **300 с**, `server_pollinterval` = **900 с**. `server_pollinterval` **должен быть одинаковым у всех координаторов сети**, иначе статусы отображаются некорректно.

### Сервер соединений

Функциональность координатора, обеспечивающая соединение clients друг с другом, когда они в разных подсетях и не могут связаться напрямую. Для каждого узла сервером соединений является координатор, назначенный ему сервером IP-адресов.

```
Client A (за Dynamic NAT)
   │  UDP-пакеты к серверу соединений каждые 25 с (keepalive)
   ▼
HW-2 (статический режим, публичный IP)  ← сервер соединений
   │  пересылает пакеты дальше по UDP
   ▼
Client B / HW-1
```

> **Экспертный нюанс.** «Сервер соединений» — это не отдельная железка и не лицензия, а **функция**, включаемая на конкретном координаторе. Один координатор может одновременно быть сервером IP-адресов для своей сети и сервером соединений для чужих узлов за NAT.

> Сервер IP-адресов — реестр: регистрирует узлы, рассылает сведения об их адресах и состоянии, пользовательский трафик не пропускает. Сервер соединений — точка встречи/ретрансляции для узлов, которые не могут соединиться напрямую; через него трафик может проходить. Для клиента роль сервера соединений выполняет координатор, назначенный ему сервером IP-адресов; для координатора за динамическим NAT — координатор из `forward_id`.

## 3. Полная схема: шесть шагов от старта до трафика

```
1. Старт узла
   Узел знает: свой ID, свой ключ, адрес своего сервера IP-адресов
        │
        ▼
2. Регистрация  ───────────────►  СЕРВЕР IP-АДРЕСОВ
   (syslog type 3)                 реестр: ID → адреса, порт, метрики, состояние
        │                                    │
        │◄── 3. Рассылка состояния ──────────┘
        │      (type 1 — доступность, type 2 — отключение,
        │       type 50 — смена адреса, type 70 — подтверждение)
        ▼
3. Опрос адресов доступа узла-партнёра
   Пробы на все известные адреса с задержкой = метрике (мс)
   Побеждает адрес с наименьшей метрикой, который ответил
        │
        ├── прямой UDP проходит? ──────► 5a. ПРЯМОЙ КАНАЛ
        │                                     UDP 55777…56031
        │
        ├── NAT не пропускает входящие? ► 5b. ЧЕРЕЗ СЕРВЕР СОЕДИНЕНИЙ
        │                                     forward_id, keepalive 25 c
        │
        └── UDP блокируется? ──────────► 5c. TCP-ТУННЕЛЬ
                                              TCP 80 на сервер соединений
        ▼
4. Шифрованный трафик (ГОСТ), служебные пакеты, смена адреса — уведомлением
```

### Что узел знает на каждом шаге

|Вопрос|Кто отвечает|Где это лежит|Чем посмотреть|
|---|---|---|---|
|Кто я?|Ключи / Prime|`key-info`|`iplir info`, `iplir show key-info`|
|Какие адреса у партнёра?|Сервер IP-адресов + `accessiplist`|`[id]`|`iplir node <ID> show` → `Access-address table`|
|Какой адрес выбрать?|Метрики|`accessiplist`|та же таблица, колонка `Metric`|
|Кто поможет, если напрямую нельзя?|Сервер соединений|`[dynamic] forward_id`, `[id] proxyid`|`iplir option show`|
|Каким адресом меня видят?|`visibility`|`[id] visibility`, `[visibility]`|`iplir node <ID> show` → `Visibility`|

## 4. Четыре сценария подключения к внешней сети

|Сценарий|Когда|Режим|Команда / действие|
|---|---|---|---|
|**Напрямую**|Публичный IP на интерфейсе|static|`iplir option mode static`|
|**Через Static NAT**|Устройство NAT с проброшенными UDP-портами|static|`iplir option mode static` + правила NAT|
|**Через Dynamic NAT**|За NAT без фиксированного адреса, нужен доступный сервер соединений|dynamic|`iplir option mode dynamic <ViPNetID HW-сервера>`|
|**Каскад**|HW во внутреннем сегменте за другим HW|dynamic|`iplir option mode dynamic <ViPNetID вышестоящего HW>`|

### Static NAT

- Статический режим использует **255 UDP-портов: 55777–56031** по умолчанию.
- Начальный порт — параметр `port` собственной секции `[id]`, количество — `iplir option udp-ports-count`.
- На NAT-устройстве нужны правила и для исходящего (source NAT), и для входящего (destination NAT) направления.
- Если за одним NAT несколько координаторов — их стартовые порты **не должны пересекаться**.
- Узлам сети задаём ViPNetID HW как сервер соединений.

### Dynamic NAT

- Обязательно ну постоянно доступный сервер соединений в **статическом** режиме.
- HW периодически шлёт пакеты серверу, чтобы пробить NAT: `timeout` по умолчанию **25 с** (`iplir option keepalive-timeout`).
- Опции: `always_use_server` (по умолчанию `off`) — весь трафик extern через сервер; `port_auto_change` (по умолчанию `off`).

### TCP-туннель

Если провайдер блокирует UDP, клиент автоматически переходит на TCP-туннель своего сервера соединений (обычно порт 80).

```
# Сервер TCP-туннелей (роль по умолчанию)
hostname# iplir tcptunnel role server
hostname# iplir show tcptunnel-info
hostname# iplir tcptunnel server port 80
hostname# iplir tcptunnel server on

# Клиент (только в dynamic-режиме)
hostname# iplir tcptunnel role client
hostname# iplir tcptunnel client mode auto      # или forced
hostname# iplir tcptunnel client port 80
hostname# iplir tcptunnel client on
```

Возврат на UDP происходит по истечении тайм-аута служебных пакетов (по умолчанию 5 минут), после проверки соединения или смены IP-адреса. При TCP-туннеле клиенту **не приходят уведомления о рассинхронизации времени**.

### 5.1. Прямой доступ (`static`)

**Условия:** оба узла имеют маршрутизируемые (обычно публичные) адреса, UDP не блокируется.

```
hostname# iplir option mode static
hostname# iplir option show
```

- На интерфейсе, смотрящем в сторону внешней сети, `type = external`; остальные — `internal`.
- Открыть весь UDP-диапазон: по умолчанию **255 портов начиная с 55777** → `55777–56031`. Начальный порт — `port` в собственной секции `[id]`, количество — `iplir option udp-ports-count`.
- Если открыть только `55777`, соединение сначала работает, а после перехода на другой порт диапазона «ломается». Классическая ошибка.

### 5.2. Статический NAT (`static`)

**Условия:** координатор стоит за NAT «один-к-одному» с фиксированным публичным адресом.

На координаторе:

```
hostname# iplir option mode static
```

На NAT-устройстве нужны **два правила**:

|Направление|Что транслируется|
|---|---|
|SNAT (исходящее)|`внутренний_IP_координатора : диапазон_UDP` → `публичный_IP_NAT : тот же диапазон`|
|DNAT (входящее)|`публичный_IP_NAT : диапазон_UDP` → `внутренний_IP_координатора : диапазон_UDP`|

Правила должны покрывать **весь диапазон**, а не только стартовый порт.

**Несколько координаторов за одним NAT:** каждому — свой непересекающийся диапазон (например, `55777` и `56032`). Иначе DNAT не сможет различить, кому предназначен входящий пакет.

### 5.3. Динамический NAT (`dynamic`)

**Условия:** провайдерский NAT, адрес меняется, входящие соединения невозможны в принципе. Нужен постоянно доступный сервер соединений с публичным адресом, работающий в режиме `static`.

```
hostname# iplir option mode dynamic 0x15c8000a
hostname# iplir option keepalive-timeout 25
hostname# iplir option show
```

Что при этом должно быть в `iplir.conf`:

```
[dynamic]
dynamic_proxy = on
forward_id = 0x15c8000a          ; сервер соединений, доступный по публичному IP
always_use_server = on           ; весь трафик к внешним узлам — через него
timeout = 25                     ; keepalive, секунды
port_auto_change = off
```

Правила, которые надо помнить наизусть:

- **Все интерфейсы — `internal`.** В динамическом режиме `external` быть не должно.
- `proxyid` в собственной секции `[id]` = `0xfffffffe`.
- Keepalive каждые **25 секунд** держит «дырку» в NAT открытой; если NAT рвёт сессию раньше — соединение будет мигать.
- `always_use_server = off` (по умолчанию) означает: сначала попытки прямого соединения, и только потом ретрансляция. Для чистого динамического NAT это лишние 7–70 секунд и риск асимметрии, поэтому здесь обычно ставят `on`.
- `port_auto_change = on` включает автоматическую смену порта при недоступности сервера соединений — полезно, но требует, чтобы на сервере это тоже допускалось.

**Каскадное подключение** — частный случай динамического режима: координатор внутреннего сегмента указывает в `forward_id` вышестоящий координатор и тем самым получает автоматическую маршрутизацию защищённого трафика наружу.

### 5.4. TCP-туннель

**Условия:** UDP блокируется провайдером, но разрешён TCP (обычно 80/443).

Схема: клиент поднимает TCP-соединение до **своего сервера соединений**, который одновременно является **сервером TCP-туннелей**; сервер распаковывает пакеты и передаёт их дальше по UDP.

На сервере:

```
hostname# iplir show tcptunnel-info
hostname# iplir tcptunnel role server
hostname# iplir tcptunnel server port 80
hostname# iplir tcptunnel server on
```

На клиенте (только динамический режим):

```
hostname# iplir tcptunnel role client
hostname# iplir tcptunnel client mode auto      ; или forced
hostname# iplir tcptunnel client port 80
hostname# iplir tcptunnel client on
```

Ограничения и нюансы:

|Параметр|Значение|
|---|---|
|Порт по умолчанию|`80` (`tcptunnelport` в `[id]`)|
|Максимум туннелей|`100`|
|Режимы клиента|`auto` — включать при пропадании UDP; `forced` — всегда, когда возможно|
|Ограничение роли|Только для координаторов в режиме `dynamic`|
|Аппаратные ограничения|HW50 не поддерживает роль сервера TCP-туннелей|
|Публичный адрес|В собственной секции `[id]` сервера должен быть публичный адрес доступа|
|Рассинхронизация времени|Через TCP-туннель уведомления о рассинхронизации **не приходят**|

Возврат на UDP происходит после истечения тайм-аута служебных пакетов (в руководстве указано значение по умолчанию 5 минут), после проверки соединения или после смены IP-адреса.

> **Важно не путать таймеры.** `[dynamic] timeout = 25` — это keepalive до сервера соединений. «5 минут» из раздела про TCP-туннель — другой таймер (служебные пакеты). В документации эти значения соседствуют и выглядят противоречиво; на стенде проверяйте фактическое поведение, а не верьте одной цифре.

## 5. Адреса доступа и метрики каналов

Узел может иметь несколько адресов доступа. Приоритет определяется **метрикой в миллисекундах**.

```
hostname# iplir node 0x15ea000b access-point add 89.135.15.2 metric 1
hostname# iplir node 0x15ea000b access-point add 82.16.10.20 metric 200 port 55777
hostname# iplir node 0x15ea000b access-point delete 82.16.10.20
```

|Правило|Значение|
|---|---|
|Наименьшая метрика|Всегда выигрывает, если адрес доступен|
|Равные метрики / недоступен лучший|Побеждает адрес, быстрее ответивший на опрос|
|`auto`|Всегда на **100 мс больше** максимальной ручной метрики|
|Диапазон метрики|0–9999 мс|
|Рекомендуемая разница|Не менее **100 мс**|
|Переключение на резерв|**7–70 с**|
|После установки соединения|Другие адреса опрашиваются только при разрыве текущего|

Ручной адрес приоритетнее адреса из Prime. Чтобы использовать адрес из Prime, нужно явно изменить его метрику с `auto`.

### Полный формат `accessiplist`

```
accessiplist = <IP доступа>, <метрика>, <реальный IP>, <№ интерфейса>, <тип>, <порт>

accessiplist = 89.135.15.2, 1, 0.0.0.0, 0, auto
```

|Поле|Кто заполняет|
|---|---|
|IP доступа, метрика, порт|Администратор вручную или Prime|
|Реальный IP узла|Автоматически службой `iplircfg`|
|№ интерфейса|Автоматически, 0–255|
|Тип|`auto`, `manual`, `addrdoc` (из справочников Prime)|

Вручную задают только первые три поля. В каждой секции `[id]` параметров `accessiplist` может быть сколько угодно. Первый `accessiplist` должен совпадать с `firewallip`.

> Правка `iplir.conf` требует `iplir stop` → `iplir config` → `iplir start`. Команда `iplir node access-point` перезапуска не требует. Изменения через группы `iplir option` применяются с задержкой ~60 с.

## 6. Как это выглядит в `iplir.conf`

Цикл правки всегда один: `iplir stop` → `iplir config` → правка → `iplir start`.

|Секция|Роль в VPN|Ключевые параметры|
|---|---|---|
|`[adapter]`|Транспортные интерфейсы|`type` (`internal`/`external`), `allowtraffic`|
|`[id]`|Карточка узла|`id`, `ip`, `accessip`, `accessiplist`, `port`, `firewallip`, `proxyid`, `visibility`, `checkconnection_interval`|
|`[dynamic]`|Режим динамического NAT|`dynamic_proxy`, `forward_id`, `always_use_server`, `timeout`, `port_auto_change`|
|`[servers]`|Известные координаторы (нередактируемо)|`server = 0x..., имя`|
|`[virtualip]`|Генерация виртуальных адресов|`startvirtualip`, `maxvirtualip`, `starttunnelvirtualip`|
|`[visibility]`|Видимость по реальным/виртуальным адресам|`default`, `subnet_real`, `subnet_virtual`, `tunneldefault`|
|`[misc]`|Таймеры и общие параметры|`client_pollinterval`, `server_pollinterval`, `timediff`, `tcptunnel_establish`|

### Фрагмент: узел за динамическим NAT

```
[id]
id = 0x15ea000b
name = HW-Branch
ip = 192.168.10.1, 11.0.0.11
port = 55777
proxyid = 0xfffffffe

[dynamic]
dynamic_proxy = on
forward_id = 0x15c8000a
always_use_server = on
timeout = 25
port_auto_change = off
```

### Фрагмент: партнёр с двумя каналами

```
[id]
id = 0x15c8000a
ip = 203.0.113.10, 11.0.0.10
port = 55777
accessiplist = 203.0.113.10, 100, 55777
accessiplist = 198.51.100.10, 300, 55777
```

После `iplir start` служба сама допишет в каждую строку реальный IP интерфейса, его номер и тип регистрации — строка станет шестипольной:

```
accessiplist = 203.0.113.10, 100, 192.168.10.1, 1, addrdoc, 55777
```

> **Ловушка формата.** В руководстве по настройке ручная форма — `<IP>, <метрика>, [<порт>]` (порт третьим). В справочнике расширенная форма — шесть полей, где порт **шестой**. Не «дописывайте» поля вручную: легко сдвинуть порт. Дайте службе сделать это самой.

Тип регистрации в разных разделах документации называется по-разному: `addrdoc` (из справочников Prime) и `mgmt-center` (централизованно задан в Prime) — это один и тот же случай.

### `proxyid` — «кто мой ретранслятор», закодированный по секциям

|Секция|Значение|Смысл|
|---|---|---|
|Собственная|`0xfffffffe`|Узел за динамическим NAT (`dynamic_proxy = on`)|
|Собственная|`0`|Статический режим|
|Чужая|`0xfffffffe`|Этот координатор — сервер соединений для данного узла|
|Чужая|`0x...` (ID координатора)|Данный узел за динамическим NAT, его сервер — указанный координатор|

## 6. Виртуальные IP-адреса и видимость

По умолчанию два диапазона:

|Диапазон|Для кого|
|---|---|
|`11.0.0.1/8`|Узлы защищённой сети и одиночные туннелируемые узлы|
|`12.0.0.1/8`|Туннелируемые узлы (диапазоны)|

Настройка в `[virtualip]`: `startvirtualip`, `maxvirtualip`, `starttunnelvirtualip`. Маска только `/8` или `/16`, первый октет 1–239, последний 1–254.

**Внимание:** изменение диапазона приводит к перераспределению всех виртуальных адресов на HW.

Если у узла несколько IP, второй октет виртуального адреса увеличивается: `11.0.0.1`, `11.1.0.1`, `11.2.0.1`, …

### Приоритет видимости

```
1. visibility в секции [id] узла
2. subnet_real / subnet_virtual в [visibility] для сети узла
3. default в [visibility]
```

Для туннелируемых узлов: `tunnelvisibility` в `[id]` координатора → `tunneldefault` в `[visibility]`.

По умолчанию: узлы в одном broadcase-сегменте — по виртуальным адресам, туннелируемые узлы — по реальным, остальные — по виртуальным.

Два критичных правила:

1. При видимости по виртуальным адресам **обязателен валидный default-маршрут** (связь с темой 8).
2. Перед сменой видимости с виртуальной на реальную нужно сделать `inet ping` на виртуальный адрес узла — иначе доступ по реальному адресу пропадёт.

Любой диапазон виртуальных адресов пересекается с реальными адресами интернета. Конфликт с открытым ресурсом лечится сменой диапазона или прокси-сервером; узлы защищённой сети при прокси нужно указать исключениями.

## 7. L3-туннелирование

Туннелирование нужно, чтобы защитить трафик на опасном участке и дать доступ к открытому узлу через координатор.

```
hostname# iplir stop
hostname# iplir config
# в [misc]: tunnel_virt_assignment = auto | manual
# в собственной [id]: tunnel = 192.168.201.5-192.168.201.10
# в [id] удалённого координатора:
#   tunnel = 192.168.201.5-192.168.201.10 to 12.0.0.5-12.0.0.10
hostname# iplir start
```

|Параметр|Смысл|
|---|---|
|`tunnel`|Диапазон реальных адресов → при `manual` плюс виртуальный диапазон|
|`tunnel_virt_assignment = auto`|Виртуальные адреса назначаются автоматически; при исчерпании диапазона режим принудительно станет `manual`, а виртуальные адреса скопируют реальные|
|`exclude_from_tunnels`|Исключение адресов из туннеля; имеет приоритет над настройками Prime|
|`tunnel_local_networks`|`on` (по умолчанию) — к туннелируемым узлам только через их координатор; `off` — напрямую, если узел в локальной подсети|
|`usetunnel`|`on`/`off` в секции `[id]` — разрешить координатору туннелировать незащищённые узлы|

На всех туннелируемых узлах нужны статические маршруты через HW или HW как default gateway. По умолчанию трафик для всех туннелируемых узлов разрешён; при изменении — `firewall tunnel add ... pass` в обе стороны.

Настройки из Prime и локальные сливаются: новые адреса из Prime добавляются, локальные адреса, исчезнувшие в Prime, удаляются.

## 9. Что смотреть в CLI

|Команда|Что даёт|
|---|---|
|`iplir node list`|Все узлы, с которыми есть связь|
|`iplir ping <ViPNetID>`|Проверка соединения с узлом|
|`iplir node <ID> show`|Сведения об узле: адреса, метрики, состояние|
|`iplir option show`|Режим VPN, server connections, адреса, syslog, IP-forwarding, MSS, keepalive, sync time|
|`inet show interface state`|internal/external и enabled/disabled (тема 7)|
|`inet show routing`|Маршрут по умолчанию для виртуальной видимости (тема 8)|
|`iplir show tcptunnel-info`|`TCP server port`, роль и состояние|
|`iplir show l2overip config`|Порты и адреса L2OverIP|
|`iplir show key-info`|NSK, алгоритмы, suite (тема 2)|

Типовой порядок диагностики «узел не виден»:

1. `iplir ping <ID>` — есть ли вообще связь.
2. `iplir node <ID> show` — какой адрес доступа выбран и с какой метрикой.
3. `inet show routing` — есть ли default.
4. `iplir option show` — правильный ли режим (static/dynamic), не включён ли `always-use-server`.
5. `firewall local/vpn show` — не блокируется ли proto 97/UDP 55777.
6. Syslog: `iplir option syslog-level` (`off`, `critical`, `error`, `warning`, `info`, `debug`).

Если статус координатора отображается некорректно — проверьте `server_pollinterval`: он обязан совпадать у всех координаторов сети.

## 8. Диагностика по журналу

|Тип|Событие|Что означает на практике|
|---|---|---|
|`1`|Сообщение о доступности узла|Реестр «жив», узел периодически отмечается|
|`2`|Отключение узла от сервера IP-адресов|Узел ушёл/пропал — проверяйте канал, а не ключи|
|`3`|Первое обращение к серверу IP-адресов|Регистрация прошла: UDP, порт и адрес сервера верны|
|`5`|Проверка соединения (запрос)|Идёт опрос доступности адресов|
|`7`|Подтверждение получения сообщения|Служебный обмен работает|
|`23`|Первое обращение к серверу соединений (если он не сервер IP-адресов)|Ретрансляция настроена верно|
|`50`|Уведомление об изменении адреса доступа|Смена IP/NAT-rebinding обработана|
|`70`|Подтверждение уведомления об изменении адреса|Партнёр принял новый адрес|

Строка вида:

```
load natsettings for 0x3E130193: firewallip=192.168.166.105 port=55888 timeout=25 ...
```

означает, что узел получил NAT-настройки партнёра: внешний адрес, порт и keepalive. Если такая строка есть, а трафика нет — проблема не в обнаружении адресов, а в фильтрах, маршрутизации или времени.

**Порядок разбора:**

1. `iplir node list` — есть ли партнёр вообще.
2. `iplir ping <ID>` — отвечает ли.
3. `iplir node <ID> show` — какой адрес и метрика победили, какой режим.
4. Журнал: есть ли `type 3` / `type 23` / `type 50`.
5. UDP-диапазон и правила NAT/фильтров.
6. `iplir show tcptunnel-info` — не ушли ли в TCP-туннель «насовсем».

Если статус координатора отображается некорректно — проверьте `server_pollinterval`: он должен быть **одинаковым на всех координаторах** сети.

## 9. Типичные ошибки

|Симптом|Причина|Лечение|
|---|---|---|
|Узел за динамическим NAT не подключается ни к кому|`forward_id` указывает на приватный адрес или сервер сам за NAT|Сервер соединений обязан быть доступен по публичному IP и работать в `static`|
|Соединение периодически «мигает»|NAT закрывает сессию раньше 25 с; `always_use_server = off`|Проверить таймаут NAT, включить `always_use_server = on`|
|В динамическом режиме часть трафика не шифруется|Интерфейсу оставили `type = external`|В dynamic **все** интерфейсы — `internal`|
|Два координатора за одним NAT конфликтуют|Одинаковый UDP-диапазон|Разные стартовые порты, непересекающиеся диапазоны|
|Связь есть, потом пропадает|На файрволе открыт только `55777`, а не все 255 портов|Открыть весь диапазон `55777–56031`|
|Приоритетный канал не выбирается|Метрики равны или везде `auto`|Явные метрики с разницей ≥ 100 мс|
|Ручной адрес «перебит» адресом из Prime|У ручной записи не задана метрика|Задать конкретную метрику, а не `auto`|
|TCP-туннель включён «на всякий случай»|`forced` при работающем UDP|Вернуть `auto`; `forced` — только для диагностики|
|Клиенты не подключаются по TCP|У сервера нет публичного адреса в собственной секции|Добавить публичный адрес доступа|
|Соединение устанавливается, но данные не идут|Рассинхронизация времени (`timediff`), фильтры, маршрут|Проверить NTP и `timediff`; помнить, что TCP-туннель о рассинхронизации не предупреждает|
|После смены `virtual` → `real` узел стал недоступен|Не выполнили `inet ping` на виртуальный адрес до смены видимости|Сначала `inet ping` по виртуальному IP, затем менять видимость|

## 10. Чек-лист темы

1. `iplir info` показывает ожидаемые `My network ID` / `My host ID`, совпадающие с Prime.
2. Режим (`static`/`dynamic`) соответствует топологии, а не «так исторически сложилось».
3. `[adapter] type`: dynamic — все `internal`; static — внешний `external`, остальные `internal`.
4. UDP-диапазон уникален и открыт целиком (255 портов от стартового).
5. Для dynamic: `forward_id` ведёт на публично доступный сервер соединений.
6. Keepalive 25 с не режется NAT-устройством и провайдером.
7. Для static NAT: настроены и SNAT, и DNAT, покрывающие весь диапазон.
8. `accessiplist`: приоритетный адрес первый, метрики заданы, разница ≥ 100 мс.
9. `visibility` / `tunneldefault` соответствуют схеме адресации (кто кого видит).
10. TCP-туннель: роль, порт, режим `auto`, публичный адрес сервера.
11. `server_pollinterval` одинаков на всех координаторах.
12. Время синхронизировано; `timediff` не мал.
13. Проверено фактически: `iplir ping`, `iplir node <ID> show`, в журнале есть `type 3` и `type 23`.
14. Понимаете, какой именно адрес (реальный/виртуальный) и какой путь (direct/relay/TCP) использует каждая пара узлов.
