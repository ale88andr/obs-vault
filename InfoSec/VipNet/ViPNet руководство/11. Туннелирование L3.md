**Цель темы:** понять, как координатор берёт обычный IP-трафис от незащищённых узлов, шифрует его на участке между координаторами и выдаёт его «как usual» на другой стороне — без установки ViPNet-клиента на сами узлы.

## 1. Что такое L3-туннелирование

**L3-туннель** — это защита IP-пакетов на опасном участке сети путём перенаправления их через ViPNet Coordinator HW.

```
Обычный узел          HW-1                       HW-2          Обычный узел
192.168.2.3  ── IP ──► шифрует ── VPN/UDP ──► расшифровывает ──► 192.168.1.2
   (открытый)          туннелирует               туннелирует      (открытый)
                       ▲                         ▲
                       └─── зашифрованный участок ───┘
```

Ключевая идея: **сам узел ничего не знает про ViPNet**. Ему достаточно прописать HW как шлюз по умолчанию или статический маршрут. Всё шифрование делает координатор.

### Forget what distinguishes L3 from L2

|Уровень|Что переносится|Команды/механизм|Тема|
|---|---|---|---|
|**L3**|IP-пакеты|`tunnel`, `firewall tunnel`, маршруты|эта тема|
|**L2**|Ethernet-кадры|L2OverIP, `proto 97`, порты сегментов|тема 12|

Здесь **нет** L2OverIP, портов сегментов и `proto 97`. Работает обычная маршрутизация плюс криптография ViPNet.

## 2. Участники схемы

|Роль|Что делает|Где настраивается|
|---|---|---|
|**Туннелируемый узел**|Открытый компьютер/сервер, трафик которого надо защитить|Маршрут через HW; адрес в `tunnel`|
|**Туннелирующий координатор**|Принимает open-трафик, фильтрует, шифрует, отправляет в VPN|Своя секция `[id]`, параметр `tunnel`|
|**Удалённый координатор**|Расшифровывает и выдаёт трафик своей стороне|Своя секция `[id]`, параметр `tunnel`|
|**Защищённый узел**|Обычный ViPNet-узел или клиент с ViPNet Client|ViPNet ID, `firewall tunnel`, `visibility`|

Порядок инициации важён:

- адреса туннелируемых узлов задаются в **ViPNet Prime**;
- после рассылки справочников они появляются на связанных координаторах;
- чтобы защищённый узел мог дойти до открытого, между ними должна быть **связь в Prime**;
- локальная настройка допустима, если связи с Prime нет.

## 3. Адреса в туннеле

Различайте три вещи:

```
Реальный адрес туннелируемого узла:  192.168.201.7
Виртуальный адрес:                   12.0.0.7   (или 11.0.0.x для одиночных)
ViPNet ID защищённого узла:          0x00020203
```

|Что|Пример|Где видно|
|---|---|---|
|Реальный адрес открытого узла|`192.168.1.2`|`tunnel = 192.168.1.2-192.168.1.2`|
|Виртуальная копия|`12.0.0.1`|`[virtualip] starttunnelvirtualip`|
|ViPNet ID защищённого узла|`0x00020203`|`firewall tunnel`, `[id]`|

По умолчанию:

|Диапазон|Для кого|
|---|---|
|`11.0.0.1/8`|Узлы защищённой сети и **одиночные** туннелируемые узлы|
|`12.0.0.1/8`|Туннелируемые **диапазоны**|

Если реальные адреса разных офисов пересекаются, включают видимость туннелируемых узлов по виртуальным адресам — иначе маршруты становятся неоднозначными.

## 4. Параметры `iplir.conf`

### 4.1. `tunnel`

```
#(auto): задаём только реальный диапазон
tunnel = 192.168.201.5-192.168.201.10

#(manual): задаём реальный и виртуальный диапазоны
tunnel = 192.168.201.5-192.168.201.10 to 192.168.111.5-192.168.111.10
```

|Режим|Где задаётся|Правило|
|---|---|---|
|`auto`|`[misc] tunnel_virt_assignment=auto`|Пишем только `<ip1>-<ip2>`. Конечный виртуальный адрес считается автоматически.|
|`manual`|`[misc] tunnel_virt_assignment=manual`|Пишем `<ip1>-<ip2> to <ip3>`; `<ip4>` можно не указывать — он выводится из разницы.|

Ограничения:

- до **1000** диапазонов в одной секции `[id]`;
- в `auto` режиме строка вида `192.168.1.2-192.168.1.2` после старта службы автоматически дополняется дублирующимся адресом;
- в `manual` режиме **нет автоматической проверки пересечений** виртуальных диапазонов — проверяйте вручную.

Если в `auto` режиме виртуальные адреса закончились, следующие узлы получают в качестве виртуальных свои же реальные адреса, а режим принудительно переключается в `manual`. Это тревожный сигнал: пора расширять диапазон.

### 4.2. `exclude_from_tunnels`

```
exclude_from_tunnels = 192.168.201.7-192.168.201.7
```

Исключает адрес из туннеля. Правила:

|Правило|Значение|
|---|---|
|Где задаётся|Только в секции `[id]` **другого** координатора|
|Приоритет|Выше настроек из Prime|
|При обновлении|Не перезаписывается|
|Эффект|Трафик к этому адресу **не шифруется**|

Типичное применение: в диапазоне `192.168.201.5-192.168.201.10` один адрес должен остаться доступным напрямую, без VPN.

### 4.3. `usetunnel`

```
usetunnel = off
```

Настраивается **только в чужих секциях `[id]`**.

|Значение|Эффект|
|---|---|
|`on`|По умолчанию. Координатор туннелирует незащищённые узлы.|
|`off`|Трафик к его туннелируемым узлам **не шифруется**.|

Это частая причина симптома «доступ есть, но трафик открытый».

### 4.4. `tunnel_local_networks`

```
tunnel_local_networks = off
```

Задаётся в секции `[id]` связанного координатора.

|Значение|Поведение|
|---|---|
|`on`|По умолчанию. К туннелируемым узлам идём только через туннелирующего координатора.|
|`off`|Если узел стоит в локальной подсети, можно идти напрямую, минуя координатор.|

Используется, когда доступ к локальным туннелируемым узлам через координатора затруднён.

### 4.5. Видимость туннелируемых узлов

```
# в [id] туннелирующего координатора
tunnelvisibility = virtual

# hoặc в [visibility]
tunneldefault = real
```

Приоритет:

```
1. tunnelvisibility в секции [id] координатора
2. tunneldefault в секции [visibility]   (по умолчанию real)
```

Для обычных узлов приоритет иллюстрируется так:

```
visibility в [id] узла
        ↓
subnet_real / subnet_virtual в [visibility]
        ↓
default в [visibility]        (по умолчанию virtual)
```

### 4.6. Слияние с Prime

|Что происходит|Результат|
|---|---|
|Из Prime пришли **новые** tunnel-адреса|Добавляются к локальным|
|Локальный адрес исчез в Prime|Удаляется|
|`exclude_from_tunnels` задан локально|Остаётся и перекрывает Prime|
|Локальные настройки без связи с Prime|Работают, но могут быть заменены после получения справочников|

Вывод: **Prime — предпочтительный источник**. Локальная правка — это аварийный или «железный» сценарий.

## 5. Как это выглядит в CLI

### 5.1. Порядок правки

```
hostname# iplir stop
hostname# iplir config
# Ctrl+O — сохранить, Ctrl+X — выйти
hostname# iplir start
```

### 5.2. Что смотреть

|Команда|Что показывает|
|---|---|
|`iplir show config`|Фактическое содержимое `iplir.conf`|
|`iplir node <ViPNetID> show`|Адреса, метрики, Tunnel settings, видимость|
|`firewall tunnel show`|Таблица фильтров туннелируемых узлов|
|`firewall tunnel show <номер>`|Конкретный фильтр|
|`iplir ping <ViPNetID>`|Живая связь с защищённым узлом|
|`inet ping <IP>`|Проверка до opensource-узла или виртуального адреса|
|`inet show routing`|Маршруты и default gateway|
|`iplir option show`|`ipforwarding`, таймеры, UDP-порты, режим VPN|

В выводе `iplir node <ID> show` интересуют поля:

```
Use tunnel: on/off
Tunnel local networks: on/off
Tunnel visibility: real/virtual
Tunnel ranges: ...
Access-address table: IP, Port, Metric, Interface, Registration type
```

### 5.3. Фильтры туннелируемых узлов

По умолчанию в таблице `tunnel` есть разрешающие правила в обе стороны:

|Название|Src|Dst|Действие|
|---|---|---|---|
|To all tunnel nodes|`@any`|`@tunneledip`|`pass`|
|From all tunnel nodes|`@tunneledip`|`@any`|`pass`|
|Default tunnel rule|`@any`|`@any`|`drop`|

Если вы удалили или переопределили эти правила, восстанавливайте **обе стороны**:

```
hostname# firewall tunnel show
hostname# firewall tunnel delete <номер>
hostname# firewall tunnel add src 192.168.1.2 dst 0x00020202,0x00020203,0x00020204 pass
hostname# firewall tunnel add src 0x00020202,0x00020203,0x00020204 dst 192.168.1.2 pass
```

Можно ограничить не только узлы, но и сервис:

```
hostname# firewall tunnel add src 0x00020203,0x00020204 dst 192.168.1.2 tcp dport 80 pass
hostname# firewall tunnel add src 192.168.1.2 dst 0x00020203,0x00020204 tcp sport 80 pass
```

Правило для tunnel-фильтров:

> Если в качестве источника указан адрес защищённой сети, получатель должен быть открытым узлом, и наоборот.

## 6. Сценарий A: открытый узел ↔ открытый узел

Дано:

|Узел|Адрес|ViPNet ID|HW|
|---|---|---|---|
|Сервер данных|`192.168.1.2`|—|HW-1 `0x00010101`, `192.168.1.1`|
|Клиенты 1–3|`192.168.2.2-192.168.2.4`|—|HW-2 `0x00020201`, `192.168.2.1`|

Задача: трафик между офисами идёт зашифрованно, но ПО ViPNet на сервере и клиентах не ставится.

```
Клиенты 192.168.2.2-4 ── gw 192.168.2.1 ── HW-2 ══ VPN ══ HW-1 ── gw 192.168.1.1 ── Сервер 192.168.1.2
```

### На HW-1

```
hostname# iplir stop
hostname# iplir config
```

```
# собственная секция HW-1
[id]
id=0x00010101
tunnel=192.168.1.2-192.168.1.2

# секция HW-2
[id]
id=0x00020201
tunnel=192.168.2.2-192.168.2.4
```

```
hostname# iplir start
```

### На HW-2

```
# собственная секция HW-2
[id]
id=0x00020201
tunnel=192.168.2.2-192.168.2.4

# секция HW-1
[id]
id=0x00010101
tunnel=192.168.1.2-192.168.1.2
```

### Маршруты на открытых узлах

|Узел|Что задать|
|---|---|
|Сервер `192.168.1.2`|Default gateway `192.168.1.1` (HW-1)|
|Клиенты `192.168.2.2-4`|Default gateway `192.168.2.1` (HW-2)|

Без этого ответный трафик пойдёт мимо HW и останется открытым.

## 7. Сценарий B: защищённый узел ↔ открытый узел

Дано:

- сервер `192.168.1.2` остаётся открытым;
- на клиентах стоит ViPNet Client;
- ViPNet ID клиентов: `0x00020202`, `0x00020203`, `0x00020204`.

**Важно:** этот локальный сценарий реализуется только при `tunnel_virt_assignment=manual`.

```
[misc]
tunnel_virt_assignment=manual

[id]
id=0x00010101
tunnel=192.168.1.2-192.168.1.2 to 192.168.1.2-192.168.1.2
```

Фильтры:

```
hostname# firewall tunnel show
hostname# firewall tunnel delete <номер>
hostname# firewall tunnel add src 192.168.1.2 dst 0x00020202,0x00020203,0x00020204 pass
hostname# firewall tunnel add src 0x00020202,0x00020203,0x00020204 dst 192.168.1.2 pass
```

На клиентах ViPNet Client в качестве IP-адреса туннелирования указывается `192.168.1.2`.

Предпочтительный вариант: задать адрес туннелируемого сервера в Prime и разослать справочники на HW-1 и все связанные узлы.

## 8. Типичные ошибки

|Симптом|Причина|Лечение|
|---|---|---|
|Ping проходит, но TCP не поднимается|Фрагментация шифрованных пакетов|`mssdecrease` 20–40 на принимающем узле|
|Трафик идёт, но не шифруется|`usetunnel=off` в `[id]` удалённого координатора|Включить `on`|
|Ответ приходит мимо HW|Нет статического маршрута или default gateway на open-узле|Прописать HW как шлюз|
|Туннель не поднимается после правки|Редактировали при работающей службе|`stop → config → start`|
|Виртуальные адреса пересеклись|`manual`, нет автопроверки|Проверить диапазоны вручную|
|Адрес не туннелируется, хотя в диапазоне|Попал в `exclude_from_tunnels`|Убрать исключение|
|Конфликт реальных адресов локальной сети и удалённого туннеля|Одинаковые подсети|Включить `tunnelvisibility=virtual`|
|Доступ预后 пропал после смены видимости|Не сделали `inet ping` на виртуальный адрес|Пропинговать до смены `virtual → real`|
|ОдинDirection фильтр не работает|Создали правило только в одну сторону|Добавить зеркальное правило|
|Старое разрешающее правило «не отключается»|Блокирующий tunnel-фильтр не рвёт установленное соединение до истечения времени жизни|Дождаться переустановки сессии|
|Транзит не идёт вообще|`ipforwarding=off`|Вернуть `on` (тема 10)|
|В `auto` режиме адреса закончились|_range виртуальных адресов исчерпан|Расширить диапазон или перейти на `manual` осознанно|
|Настройки из Prime «перезатёрли» локальные|Локальная правка параметра, управляемого центром|Перенести изменение в Prime|
