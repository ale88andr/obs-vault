## 1.1. Одна фраза, из которой всё вытекает

**ViPNet — это наложенная (overlay) защищённая сеть поверх обычных IP-сетей, в которой узлы адресуются не IP-адресами, а идентификаторами ViPNet ID, а трафик между ними шифруется на сетевом уровне по ГОСТ.**

Из этого следуют три инварианта, которые надо помнить всегда:

1. **Адресация отделена от транспорта.** Узел имеет ViPNet ID (не меняется) и может менять реальный IP хоть каждый день.
2. **Связь существует только там, где она разрешена в справочнике.** Нет связи в справочнике — нет ключа — нет трафика. Это не «открытый интернет с шифрованием».
3. **Политика задаётся центром.** Структура сети, связи, ключи и политики безопасности формируются в ViPNet Prime и рассылаются на узлы; локальная настройка — вторична

|Плоскость|Что в ней|Чем задаётся|
|---|---|---|
|**Криптографическая**|ViPNet ID, ключи обмена, шифрование ГОСТ|ViPNet Prime (ключи, справочники)|
|**Транспортная**|реальные IP, UDP/TCP/IP-241, NAT, туннели|`iplir.conf`, команды `inet`, `iplir option`|
|**Управляющая**|связи, видимость, фильтры, политики|Prime + локальные команды/файлы|

Ошибка новичка — видеть только одну плоскость. «Пинг не идёт» может означать: нет связи в справочнике (крипто), неверный адрес доступа (транспорт) или блокирующий фильтр (управление).

## 1.2. Два пространства адресов

| Пространство       | Что это                                                                                    | Кто использует                                             |
| ------------------ | ------------------------------------------------------------------------------------------ | ---------------------------------------------------------- |
| **Реальный IP**    | адрес в физической сети (Ethernet, провайдер, NAT)                                         | маршрутизаторы, провайдеры                                 |
| **ViPNet ID**      | 4-байтовый идентификатор узла, в CLI пишется как `0x00010101`                              | сам ViPNet: маршрутизация защищённого трафика, выбор ключа |
| **Виртуальный IP** | «псевдо-IP» для приложений, привязанный к ViPNet ID или к реальному IP туннелируемого узла | приложения на защищённом узле                              |

> разделение на номер сети и номер узла (`My network ID` / `My host ID` в `iplir show key-info`); пример `0x15ea000b` = сеть `0x15ea`, узел `0x000b`.

#### Три адреса одного узла

|Адрес|Что это|Где виден|Меняется ли|
|---|---|---|---|
|**ViPNet ID**|4 байта: 2 байта номер сети + 2 байта номер узла; в CLI — `0x15ea000b`|`iplir info`, `iplir show config`, `iplir show key-info` (отдельно `My network ID` и `My host ID`)|практически нет (присваивается в Prime)|
|**Реальный IP**|адрес в физической сети|`ip = 10.0.14.101`|да, свободно|
|**Виртуальный IP**|адрес для приложений, локальный для каждого узла|`ip = <реальный>, <виртуальный>`|да, автоматически|

Ключевой нюанс: **виртуальные адреса назначаются каждым узлом самостоятельно** и не являются глобальными. База — `startvirtualip = 11.0.0.1` (секция `[virtualip]`), для диапазонов туннелируемых узлов — `12.0.0.1`. Поэтому «один и тот же» узел с точки зрения разных корреспондентов может иметь разные виртуальные адреса — это норма, а не ошибка.

Второй нюанс: **по умолчанию видимость узлов — по виртуальным адресам** (`[visibility] default = virtual`), а для туннелируемых — по реальным (`tunneldefault = real`). Это разные настройки, и их путают.

Зачем виртуальные IP: две локальные сети могут иметь одинаковую адресацию `192.168.1.0/24`. Приложения обращаются к «своему» виртуальному адресу, драйвер ViPNet подменяет его на реальный при отправке и обратно при приёме — **но только после успешной расшифровки пакета ключом отправителя**. Это одновременно решает конфликт адресов и даёт защиту от подмены адреса источника.

## 1.3. Типы узлов

|Узел|Что делает|Чего не делает|
|---|---|---|
|**Клиент**|конечная точка: шифрует/расшифровывает свой трафик|не маршрутизирует чужой трафик|
|**Координатор**|VPN-шлюз, маршрутизатор защищённых пакетов, сервер IP-адресов, сервер соединений, МЭ/NGFW|не является «просто роутером» — без ключей и справочников бесполезен|
|**Открытый узел**|обычный хост без ViPNet за координатором|не шифрует сам, его трафик защищает координатор|
|**ViPNet Prime**|центр управления: топология, связи, ключи, политики, обновления, мониторинг|не передаёт пользовательский трафик|

Координатор — это не «один сервис», а набор ролей. В документации явно перечислены:

- **VPN-шлюз** — туннели L3 и L2, инкапсуляция в UDP, TCP и IP/241 (протокол 241).
- **Маршрутизатор VPN-пакетов** — доставка по ViPNet ID между сетями.
- **Сервер IP-адресов** — сообщает клиентам адреса и параметры доступа других узлов.
- **Сервер соединений** — помогает клиентам из разных подсетей соединиться, когда напрямую нельзя (в т.ч. TCP-туннель при блокировке UDP).
- **МЭ/NGFW** — SPI, DPI, IPS, NAT, фильтрация по пользователям/URL/GeoIP.
- **Сетевые службы** — DHCP, DNS, NTP, AD/LDAP, Captive Portal.
- **Кластер** — отказоустойчивость (активный/пассивный узел, синхронизация фильтров и сессий, виртуальные MAC).

> координатор — это **набор служб**, а не одна. Отсюда команды вида `service vpn start/stop`, `iplir start/stop`, отдельные `service dhcp`, `service dns`, `service snmp`, `service user-control`. Понимание «какая служба за что отвечает» — половина диагностики.

## 1.4. Как реально идёт пакет

```
Клиент A(ID 0x00010101)          Координатор(ID 0x00010201)      Клиент B(ID 0x00010301)
      │                                       │                           │
 1. приложение → виртуальный IP B             │                           │
 2. драйвер: ID получателя в открытую часть,  │                           │
    полезная нагрузка — ГОСТ-CFB ключом A–B   │                           │
 3. отправка: UDP 55777… (диапазон 255)       │                           │
    или TCP-туннель (порт 80)                 │                           │
      └──────────────► │ 4. проверка связи A–B по справочнику             │
                       │ 5. фильтры (защищённый трафик)                   │
                       │ 6. маршрут по ID B                               │
                       └──────────────────────────────────────►│ 7. расшифровка
                                                              │ 8. ID → вирт. IP
```

Что здесь принципиально:

- **Открытая часть пакета** содержит ID получателя — его видит провайдер. **Содержимое** — нет. Поэтому ViPNet спокойно работает через NAT и не требует «белого» IP у каждого клиента.
- **Ключ обмена** — симметричный, существует персонально для пары «узел A ↔ узел B» (или A ↔ координатор). Он приходит в дистрибутиве ключей, сгенерированном в ViPNet Prime.
- **Координатор не «доверенный посредник» в смысле TLS**: он маршрутизирует уже зашифрованные пакеты и одновременно применяет к ним политику МЭ. Расшифровка на координаторе происходит в сценариях шлюза (L3-туннель открытых узлов, SSL-инспекция и т.п.), но не является обязательной для транзита «клиент–клиент».
- **UDP 55777** — порт по умолчанию; если провайдер режет UDP, используется **TCP-туннель через сервер соединений**.

Что закреплено на каждом шаге:

1. **Шифрование** — `ciphertype = gost` (единственное значение), на практике `GOST-CFB` — это подтверждает вывод `iplir show ciphertype`: `GOST-CFB: Cipher Feedback Mode`.
2. **Формат пакета** — `packettype = 4.1` (по умолчанию) или `4.0` для совместимости со старыми узлами. Входящие пакеты драйвер распознаёт автоматически.
3. **Защита от повторов/рассинхронизации** — `timediff` (по умолчанию **7200 с**): если время отправки отличается от времени приёма сильнее, пакет отбрасывается. Отсюда требование к NTP.
4. **Транспорт** — UDP-диапазон из 255 портов от 55777 (`iplir option udp-ports-count`), IP-протокол № 241, TCP-туннель (по умолчанию **порт 80**, `tcptunnel_establish = off`).
5. **Целостность адреса** — ID получателя в открытой части защищён от подмены; виртуальный адрес отправителя подставляется только после успешной расшифровки.

#### Как координаторы находят друг друга по ViPNet ID

ID — это не имя, которое кто-то резолвит, а ключ к записи в локальной таблице соответствий «ID → адреса доступа». Таблица приходит из справочников ViPNet Prime и лежит в `iplir.conf` в секциях `[id]`. Никакого broadcast, ARP или «опроса сети» нет.

##### Что координатор знает заранее

Для каждого связанного узла в `iplir.conf` есть секция `[id]`:

```
[id]
id      = 0x00020201
name    = Coordinator 2
ip      = 203.0.113.10, 10.1.0.5     # реальный, виртуальный
port    = 55777
accessiplist = 203.0.113.10, 5, 203.0.113.10, 1, addrdoc, 55777
```

`accessiplist` — это и есть «список, куда стучаться»: IP-адрес доступа, метрика, реальный IP узла, номер интерфейса, тип регистрации (`auto` / `manual` / `addrdoc`) и порт. Первый адрес в списке — самый приоритетный; при обновлении адресов приоритет пересчитывается автоматически.

##### Пять шагов поиска

1. **Поиск записи.** ID разбирается на номер сети и номер узла (в `iplir show key-info` они выводятся отдельно: `My network ID`, `My host ID`). По номеру сети координатор понимает, к какой сети относится адресат, по номеру узла — конкретную секцию `[id]`.
2. **Выбор адреса.** Из нескольких адресов доступа по метрике выбирается приоритетный.
3. **Проверка доступности.** Обмен служебными сообщениями: узел при включении и далее периодически рассылает сообщение о доступности (в журнале — `type 1`), проверка соединения — `type 5`. Периодичность: для координаторов `checkconnection_interval` (`20–3600` сек, если задан) или `server_pollinterval` (по умолчанию `900` сек); для клиентов — `client_pollinterval` (300 с). Отдельно `iplir node <id> availability-monitoring on` включает мониторинг доступности с SNMP-уведомлениями (по умолчанию **off**).
4. **Отправка.** UDP на выбранный `IP:порт` либо IP-протокол 241. В открытой части — ID получателя, который защищён от подмены; содержимое зашифровано ключом обмена пары A–B.
5. **Фиксация результата.** Текущий используемый адрес виден как нередактируемый `accessip`. Если адрес перестал работать — координатор пробует альтернативный из списка.

##### Кто сообщает координаторам новые адреса

Функция **сервер IP-адресов**. Узел при подключении регистрируется на своём координаторе; тот рассылает сведения об изменившихся адресах связанным клиентам и координаторам. Отсюда сообщения `type 3` (первое обращение к серверу IP-адресов), `type 50` (уведомление об изменении адреса) и `type 70` (подтверждение).

То есть цепочка такая:

```
клиент сменил IP → зарегистрировался на своём координаторе (сервер IP-адресов)
      → координатор разослал уведомление связанным узлам и координаторам
            → они обновили accessiplist/accessip и продолжили обмен
```


## 1.5. Четыре транспортных сценария

|Сценарий|Признак|Ключевые параметры|
|---|---|---|
|**Прямой доступ**|у узла есть доступный IP|`ip` в секции `[id]`, `port`|
|**Статический NAT**|фиксированный внешний адрес|`[adapter] type = external` для внешнего интерфейса, остальные `internal`; правило DNAT на порт диапазона|
|**Динамический NAT**|узел сам за NAT, адрес неизвестен|`[dynamic] dynamic_proxy = on`, `forward_id = <ID сервера соединений>`, `timeout = 25`, `always_use_server`; **все** интерфейсы `type = internal`|
|**TCP-туннель**|UDP заблокирован провайдером|`tcptunnel_establish = on`; роль `client`/`server` (`iplir show tcptunnel-info`), режимы `auto`/`forced`, до 100 туннелей|

Практический вывод: **одно и то же устройство нельзя «наполовину» перевести в динамический NAT** — тип интерфейсов меняется целиком, иначе координатор просто не соберёт транспорт.

## 1.6. Кого и как узел «видит»

|Параметр|Смысл|Значение по умолчанию|
|---|---|---|
|`visibility` в `[id]`|видимость конкретного узла: `real` / `virtual`|по `[visibility] default`|
|`[visibility] default`|видимость всех узлов|`virtual`|
|`subnet_real` / `subnet_virtual`|видимость по номерам сетей ViPNet|не заданы|
|`tunnelvisibility`|видимость узлов, туннелируемых координатором|по `tunneldefault`|
|`tunneldefault`|видимость туннелируемых по умолчанию|`real`|
|`usetunnel`|туннелировать ли открытые узлы через этот координатор|`on`|
|`blockforward`|блокировать транзит в сторону узла|`off`|
|`exclude_from_tunnels`|исключения из туннелируемых диапазонов (приоритет выше настроек Prime)|—|
|`tunnel = 192.168.0.1-192.168.0.100 to 192.120.0.1`|сопоставление реального диапазона виртуальному|режим `auto`/`manual` (`tunnel_virt_assignment`)|

Это ровно тот слой, из-за которого возникают «странные» симптомы: доступ по реальному адресу работает, по виртуальному — нет (и наоборот), или часть подсети туннелируется, а часть — нет.

## 1.7. Где модель хранится физически

Всё, что описывает защищённую сеть, лежит в **`iplir.conf`** (и в `iplir.conf-<интерфейс>`):

|Секция|Содержимое|
|---|---|
|`[adapter]`|интерфейсы: `allowtraffic`, `type` (internal/external)|
|`[id]`|по секции на каждый связанный узел: `ip`, `port`, `accessiplist`, `tunnel`, `visibility`, `blockforward`, `proxyid`, `firewallip`|
|`[dynamic]`|динамический NAT: `dynamic_proxy`, `forward_id`, `timeout`, `always_use_server`, `port_auto_change`|
|`[misc]`|`ciphertype`, `packettype`, `ipforwarding`, `timediff`, `mssdecrease`, `tcptunnel_establish`, таймеры опроса|
|`[servers]`|список известных координаторов|
|`[virtualip]`|`startvirtualip`, `maxvirtualip`, `starttunnelvirtualip`|
|`[visibility]`|`default`, `subnet_real`, `subnet_virtual`, `tunneldefault`|

Правильный цикл правки: `iplir stop` → `iplir config` → правка → `iplir start`. И только `iplir.conf`; `iplir.db-<интерфейс>` — это журнал, его не редактируют.

## 1.8. Дефолты, которые обязан знать администратор

|Параметр|Значение|Почему важно|
|---|---|---|
|UDP-порты|255 шт., начало 55777|конфликт диапазонов за одним NAT|
|TCP-туннель|порт 80, выключен|«UDP режут» — включать осознанно|
|`timediff`|7200 с|без NTP пакеты молча отбрасываются|
|`client_pollinterval`|300 с|скорость обнаружения «клиент пропал»|
|`server_pollinterval`|900 с|то же для координаторов|
|`ifcheck_timeout`|периодическая сверка интерфейсов|изменение IP подхватывается автоматически|
|`ipforwarding`|`on`|при `off` не работают транзит и туннели|
|`mssdecrease`|0|лечит «ping есть, TCP не открывается» при фрагментации|
|`msg_compress_level`|3|выше 5 не рекомендуется на нагрузке|
|`startvirtualip`|11.0.0.1|конфликт с реальной сетью 11.0.0.0/8|

## 1.9. Шпаргалка: посмотреть модель на живом устройстве

```
hostname> iplir info                 # свой узел, сеть, версия, туннели, статистика фильтрации
hostname> iplir show config          # весь iplir.conf (Q — выход)
hostname> iplir show config eth0     # конфиг интерфейса
hostname> iplir show adapters        # активные интерфейсы и allowtraffic
hostname> iplir show ciphertype      # GOST-CFB
hostname> iplir show key-info        # ключ защиты обновлений, network/host ID, crypto suites
hostname> iplir show firewall status # лимиты и таймауты соединений
hostname> iplir show tcptunnel-info  # роль, порт 80, режим auto/forced
hostname> service vpn show status    # подсистема VPN и автозапуск
```

Пять команд из этого списка дают 80 % ответов на вопрос «почему не работает» ещё до чтения журналов.

## 1.10. Чем это не является

|Заблуждение|Реальность|
|---|---|
|«ViPNet = IPsec»|Свой протокол: адресация по ID, симметричные ключи из дистрибутива, политика из Prime, встроенный NGFW|
|«SSL-VPN»|Защита на сетевом уровне, прозрачна для приложений|
|«Координатор всё расшифровывает»|Трафик «клиент–клиент» идёт end-to-end; координатор расшифровывает только в сценариях шлюза (открытые узлы, L2, SSL-инспекция, прикладные протоколы)|
|«Ключи настраиваются локально»|Ключи формирует Prime по матрице связей; локально — только транспорт и часть политик|
|«ID — это просто имя»|ID — адрес маршрутизации и признак выбора ключа; он защищён от подмены|
|«Порт один — 55777»|Диапазон 255 портов; за одним NAT диапазоны должны различаться|
