
**Цель темы:** понять, как два ViPNet Coordinator HW работают как единый шлюз: кто является активным, как обнаруживается сбой, что именно синхронизируется между узлами и почему ошибка в `failover.ini` приводит к циклическому переключению.

**Источники:** «Настройка с помощью CLI», с. 324–343, 421; «Справочник команд и конфигурационных файлов», с. 45–52, 583–590.

## 1. Два уровня системы защиты от сбоев

Система защиты от сбоев состоит из **watchdog-драйвера `itcswd`** и **службы `failoverd`**.

### 1.1. Одиночный режим (по умолчанию)

```
itcswd  ── следит ──► failoverd ──► iplir, mftp, webgui, uc, controld, aad, licd, ...
   │                      ▲
   └── перезагрузка       └── сообщения «я жив» от каждой службы
       при пропаже
       сообщений
```

- Драйвер следит за `failoverd`.
- `failoverd` следит за остальными службами и драйверами.
- Если служба перестала отвечать — корректная остановка, затем принудительный рестарт.
- После **пяти неудачных перезапусков подряд** служба считается неработоспособной и система перезагружается.
- Управляется параметром `reboot` в секции `[misc]` файла `failover.ini`.

### 1.2. Режим кластера

Кластер — это **два HW или VA с одинаковой платформой и версией ПО**. Для VA дополнительно должны совпадать emulated-параметры: количество CPU, ОЗУ, сетевых интерфейсов.

|Роль|Поведение|
|---|---|
|**Активный узел**|Выполняет функции координатора: VPN, маршрутизация, фильтры, MFTP, веб-интерфейс|
|**Пассивный узел**|Находится в ожидании; его резервируемые интерфейсы **не имеют кластерных IP**|

**В кластере не поддерживаются Wi-Fi и 3G** — отключите их до развёртывания.

## 2. Интерфейсы кластера

Различайте три категории. Их легко путать, особенно `activeip` в разных секциях.

```
                        Ethernet-кабель (синхронизация)
              ┌──────────────────────────────────────────────┐
              │                                              │
      ┌───────┴────────┐                            ┌────────┴───────┐
      │   HW-1 ACTIVE  │                            │  HW-2 PASSIVE  │
      │                │                            │                │
      │ eth0 172.16.10.1   ◄──── sync ────►   eth0 172.16.10.2       │
      │                |                            │                |
      │ eth1 192.168.10.50/24  ◄─ кластерный IP     │ eth1 без IP    │
      │ eth2 80.251.137.40/24  ◄─ кластерный IP     │ eth2 без IP    │
      └───────┬────────┘                            └────────┬───────┘
              │                                              │
       внутренняя сеть                                внешняя сеть
       testip 192.168.10.1                            testip 80.251.137.80
```

| Категория                   | Что это                                                                 | Где                                 |
| --------------------------- | ----------------------------------------------------------------------- | ----------------------------------- |
| **Резервируемый интерфейс** | Интерфейс, который будет управляться системой защиты от сбоев           | Секции `[channel]` в `failover.ini` |
| **Интерфейс кластера**      | Резервируемый интерфейс **активного** узла; имеет общий для кластера IP | Параметр `activeip` в `[channel]`   |
| **Интерфейс синхронизации** | Прямое соединение двух узлов; не резервируется                          | Параметр `device` в `[sendconfig]`  |

Ключевое свойство: **кластерный IP всегда принадлежит активному узлу**. При переключении пассивный узел получает эти адреса, а бывший активный их сбрасывает.

Через интерфейс синхронизации передаются:

- пакеты синхронизации ролей — защита от ситуации «оба активны»;
- копии MFTP-конвертов;
- конфигурационные файлы и журналы;
- справочники, ключи, лицензии.

Передача идёт **в открытом виде** через временный каталог с проверкой полной передачи группы файлов. Поэтому интерфейс синхронизации должен быть физическим, выделенным и защищённым физически.

## 3. Как обнаруживается сбой

Это сердце темы. Существуют три независимых механизма.

### 3.1. Пассивный узел следит за активным (DAD ARP)

```
 Пассивный                         Активный
     │ ── ARP-запрос на activeip ──► │
     │ ◄── ARP-ответ ─────────────── │   актив жив
     │                               │
     │ ── ARP-запрос на activeip ──► │
     │        нет ответа             │   актив пропал/перезагрузился
     ▼                               ▼
 становится активным             уходит в пассивный
```

- Пассивный каждые `checktime` секунд посылает ARP-запрос на обнаружение дублирующего IP (режим **DAD**).
- Ответ есть — счётчик сбоев обнуляется.
- Нет ответа ни от одного `activeip` — счётчик растёт; при достижении `activeretries` узел становится активным.

> Увеличение времени ожидания ARP-ответа увеличивает время перехода пассивного узла в активный.

Максимальное время обнаружения падения активного:

```
checktime + (timeout × activeretries)
```

### 3.2. Активный узел следит за своими интерфейсами

```
 за checktime секунд был IP-трафик? ── да ──► интерфейс живой, счётчик = 0
                  │
                  нет (checkonlyidle = yes)
                  ▼
 эхо-запросы на testip ── есть ответ ──► счётчик = 0
                  │
                  нет ответа
                  ▼
 счётчик +1 ──► при channelretries ──► интерфейс неработоспособен ──► переключение
```

- При `checkonlyidle=yes` (по умолчанию) пинги посылаются **только если за период опроса не было ни одного входящего/исходящего пакета**.
- При `checkonlyidle=no` пинги идут постоянно.
- Счётчик обнуляется, если пришёл хотя бы один ответ или появился трафик.

Максимальное время определения неработоспособности интерфейса:

```
checktime + (timeout × channelretries)
```

### 3.3. Потеря физического соединения (`testdevice`)

`testdevice` контролирует состояние **физического** линка. При потере соединения переключение происходит примерно за **3 секунды**, без ожидания счётчиков.

Ограничения:

- только физические интерфейсы `eth`;
- нельзя `bond`, alias (`eth0:1`), VLAN, `localhost`;
- можно указать физический интерфейс, который является trunk для VLAN;
- одна секция `[channel]` — не более одного `testdevice`.

> **Не更改** параметры интерфейса, указанного в `testdevice`, при запущенном `failoverd` в режиме кластера — это воспринимается как потеря линка и вызовет переключение.

### 3.4. Что НЕ синхронизируется при переключении

|Не синхронизируется|Последствие|
|---|---|
|Сессии, к которым применено правило NAT источника|Разрыв此类 соединений|
|Журнал IP-пакетов и его настройки|Журнал не «переезжает» на новый активный узел|
|BGP-сессии|Восстановление и построение маршрутов занимает **1–3 минуты**|
|Открытые DNS-сессии|Могут прерваться даже при `syncconnections=yes`|
|Защищённые соединения по TCP-туннелям|Могут прерваться|
|Локальные соединения, где HW является источником/получателем|Могут прерваться|
|Соединения прикладных протоколов|Могут прерваться; частично лечится `syncalgtcp=yes`|

## 4. Файл `failover.ini`

Правка только через:

```
hostname# failover stop
hostname# failover config edit
# Ctrl+O — сохранить, Ctrl+X — выйти
hostname# failover start
```

Изменения применяются **только после перезапуска `failoverd`**.

### 4.1. Секция `[channel]`

Одна секция на каждый резервируемый интерфейс. Параметры интерпретируются **только в режиме кластера**. Чтобы снять интерфейс с контроля, удалите его секцию.

|Параметр|Назначение|
|---|---|
|`device`|Имя интерфейса, например `eth1`. На обоих узлах для одной сети имена должны совпадать|
|`activeip`|IP/маска, которые интерфейс получит в активном режиме. CIDR или прямая маска; после старта маска переписывается в CIDR|
|`testip`|Стабильный объект сети для echo-проверки. Можно несколько; сбой — когда нет ответа **ни от одного**|
|`testdevice`|Физический интерфейс для контроля линка (необязательный)|
|`ident`|Текстовый идентификатор сети. Для пар интерфейсов, подключённых к одной сети, должен совпадать|
|`checkonlyidle`|`yes` — пинги только при отсутствии трафика; `no` — постоянно|
|`usevirtualmac`|`yes` — использовать виртуальный MAC на активном узле; `no` по умолчанию|

Пример пары интерфейсов на обоих узлах:

```
[channel]
device = eth1
activeip = 192.168.10.50/24
testip = 192.168.10.1
testdevice = eth1
ident = internal
checkonlyidle = yes

[channel]
device = eth2
activeip = 80.251.137.40/24
testip = 80.251.137.80
testdevice = eth2
ident = external
checkonlyidle = no
usevirtualmac = yes
```

Правила для `testip`:

- у каждого `[channel]` должен быть **свой адрес из подсети этого интерфейса**;
- одинаковый `testip` в нескольких секциях — проверяется только **первый** интерфейс в файле;
- адрес вне подсети требует статического маршрута или default gateway;
- нельзя `127.0.0.1` — реальной проверки не будет;
- не используйте один и тот же адрес одновременно в DGD и `testip` — возможны циклические переключения;
- **недоступный `testip` в любой секции `[channel]` может вызвать циклическое переключение кластера**.

### 4.2. Виртуальные MAC-адреса

Виртуальный MAC ускоряет восстановление связи после failover: ARP-таблицы соседей не нужно переучивать.

|Свойство|Правило|
|---|---|
|Генерация|На основе `virtualmacprefix` из `[network]`; 2–5-й октеты — активный IP в hex, 6-й — `0`|
|Пример|Для `10.20.2.1` и `virtualmacprefix=39` получается `9e:0a:14:02:01:00`|
|Симметрия|`virtualmacprefix` должен совпадать на обоих узлах|
|Поведение|На активном — виртуальный MAC; после ухода в passive восстанавливается аппаратный MAC|
|Запрет|Нельзя на `bond` и alias-интерфейсах (`eth0:1`)|
|Коммутатор|Разрешить **два MAC на одном Ethernet-порту**; port-security не должен блокировать смену MAC|
|Откат|Если `usevirtualmac` был включён, а затем выключен, MAC может остаться виртуальным до перезагрузки — `machine reboot`|

### 4.3. Секция `[network]`

Все параметры работают только в кластере; рекомендуется идентичная настройка обоих узлов.

|Параметр|По умолчанию|Смысл|
|---|---|---|
|`checktime`|10|Период опроса, сек|
|`timeout`|2|Время ожидания ответа, сек. Должно быть **меньше** `checktime`|
|`activeretries`|3|Попыток опроса активного пассивным узлом|
|`channelretries`|3|Попыток опроса интерфейса перед признанием его неработоспособным|
|`synctime`|5|Период отправки синхронизационных пакетов, сек|
|`fastdown`|`yes`|Принудительно выключать интерфейсы перед перезагрузкой: быстрее failover, но завершение сетевых служб может быть некорректным|
|`virtualmacprefix`|39|Основа для расчёта первого октета виртуального MAC|

### 4.4. Секция `[misc]`

|Параметр|По умолчанию|Смысл|
|---|---|---|
|`reboot`|`yes`|Регистрация в watchdog и перезагрузка при невозможности восстановить службу/драйвер|
|`syncconnections`|`no`|Синхронизация сетевых соединений; должно быть `yes` **на обоих узлах**|
|`syncalgtcp`|`no`|Синхронизация сессий DNS, FTP, H.323, SCCP, SIP|
|`syncdatetime`|`yes`|Активный передаёт пассивному время и часовой пояс; значения должны совпадать|
|`maxjournal`|без ограничения|Хранение записей журнала переключений, дней|
|`interclustermtu`|1500|MTU интерфейсов синхронизации; для аппаратных платформ рекомендуется **9000**|

Не редактируются: `activeconfig`, `passiveconfig` — путь к конфигурации управляющей службы, по умолчанию `/etc/iplirpsw`.

### 4.5. Секция `[sendconfig]`

Отвечает за резервирование файлов с активного узла на пассивный.

|Параметр|По умолчанию|Смысл|
|---|---|---|
|`device`|—|Имя интерфейса синхронизации **текущего** узла|
|`activeip`|—|IP интерфейса синхронизации **другого** узла. Внимание: значение разное на HW-1 и HW-2|
|`port`|10090|Порт, на котором активный ждёт пассивного|
|`connectport`|= `port`|Порт пассивного при приёме файлов; используется также для проверки доступности интерфейсов активного — не меняйте без нужды|
|`sendtime`|60|Период резервирования, сек|
|`config`|`yes`|Группа конфигурационных файлов|
|`keys`|`yes`|Группа справочников, ключей, лицензий|
|`journals`|`yes`|Группа файлов журналов|
|`file`|—|Дополнительный файл, не входящий в группы; до 1 Мбайт|

Состав групп:

|Группа|Что входит|
|---|---|
|`config`|`iplir.conf`, `iplir.conf-<интерфейс>` кроме синхронизации, `mftp.conf`, пользовательские и пришедшие из Prime фильтры/NAT, настройки L2OverIP, `*.crg`, статические маршруты, служебные файлы|
|`keys`|Справочники, ключи, лицензии|
|`journals`|Журналы IP-пакетов интерфейсов кроме синхронизации, журнал конвертов MFTP, служебные журналы|

Пассивный в каждом цикле сначала запрашивает список файлов групп, затем инициирует передачу. Резервирование групп идёт только при запущенных `iplircfg` и `mftpd` на активном узле. **Отключать группы не рекомендуется.**

Запрещено использовать alias и bond в качестве `device`.

### 4.6. Секция `[debug]`

|Параметр|Значение|
|---|---|
|`debuglevel`|−1…4, по умолчанию **3**; −1 выключает журнал; 4 — только по рекомендации ИнфоТеКС|
|`debuglogfile`|`syslog:<facility.level>`, например `syslog:daemon.debug`; facility: `kern`, `user`, `daemon`; level: `err`, `info`, `debug`|

В исполнениях с одним диском по умолчанию уровень **1**, а при локальном протоколировании доступны уровни −1…3.

## 6. Как это выглядит в CLI

### 6.1. Команды группы `failover`

|Команда|Что делает|
|---|---|
|`failover config edit`|Открыть `failover.ini` в nano; изменения вступают после `stop`/`start`|
|`failover config mode {single \| cluster}`|Переключить режим. При переходе в `cluster` автоматически останавливаются неподдерживаемые службы, например DHCP|
|`failover show config`|Просмотреть файл, выход по `Q`|
|`failover show info`|Текущее состояние: режим `single/active/passive`, uptime, CPU/memory, состояния служб; в кластере — столбцы `local` и `remote`|
|`failover show active-mac-address`|Со стороны пассивного узла — доступность активного; `MAC = NA` означает недоступность|
|`failover show sync-connections`|Количество соединений в кеше синхронизации, требует `syncconnections=yes`|
|`failover start [{active \| passive}]`|Запустить `failoverd`. Без параметра — в прежнем режиме|
|`failover stop`|Остановить `failoverd`|
|`failover view <начало> <конец>`|Журнал переключений, формат `DD.MM.YYYY[.hh.mm.ss]`, только в кластере|

События журнала:

|Код|Событие|
|---|---|
|`<BOOT>`|Запуск `failoverd` при загрузке ОС|
|`<P_START>`|Ручной запуск в пассивном режиме|
|`<A_START>`|Ручной запуск в активном режиме|
|`<SWITCH>`|Переход из пассивного в активный или наоборот|

### 6.2. Порядок развёртывания кластера

```
# на обоих узлах
hostname# version
hostname# admin remove keys

# инициализация обоих узлов ОДНИМ дистрибутивом ключей
# настройка резервируемых интерфейсов: Static IP, class access, без DHCP
# настройка интерфейса синхронизации:_STATIC IP, одна подсеть на пару

hostname# failover stop
hostname# failover config edit
# [channel], [misc], [network], [sendconfig]
# Ctrl+O, Ctrl+X

hostname# failover config mode cluster

# подключить узлы к LAN, настроить коммутаторы
hostname> inet ping <testip>          # доступен ли стабильный узел

hostname# failover start active       # на первом узле
hostname# failover start passive      # на втором узле
```

Перед запуском второго узла проверьте активный:

```
hostname> failover show active-mac-address
Interface   IP-address        MAC-address
eth0        10.0.2.10         38:D5:47:C9:DA:4C
eth1        10.0.3.10         C9:DA:4C:C9:DA:4C
```

Если вместо MAC выводится `NA` — активный не виден, запуск второго в `active` приведёт к конфликту IP.

### 6.3. Что увидите после старта

```
hostname> failover show info
...
* local    * remote
failover mode   * active   * passive
failover uptime * 3d 5:26  * 0d 0:00
iplir state     * works    * works
mftp state      * works    * works
webgui state    * works    * stopped
```

Интерфейс синхронизации **не контролируется** системой защиты от сбоев. Если `failover show info` показывает данные только по одному узлу — проверьте кабель и IP интерфейса синхронизации вручную.

В кластере автоматически создаются нередактируемые служебные фильтры, в том числе:

```
ViPNet Service in   @any   @local   udp: from 2060 to 2060   pass
ViPNet Service out  @local @any     udp: from 2060 to 2060   pass
```

### 6.4. Специальные сценарии

|Сценарий|Действие|
|---|---|
|DHCP в кластере|На момент перехода в `cluster` DHCP должен быть остановлен. После развёртывания настройте DHCP-сервер/relay **на активном узле**, включите автозапуск; IP резервируемого интерфейса должен равняться его `activeip`|
|SNMP|Если агент уже настроен на одном узле, первым запускайте `failoverd` именно на нём; затем `inet snmp start` на пассивном|
|Одиночный режим|`failover config mode single` на обоих, отключить один узел от LAN; параметры интерфейсов из `failover.ini` игнорируются|
|Замена узла|Backup активного → новый узел отключён от LAN → восстановление конфигурации → задать IP синхронизации сбойного узла → заменить `activeip` в `[sendconfig]` на IP активного → разнести время плановых перезагрузок минимум на 30 минут|
|Работа с одним узлом|Допустима временно, но如果 пришли обновления ключей, а активный узел затем сぼит — восстановление из backup с обновлённым дистрибутивом ключей|

## 7. Типичные ошибки

|Симптом|Причина|Лечение|
|---|---|---|
|Кластер циклически переключается|Недоступен хотя бы один `testip` в `[channel]`|Проверить все `testip` командами `inet ping`, устранить недоступность|
|Циклические переключения после включения DGD|Один и тот же IP используется в DGD и `testip`|Разделить адреса|
|Пассивный узел не видит активного|Proxy ARP включён, ARP-ответы не проходят, port-security блокирует|Проверить коммутатор: Proxy ARP off, ARP в обе стороны|
|Переключение не происходит при обрыве между HW и хостом|`checkonlyidle=yes`, а `testip` за промежуточным коммутатором|Поставить `checkonlyidle=no` или подключить `testip` напрямую|
|Проверяется только один интерфейс|Одинаковый `testip` в нескольких `[channel]`|Уникальный `testip` в подсети каждого интерфейса|
|`testip` «всегда живой»|Указан `127.0.0.1`|Указать реальный маршрутизатор|
|Самопроизвольный failover при правке сети|Изменяли `testdevice` или параметры интерфейса при работающем `failoverd`|`failover stop` → правка → `failover start`|
|Конфликт IP после старта|Оба узла запущены с `active`|Один `active`, второй `passive`; проверить `failover show active-mac-address`|
|Трафик на адреса синхронизации блокируется|IP синхронизации совпадает с адресами защищённых узлов|Выделить подсеть или включить виртуальную видимость узлов|
|Нет ускорения после failover|`usevirtualmac=no` либо MAC на `bond`/alias|Включить на физических `eth`, разрешить два MAC на порту коммутатора|
|MAC остался виртуальным после отключения функции|Функция ранее использовалась|`machine reboot`|
|BGP не восстанавливается сразу|Сессии не синхронизируются|Ждать 1–3 минуты|
|Сессии NAT/TCP-туннелей рвутся|Не синхронизируются по дизайну|Учесть в SLA; частично — `syncalgtcp=yes`|
|L2OverIP-интерфейс не проходит проверку|`testip` указан в удалённом сегменте|Указать адрес локального сегмента и `iplir set l2overip unsolicited-frames broadcast`|
|DHCP не стартует при переводе в кластер|Служба работала в момент `failover config mode cluster`|Остановить DHCP до перевода, затем настроить на активном узле|
|Пассивный узел «не показывает» вторую колонку|Проблема интерфейса синхронизации|Проверить кабель, IP, `failover show info`|
|Wi-Fi/3G мешают кластеру|Модули не поддерживаются в кластере|Отключить до развёртывания|

1. Различаю одиночный режим и режим кластера; знаю роль `itcswd` и `failoverd`.
2. Понимаю разницу между резервируемым интерфейсом, интерфейсом кластера и интерфейсом синхронизации.
3. Знаю, что кластерный IP принадлежит только активному узлу.
4. Понимаю机制 DAD ARP и формулу `checktime + timeout × activeretries`.
5. Понимаю проверку интерфейсов и формулу `checktime + timeout × channelretries`.
6. Знаю, что `testdevice` даёт переключение примерно за 3 секунды и работает только с физическими `eth`.
7. Умею объяснить `checkonlyidle=yes` и `no` и выбрать нужное значение под拓扑.
8. Знаю параметры `[channel]`, `[network]`, `[misc]`, `[sendconfig]`, `[debug]`.

10. Помню, что не синхронизируются: NAT-сессии, журнал IP-пакетов, BGP (1–3 мин), DNS/TCP-туннели/локальные/прикладные соединения.
11. Знаю ограничения виртуальных MAC: не на `bond`/alias, два MAC на порту, `virtualmacprefix` одинаковый.
12. Проверяю кластер через `failover show info`, `failover show active-mac-address`, `failover view`.
