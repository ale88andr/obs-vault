
**Цель темы:** разделить два источника истины — данные из ViPNet Prime (справочники и ключи) и локальные конфигурационные файлы Coordinator — и науиться безопасно редактировать `iplir.conf`, понимая, что перезапишется при следующем обновлении, а что останется.

## 1. Два источника истины

```
ViPNet Prime
   │  UT-сообщения: политики / обновление справочников и ключей
   │  транспорт UT → MFTP → Coordinator
   ▼
Справочники на HW  ──┐
                     ├──► iplir.conf → iplircfg → драйвер ViPNet
Локальные правки ────┘         │
   (iplir config)              ▼
                        зашифрованный трафик
```

|Источник|Что приносит|Идеология|
|---|---|---|
|**Prime / справочники**|Узлы, связи, ViPNet ID, адреса, политики, ключи|Централизованный «контрольный план»|
|**Локальные файлы**|Режим подключения, адаптеры, видимость, туннели, метрики, отладка|Исполнение на конкретном устройстве|

Инициализация: дистрибутив ключей `ds5` с паролем, USB/CD/TFTP/консоль. **После первого подключения HW к Prime использованный `ds5` становится недействительным.**

### Правила слияния

|Параметр|Поведение при обновлении из Prime|
|---|---|
|`accessiplist` из Prime|Приходят как `addrdoc`; локальные адреса остаются и имеют приоритет за счёт метрики|
|Новые `tunnel`-адреса из Prime|Добавляются|
|Локальный `tunnel`-адрес, исчезнувший в Prime|Удаляется|
|`exclude_from_tunnels`|Имеет приоритет над настройками Prime и **не изменяется** при обновлении|
|`fqdn`|При изменении в Prime **перезаписывает** локальную правку|
|`visibility`, `visibility` у мобильных узлов|Для мобильных узлов всегда принудительно `virtual`|
|Виртуальные адреса при `auto`|При обновлении ПО перераспределяются заново|

Практический вывод: **всё, что можно задать в Prime, задавайте в Prime**. Локальные правки допустимы для «железных» особенностей и аварийных режимов, но должны быть задокументированы.

## 2. Карта конфигурационных файлов

|Файл|Секции|Назначение|
|---|---|---|
|`iplir.conf`|`[adapter]`, `[debug]`, `[dynamic]`, `[id]`, `[misc]`, `[servers]`, `[virtualip]`, `[visibility]`|Основная конфигурация защищённой сети|
|`iplir.conf-<интерфейс>`|`[db]`|Журнал прохождения IP-пакетов через интерфейс/группу (`eth0`, `ppp`, `wifi`)|
|`healthmon.ini`|`[CPU]`, `[Memory]`, `[Netdev]`, `[Disk]`, `[CPS]`, `[IP_ban]`|Пороги здоровья, SNMP, блокировка источников нагрузки|
|`failover.ini`|кластерные секции|Настройки отказоустойчивости (тема 13)|
|`mftp.conf`|транспорт MFTP|Доставка конвертов из Prime|
|`iplirdb/iplir.db-<интерфейс>`|—|Сам журнал пакетов; ротация по `maxsize`|

`iplir.conf-<интерфейс>` создаётся автоматически при запуске службы для каждого статического интерфейса из `[adapter]` и для групп динамических интерфейсов. Если добавить `[adapter]` вручную, файл появится только после цикла `start → stop`.

> Напоминание из темы 6: `iplir config eth0` редактирует **`iplir.conf-eth0`** (журнал трафика), а не IP-адрес `eth0`. Адрес задаётся через `inet ifconfig`.

## 3. Безопасные правки

```
hostname> iplir show config          # просмотр, Q — выход
hostname# iplir stop                 # остановить iplircfg
hostname# iplir config               # GNU nano: Ctrl+O — save, Ctrl+X — exit
hostname# iplir start
hostname> iplir option show
hostname> iplir show adapters
```

|Правило|Почему|
|---|---|
|Править только при `iplir stop`|Иначе служба перезапишет файл при сохранении состояния|
|Не редактировать «нередактируемые» поля|Они пересчитываются службой (`id`, `firewallip`, `virtualip`, `accessip`, …)|
|Не править `iplir.conf` напрямую «на ходу»|Изменения не попадут в драйвер до перезапуска|
|После правки проверить `iplir option show`|Подтверждает, что служба приняла конфигурацию|
|Помнить про задержку|Изменения через `iplir option` применяются с задержкой ~60 с|

## 4. Секции `iplir.conf`

`iplir.conf` — восемь отдельных блоков, каждый за свой слой системы. Если запомнить эту логику, файл перестаёт быть страшным.

```
Физика:        [adapter]      ← какие интерфейсы вообще exist для ViPNet
Идентичность:  [id]           ← кто известен, где живёт, как к нему идти
               [servers]      ← какие координаторы известны (только чтение)
Транспорт:     [dynamic]      ← как пробиваться из-за NAT
               [misc]         ← таймеры, шифрование, форвардинг, UDP-порты
Адреса:        [virtualip]    ← фабрика виртуальных адресов 11.x / 12.x
               [visibility]   ← по какому адресу обращаться: real или virtual
Наблюдение:    [debug]        ← что и как писать в syslog
```

Сводная таблица

| Секция         | Простыми словами                          | Вопрос, на который отвечает                                                                           |
| -------------- | ----------------------------------------- | ----------------------------------------------------------------------------------------------------- |
| `[adapter]`    | Паспорт сетевого интерфейса               | «Какой кабель считается своим и можно ли через него пускать IP?»                                      |
| `[id]`         | Адресная книга узлов ViPNet               | «Кто мне известен, по какому IP/port его искать, как к нему обращаться и что туннелировать?»          |
| `[dynamic]`    | Режим «я за NAT, нужен сервер соединений» | «Как установить связь, если публичного адреса нет?»                                                   |
| `[misc]`       | Руль управляющей службы                   | «Как часто опрашивать узлы, сколько UDP-портов держать, какой формат пакетов, включён ли форвардинг?» |
| `[virtualip]`  | Фабрика виртуальных адресов               | «С какого адреса раздавать 11.0.0.1, 12.0.0.1 и т.д.?»                                                |
| `[visibility]` | Правила показа адресов                    | «Обращаться к узлам по реальным или по виртуальным адресам?»                                          |
| `[debug]`      | Настройки журналирования `iplircfg`       | «Насколько подробно логировать и откуда брать сообщения?»                                             |
| `[servers]`    | Список известных координаторов            | «Какие координаторы мне известны?»                                                                    |

## `[adapter]` — интерфейсы

```
[adapter]
name=eth0
allowtraffic=on
type=external
```

**Зачем:** связать физический интерфейс Linux с драйвером ViPNet.

Главное правило:

> Если статический интерфейс не описан секцией `[adapter]`, все IP-пакеты через него блокируются.

Но есть важная оговорка: **если в файле нет ни одной секции `[adapter]`**, служба при старте сама получает список интерфейсов от системы и создаёт секции автоматически. Опасность возникает, когда секции уже есть, а новый интерфейс в них не попал.

|Параметр|Смысл|
|---|---|
|`allowtraffic=on`|Пропускать пакеты, но согласно сетевым фильтрам. По умолчанию.|
|`allowtraffic=off`|Блокировать всё независимо от фильтров.|
|`type=external`|Внешний интерфейс. В static-режиме — тот, через который идём к NAT/провайдеру.|
|`type=internal`|Внутренний интерфейс. В dynamic-режиме такими должны быть все интерфейсы.|
|`name`|Только чтение. `eth0:0`, `eth0:1` всё равно видятся как `eth0`.|

**Ловушка:** добавили `[adapter]` вручную, но не перезапустили службу — файл `iplir.conf-eth0` не появится. Нужно `start → stop → правка → start`.

Динамические группы `ppp` и `wifi` секций не требуют. Встроенный `wlan0` в группу `wifi` **не входит**.

## `[id]` — узлы и адреса

Это самая важная и самая большая секция.

```
[id]
id=0x15ea000b
accessiplist=89.135.15.2, 1, 0.0.0.0, 0, manual, 55777
ip=192.168.10.1, 11.0.0.1
proxyid=0
tcptunnelport=80
visibility=virtual
tunnel=192.168.201.5-192.168.201.10
exclude_from_tunnels=192.168.201.7-192.168.201.7
usetunnel=on
```

**Зачем:** описать каждый известный узел ViPNet.

- **Первая секция `[id]`** — это сам ViPNet Coordinator HW.
- **Остальные секции `[id]`** — связанные координаторы и узлы.
- Секции различаются по параметру `id=` — ViPNet ID из Prime.

### Что именно здесь решается

|Параметр|Зачем|
|---|---|
|`id=0x...`|Уникальный идентификатор узла. Присваивается в Prime. Только чтение.|
|`accessiplist`|IP-адреса доступа и их приоритет. Формат: `IP, метрика, реальный IP, № интерфейса, тип, порт`.|
|`ip`|Пара «реальный IP, виртуальный IP». Первым идёт приоритетный адрес.|
|`firewallip`|Адрес NAT/межсетевого экрана, куда реально уходит UDP. Только чтение.|
|`port`|Порт назначения, если узел за NAT. По одному на секцию.|
|`proxyid`|Признак работы за NAT: в своей секции `0` — static, `0xfffffffe` — dynamic; в чужой — ID сервера соединений или `0xfffffffe`.|
|`tcptunnelport`|Порт для TCP-туннеля, по умолчанию **80**. Рассылается клиентам.|
|`fqdn`|Домен для восстановления связи при смене IP. Перезаписывается из Prime.|
|`checkconnection_interval`|20–3600 с. Если не задан — используется `server_pollinterval`.|
|`blockforward=on`|Блокировать транзит к узлу с кодом 70. По умолчанию absent/off.|
|`visibility`|Индивидуальная видимость узла: `real` или `virtual`.|
|`tunnelvisibility`|Видимость всех узлов, которые туннелирует этот координатор.|
|`tunnel`|Диапазоны незащищённых адресов: `192.168.0.1-192.168.0.100` или `... to 192.120.0.1`. До **1000** диапазонов.|
|`exclude_from_tunnels`|Исключения из туннеля. Только в чужих секциях `[id]`. Приоритетнее Prime.|
|`tunnel_local_networks`|`on` — всегда через туннелирующего координатора; `off` — можно напрямую в локальной подсети.|
|`usetunnel`|`off` у удалённого координатора означает: трафик к его туннелируемым узлам **не шифруется**. По умолчанию `on`.|

### Что редактировать нельзя

Служба пересчитывает эти поля сама:

```
accessip, always_use_server, dynamic_timeout, id,
firewallip, fixfirewall, name, virtualip, version
```

Если их «исправить» вручную, правка исчезнет после перезапуска.

### Метрики `accessiplist`

Вручную задают только:

- IP доступа;
- метрику;
- порт.

Остальное заполняет `iplircfg`:

- реальный IP узла;
- номер интерфейса;
- тип регистрации: `auto`, `manual`, `addrdoc`.

`addrdoc` — адрес пришел из справочников Prime. Метрика `auto` всегда проигрывает ручной, потому что равна `максимальная ручная + 100 мс`.

## `[dynamic]` — работа из-за динамического NAT

```
[dynamic]
dynamic_proxy=on
forward_id=0x15c8000a
always_use_server=off
timeout=25
port_auto_change=off
```

**Зачем:** описать режим, когда у HW нет публичного адреса и он сидит за NAT.

|Параметр|По умолчанию|Смысл|
|---|---|---|
|`dynamic_proxy`|`off`|Главный выключатель режима. Если `off`, остальные параметры секции игнорируются.|
|`forward_id`|—|ViPNet ID сервера соединений. Обязательно должен быть доступен из внешней сети по публичному IP.|
|`always_use_server`|`off`|`off` — ищем прямую связь, сервер соединений используется пока не получилось; `on` — весь внешний трафик идёт через сервер.|
|`timeout`|`25`|Keepalive в секундах. Пакеты пробивают NAT и удерживают трансляцию.|
|`port_auto_change`|`off`|Автосмена порта, если сервер соединений недоступен.|

Команда-аналог из темы 9:

```
hostname# iplir option mode dynamic 0x15c8000a
hostname# iplir option mode static
hostname# iplir option mode auto
```

**Ловушка:** указали `forward_id`, но сервер соединений сам за NAT или недоступен — dynamic-режим не заработает.

## `[misc]` — глобальные параметры службы

**Зачем:** задать параметры для всей защиты и обмена служебными пакетами.

```
[misc]
ipforwarding=on
ciphertype=gost
packettype=4.1
udp_ports_count=255
client_pollinterval=300
server_pollinterval=900
timediff=7200
```

|Параметр|По умолчанию|Зачем|
|---|---|---|
|`ciphertype`|`gost`|Алгоритм шифрования исходящих пакетов. Другого значения нет.|
|`packettype`|`4.1`|Формат исходящих пакетов. `4.0` — для старых версий ViPNet. Входящий формат определяется автоматически.|
|`ipforwarding`|`on`|Транзит и туннелирование. `off` / `system` — только для отладки.|
|`udp_ports_count`|`255`|Сколько UDP-портов слушать. Старт берётся из `port` своей `[id]`, по умолчанию 55777 → диапазон 55777–56031.|
|`client_pollinterval`|`300 с`|Опрос клиентов, для которых HW — сервер IP-адресов.|
|`server_pollinterval`|`900 с`|Опрос других координаторов. Должен совпадать у всех координаторов сети.|
|`ifcheck_timeout`|`30 с`|Как часто опрашивать состояние интерфейсов.|
|`timediff`|`7200 с`|Допустимая разница времени отправки и получения. Защита от «старых» пакетов. Диапазон 1–7200.|
|`mssdecrease`|`0`|Уменьшение MSS на 20–40 байт, если ping проходит, а TCP не поднимается из-за фрагментации.|
|`msg_compress_level`|`3`|Сжатие служебных сообщений. На нагруженных узлах не выше 5.|
|`iscaggregate`|`on`|Накопление служебного трафика и отправка не чаще раза в минуту.|
|`tcptunnel_establish`|`off`|Включение TCP-туннеля. Порт — из `tcptunnelport` в `[id]`.|
|`tunnel_virt_assignment`|`auto`|Назначение виртуальных адресов туннелируемых узлов. `manual` — вручную в `tunnel`.|
|`be_dg_coordinator`|`auto`|Объявлять ли HW default gateway.|
|`cef_ip`, `cef_port`, `cef_format`|`514`, `hw`|Экспорт CEF. Нельзя указывать localhost, свои IP и алиасы.|
|`warnoldautosave`|`on`|Предупреждать о конфигурациях, автосохранённых более месяца назад.|
|`timesync`|`off`|Только для клиентского ПО; на координаторе менять нельзя.|

**Ловушка:** разные `server_pollinterval` у координаторов → статусы узлов «мигают».

## `[virtualip]` — фабрика виртуальных адресов

```
[virtualip]
startvirtualip=11.0.0.1
starttunnelvirtualip=12.0.0.1
```

**Зачем:** выдавать виртуальные адреса, когда реальные подсети разных филиалов пересекаются.

|Параметр|По умолчанию|Смысл|
|---|---|---|
|`startvirtualip`|`11.0.0.1`|Старт базовых виртуальных адресов защищённых узлов.|
|`maxvirtualip`|не задан|Верхняя граница диапазона. Должен быть больше `startvirtualip`.|
|`starttunnelvirtualip`|`12.0.0.1`|Старт виртуальных адресов для туннелируемых диапазонов в `auto`-режиме. Для одиночных туннелируемых адресов — `11.0.0.1`.|

**Опасная операция:** смена `startvirtualip` перераспределяет **все** базовые виртуальные адреса, включая параметры `ip=` в секциях `[id]`. После этого клиентам нужно заново получить справочники.

## 7. `[visibility]` — реальные или виртуальные адреса

```
[visibility]
default=virtual
subnet_real=0x5155
subnet_virtual=0x5156,0x5157
tunneldefault=real
```

**Зачем:** выбрать, по какому адресу «стучаться» к узлу.

| Параметр         | По умолчанию | Смысл                                                                |
| ---------------- | ------------ | -------------------------------------------------------------------- |
| `default`        | `virtual`    | Видимость для всех узлов, у которых нет персональной настройки.      |
| `subnet_real`    | absent       | ID сетей ViPNet, узлы которых видны по реальным IP.                  |
| `subnet_virtual` | absent       | ID сетей ViPNet, узлы которых видны по виртуальным IP.               |
| `tunneldefault`  | `real`       | Видимость туннелируемых узлов, если в `[id]` нет `tunnelvisibility`. |

Приоритет:

```
1. visibility в секции [id] узла
2. subnet_real / subnet_virtual для сети узла
3. default в [visibility]
```

Для туннелируемых узлов отдельно:

```
1. tunnelvisibility в секции [id] координатора
2. tunneldefault в [visibility]
```

Идентификаторы сетей смотрите в Prime или командой:

```
hostname# iplir info
```

**Ловушки:**

- один и тот же ID сети нельзя указать и в `subnet_real`, и в `subnet_virtual`;
- при старте ID сортируются и.groupруются по 8 на строку;
- при виртуальной видимости нужен корректный default-маршрут;
- перед сменой `virtual → real` желательно сначала сделать `inet ping` на виртуальный адрес узла.

## `[debug]` — логирование `iplircfg`

```
[debug]
syslog-level=1
debuglogfile=syslog:daemon.debug
```

**Зачем:** управлять подробностью системного журнала управляющей службы.

|Параметр|По умолчанию|Смысл|
|---|---|---|
|`syslog-level`|`1`|Уровень важности. Локально: −1…3. Удалённо: −1…4.|
|`debuglogfile`|`syslog:daemon.debug`|Источник сообщений: `syslog:<facility.level>`. Facility: `kern`, `user`, `daemon`; level: `err`, `info`, `debug`.|

**Ловушка:** если включить уровень `4` при удалённом логировании, а потом перейти на локальное, уровень сам не сбросится. Нужен перезапуск `iplircfg`, то есть штатный цикл `iplir stop` → `iplir start`.

## `[servers]` — известные координаторы

```
[servers]
server=0x15ea0001,Control Center
server=0x15ea0002,HQ-GW
```

**Зачем:** хранить список координаторов, известных этому узлу.

Формат: `ID,имя`.

Параметр `server` **нередактируемый**. Он заполняется службой на основе справочников. Эту секцию нужно читать, а не править.

## 10. Как секции живут вместе

```
[adapter]     решили: через eth0 можно, через eth1 нельзя
     |
[id]          решили: узел 0x15ea000b ищем по 89.135.15.2:55777
     |
[dynamic]     решили: сами мы за NAT, сервер соединений 0x15c8000a
     |
[misc]        решили: 255 UDP-портов, ping каждые 900 с, шифруем ГОСТ
     |
[virtualip]   решили: виртуальные адреса начинаются с 11.0.0.1
     |
[visibility]  решили: к этому узлу идём по виртуальному адресу
     |
[debug]       решили: писать syslog с уровнем 1
```

И сверху над всем этим — **ViPNet Prime**:

|Что приходит из Prime|Что остаётся локальным|
|---|---|
|Узлы, ViPNet ID, связи, ключи, `fqdn`,`tunnel`-адреса|`[adapter]`, `[dynamic]`, `[misc]`, метрики, `exclude_from_tunnels`, часть `[visibility]`|
|`addrdoc` в `accessiplist`|`manual` в `accessiplist`|
|Новые`tunnel`-диапазоны добавляются|Локальные исключения не перезаписываются|

Практическое правило: **если параметр можно задать в Prime — задавайте в Prime**. Локальные правки нужны для «железных» особенностей и аварийных режимов.

## 11. Памятка по правке

```
hostname# iplir stop
hostname# iplir config
# Ctrl+O — сохранить, Ctrl+X — выйти
hostname# iplir start
hostname> iplir show config
hostname> iplir option show
hostname> iplir show adapters
hostname> iplir ping 0x15ea000b
```

| Правило                           | Почему                                                   |
| --------------------------------- | -------------------------------------------------------- |
| Не править при работающей службе  | `iplircfg` может перезаписать файл.                      |
| Не трогать поля только для чтения | Они пересчитываются автоматически.                       |
| Проверять `iplir option show`     | Подтверждает, что служба приняла конфигурацию.           |
| Помнить про задержку ~60 с        | Изменения через `iplir option` применяются не мгновенно. |


---
### `[adapter]`

```
[adapter]
name=eth0
allowtraffic=on
type=external
```

| Параметр       | Значения                   | Команда из темы 7                                             |
| -------------- | -------------------------- | ------------------------------------------------------------- |
| `allowtraffic` | `on` (по умолчанию), `off` | `inet ifconfig enable`                                        |
| `type`         | `internal`, `external`     | `inet ifconfig ... type`, видно в `inet show interface state` |
| `name`         | только чтение              | системное имя интерфейса                                      |

Критично: **если статический интерфейс не описан секцией `[adapter]`, все проходящие через него IP-пакеты блокируются**. Если в файле нет ни одной секции `[adapter]`, служба при старте создаёт их автоматически по списку интерфейсов системы.

Динамические интерфейсы групп `ppp` (встроенный модем) и `wifi` (внешние Wi-Fi-адаптеры) разрешены по умолчанию и секций не требуют. Встроенный `wlan0` в группу `wifi` **не входит**.

Тип: dynamic NAT → все интерфейсы `internal`; static NAT → внешний `external`, остальные `internal`.

### `[debug]`

```
[debug]
syslog-level=1
debuglogfile=syslog:daemon.debug
```

Уровни: при локальном протоколировании −`1…3`, при удалённом −`1…4`; по умолчанию **1**. Если включить уровень 4 при удалённом логировании, а затем перейти на локальное — уровень не сбросится сам; только перезапуск `iplircfg` вернёт значение по умолчанию.

### `[dynamic]`

```
[dynamic]
dynamic_proxy=on
forward_id=0x15c8000a
always_use_server=off
timeout=25
port_auto_change=off
```

`forward_id` — ViPNet ID сервера соединений; он обязан быть доступен из внешней сети по публичному IP. Если `dynamic_proxy=off`, остальные параметры секции игнорируются.

### `[id]`

Первая секция — **собственный узел**, остальные — связанные узлы.

```
[id]
id=0x15ea000b
accessiplist=89.135.15.2, 1, 0.0.0.0, 0, manual
ip=192.168.10.1, 11.0.0.1
proxyid=0
tcptunnelport=80
visibility=virtual
tunnel=192.168.201.5-192.168.201.10
exclude_from_tunnels=192.168.201.7-192.168.201.7
```

|Параметр|Назначение / значение|
|---|---|
|`accessiplist`|IP доступа, метрика, реальный IP, № интерфейса, тип (`auto`/`manual`/`addrdoc`), порт|
|`blockforward`|`on` блокирует транзит к узлу с кодом 70; по умолчанию `off`|
|`fqdn`|Домен для восстановления связи при смене IP; перезаписывается из Prime|
|`checkconnection_interval`|20–3600 с; если не задан — используется `server_pollinterval`|
|`ip`|`реальный, виртуальный`; первым — приоритетный адрес|
|`port`|Порт назначения, если узел за NAT; только один на секцию|
|`proxyid`|Своя секция: `0xfffffffe` (dynamic) или `0` (static). Чужая: `0xfffffffe` (HW — сервер соединений) или ID координатора|
|`tcptunnelport`|0–65535, по умолчанию **80**; рассылается клиентам сервера соединений|
|`tunnel`|`<real1>-<real2> to <virt1>-<virt2>`; не более **1000** диапазонов|
|`exclude_from_tunnels`|Исключения; приоритетнее Prime|
|`tunnel_local_networks`|`on` (по умолчанию) — только через туннелирующего координатора; `off` — напрямую в локальной подсети|
|`tunnelvisibility`|`real` / `virtual` для всех узлов этого координатора|
|`usetunnel`|`on`/`off`; при `off` трафик к его туннелируемым узлам **не шифруется**|
|`visibility`|Индивидуальная видимость узла: `real`/`virtual`|

Только для чтения: `accessip`, `always_use_server`, `dynamic_timeout`, `id`, `firewallip`, `fixfirewall`, `name`, `virtualip`, `version`.

### `[misc]` — самые важные параметры

```
[misc]
ipforwarding=on
ciphertype=gost
packettype=4.1
timediff=7200
udp_ports_count=255
server_pollinterval=900
client_pollinterval=300
```

| Параметр                             | По умолчанию | Комментарий                                                                           |
| ------------------------------------ | ------------ | ------------------------------------------------------------------------------------- |
| `be_dg_coordinator`                  | `auto`       | Объявление HW как default gateway                                                     |
| `ciphertype`                         | `gost`       | Только `gost`                                                                         |
| `cef_ip` / `cef_port` / `cef_format` | 514 / `hw`   | Экспорт CEF; нельзя указывать localhost и свои алиасы                                 |
| `client_pollinterval`                | 300 с        | Опрос клиентов                                                                        |
| `ifcheck_timeout`                    | 30 с         | Опрос параметров интерфейсов                                                          |
| `ipforwarding`                       | `on`         | `off`/`system` — только для отладки; без него не работают транзит и туннели           |
| `iscaggregate`                       | `on`         | Накопление служебного трафика раз в минуту                                            |
| `msg_compress_level`                 | 3            | 1–9; на нагруженных узлах не выше 5                                                   |
| `mssdecrease`                        | 0            | 20–40 байт, если ping есть, а TCP не поднимается                                      |
| `packettype`                         | 4.1          | `4.0` — совместимость со старыми версиями; входящий формат определяется автоматически |
| `server_pollinterval`                | 900 с        | Должен совпадать у всех координаторов сети                                            |
| `tcptunnel_establish`                | `off`        | Включение TCP-туннеля                                                                 |
| `timediff`                           | 7200 с       | 1–7200; драйвер блокирует «старые» пакеты                                             |
| `timesync`                           | `off`        | На координаторе не меняется                                                           |
| `tunnel_virt_assignment`             | `auto`       | `manual` — ручные виртуальные адреса туннелей                                         |
| `udp_ports_count`                    | 255          | Старт — `port` в собственной `[id]`, по умолчанию 55777                               |
| `warnoldautosave`                    | `on`         | Предупреждение о конфигурациях старше месяца                                          |

### `[servers]` — только чтение

```
[servers]
server=0x15ea0001,Control Center
server=0x15ea0002,HQ-GW
```

Список координаторов, известных узлу: `ID,имя`.

### `[virtualip]` и `[visibility]`

```
[virtualip]
startvirtualip=11.0.0.1
starttunnelvirtualip=12.0.0.1

[visibility]
default=virtual
subnet_real=0x5155
subnet_virtual=0x5156,0x5157
tunneldefault=real
```

- `startvirtualip` по умолчанию `11.0.0.1`, `starttunnelvirtualip` — `12.0.0.1` (одиночные туннелируемые узлы — `11.0.0.1`).
- Изменение `startvirtualip` **перераспределяет все базовые виртуальные адреса**, включая `ip` в секциях `[id]`.
- Один и тот же ID сети нельзя указывать и в `subnet_real`, и в `subnet_virtual`. При старте ID сортируются и группируются по 8 строк.
- `tunneldefault` по умолчанию `real`.

## 5. Синтаксические ловушки

|Ошибка|Последствие|
|---|---|
|Пробел перед числом после запятой или его отсутствие|Парсер может не понять метрику/порт|
|ID без префикса `0x`|Неверный идентификатор узла/сети|
|Две секции `[id]` с одним `id=`|Служба не сможет различить узлы|
|Правка `firewallip` / `virtualip` вручную|Значение пересчитается службой, правка «пропадёт»|
|Попытка задать `visibility` и для сети, и для узла сразу|Побеждает узел — это может быть неожиданностью|
|`subnet_real` и `subnet_virtual` с одинаковым ID|Конфликт настроек видимости|
|Правка `[adapter]` без перезапуска|Файл `iplir.conf-<интерфейс>` не создастся|
|Ожидание мгновенного эффекта от `iplir option`|Задержка до 60 с|
|Увеличение `msg_compress_level` > 5 на нагруженном узле|Просадка по CPU|
|Слишком маленький `timediff`|Блокировка легальных пакетов из-за дрейфа времени|

## 7. Типичные ошибки

| Симптом                                  | Причина                                       | Лечение                                   |
| ---------------------------------------- | --------------------------------------------- | ----------------------------------------- |
| Правка в `iplir.conf` не применяется     | Файл правили при работающей службе            | `stop` → `config` → `start`               |
| После обновления из Prime правка исчезла | Параметр перезаписывается центром             | Перенести изменение в Prime               |
| `exclude_from_tunnels` не сработал       | Задан в собственной секции `[id]`             | Только в секциях **других** координаторов |
| Адрес доступа «сбросился» на `auto`      | Метрика не задана явно                        | Указать метрику вручную                   |
| Интерфейс блокирует трафик               | Нет секции `[adapter]`                        | Добавить секцию и перезапустить службу    |
| Нет файла `iplir.conf-eth1`              | `[adapter]` добавили вручную без перезапуска  | `start` → `stop` → правка → `start`       |
| Туннель не шифруется                     | `usetunnel=off` у удалённого координатора     | Включить                                  |
| TCP не поднимается при успешном ping     | Фрагментация                                  | `mssdecrease` 20–40 на принимающем узле   |
| Статусы координаторов «мигают»           | Разные `server_pollinterval`                  | Выровнять                                 |
| Пакеты отбрасываются как «старые»        | Слишком жёсткий `timediff` или рассинхрон NTP | Проверить время, увеличить `timediff`     |
| Ошибка совместимости со старым узлом     | `packettype=4.1`                              | Перейти на `4.0`                          |
| Служебный трафик «съедает» канал         | `iscaggregate=off`                            | Вернуть `on`                              |
